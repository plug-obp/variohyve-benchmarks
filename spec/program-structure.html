VarioHyve Language Specification

Program Structure

VarioHyve explores behavioral federation for systems-of-systems and modeling environments. This chapter defines how programs receive capabilities and how module entry differs from tooling evaluation. The current sequential core interacts with foreign participants through the Alien/Expat boundary; analysis and concurrent coordination remain research directions, including the proposed semantic language interface.

A Program Is a Single Expression

The grammar entry point is:

top: expression? EOF;

A VarioHyve program is an optional single expression. A top-level class literal, named or anonymous, serves as a module. The service that instantiates it supplies the existing object instances required by its constructor; the language does not prescribe their number or names.

class Application(consoleService, clockService, settings) {
    console = consoleService;
    clock = clockService;
    config = settings;

    run { console.print(clock.now) }
}

class(consoleService, clockService, settings) { ... } has the same dependency rules. Naming the class does not create an ambient binding or change how it receives capabilities. The top-level expression is optional; empty input is represented as EmptyExpression and is a no-op for expression evaluation. The module-instantiation entry specifically requires a class literal; it rejects empty input and other expression forms without evaluating them.

Four Sources of Class Capabilities

A class literal, whether named or anonymous, obtains its required capabilities through four mechanisms:

  1. Superclass inheritance: inherited behavior and the capabilities available through that behavior.
  2. Mixin composition: behavior contributed by composed mixins, preserving their definition scopes and the capabilities available through that behavior.
  3. Lexical nesting: bindings available from the enclosing scope in which the class is defined.
  4. Constructor parameters: existing objects supplied when an instance is constructed.

These describe where capabilities come from, not a new lookup priority. The language’s lookup rules still distinguish lexical scope, composition and inheritance. Calling a class from another scope does not give it that caller’s lexical bindings. Constructor arguments supply object references, not an implicit caller environment.

Constructor parameters are initializer-only bindings. Persistent behavior uses values explicitly bound to instance slots, or deliberate captures of expressions created during initialization. Member-class declarations access the enclosing instance and declaration origin; they do not capture its constructor parameters. Named and anonymous class expressions retain their actual lexical scopes.

Capabilities include ordinary VarioHyve objects, callable class objects, and Aliens representing foreign services. Sending messages to an available object may return further objects; such access derives from that object’s authority and is not an additional ambient acquisition mechanism.

Top-Level Classes and Instantiation

Normal module evaluation starts in an empty top activation at the base of the lexical chain. This is an activation object, not a separate environment or an implicit platform object. It contributes no capability bindings and has no capability-bearing parent or receiver. Keeping this execution frame is compatible with saying that a top-level class has no enclosing application scope: the empty root supplies no interesting capabilities.

Under this normal entry contract, the top-level class inherits only from the language root Object and composes no mixins. The empty top activation supplies no other superclass or mixin to resolve. The root Object relationship is part of the object model; it does not supply an ambient platform namespace or host services. Internal lexical links may retain the empty activation without making it an enclosing application object exposed through outer.

This is VarioHyve’s Newspeak-inspired module discipline: dependencies are supplied as objects when a module is instantiated, rather than imported from global scope.

Consequently, constructor parameters are the only way to supply external capabilities to a top-level module. There can be zero, one, or several parameters, with the normal declared arity. No name such as kernel or platform is reserved or required. A zero-parameter top-level module receives no external capabilities through construction.

The instantiation service acquires or already holds the existing objects needed by the module, then supplies them as arguments. Those objects may come from previously constructed modules, explicit platform assembly, or foreign systems through the Alien/Expat boundary. How that service acquires them is external to the module’s lexical scope. The module cannot discover the service’s other objects, its registry, or its caller scope. Objects intentionally passed as arguments retain their own behavior and reachable object graphs.

Constructor parameters do not make a top-level superclass or mixin clause legal: class structure is established before that class’s constructor receives arguments. A module can instead use supplied class/mixin objects when defining nested classes inside the constructed module:

class Module(baseClass, loggingMixin, output) {
    Base = baseClass;
    Logging = loggingMixin;
    console = output;

    class Worker(identifier) <: Logging < Base {
        id = identifier;
        report { console.print(id) }
    }
}

Module has only root Object inheritance and no composition. Its nested Worker uses all four routes: Base, Logging, the enclosing console, and its own identifier argument. The same rules hold for anonymous class literals.

The Kernel Parameter

A kernel is an optional ordinary capability bundle, not the unique parameter or a privileged entry mechanism. An application may choose a bundle, several independent service objects, or a mixture:

class(kernel, consoleService, repository) {
    null = kernel.null;
    true = kernel.true;
    false = kernel.false;
    console = consoleService;
    records = repository;

    run { console.print(records.summary) }
}

Here kernel is one ordinary argument. A class(kernel) { ... } example is simply a one-argument convention. The instantiation service must honor the module’s declared constructor interface rather than always inserting one kernel. There is no global environment or implicit platform lookup.

Consequences

  • Explicit dependencies. Superclass inheritance, mixin composition, lexical nesting and constructor parameters are the four class capability routes. The top-level restrictions leave parameters as the external entry route.
  • Testability. Supply alternatives for individual arguments or for a bundle without changing the class’s lookup or invocation semantics.
  • Analysis boundary. An analysis must account for all supplied arguments and their reachable behavior. Supplying abstract input objects alone does not implement abstract interpretation; domains, effects and machine semantics also need an appropriate analysis model.
  • Isolation depends on reachability. A nested class can access its enclosing scope, and inherited/composed behavior retains its own capabilities. Passing a narrow argument does not remove those other routes. Separate top-level modules with appropriately restricted argument graphs provide a clearer boundary.

Optional Bootstrap Bundle

A platform may bundle canonical null/Boolean values, library objects, collections and I/O capabilities for convenience. Such a bundle’s inventory is a platform contract, not a required module signature. Services can equally be supplied as separate arguments. The current bootstrap exports null, true and false; nil may be a platform alias for the same null object, not a second null value.

The implemented native Boolean protocol uses eager and/or and thunk-taking andThen/orElse, with ifTrue, ifFalse and not. Numeric, string and collection protocols remain library milestones. The inventory of one bootstrap bundle must not be mistaken for the language’s only possible set of constructor parameters.

Bootstrap Conformance Requirements

These requirements describe normal module entry with an empty top activation. The explicitly supplied tooling contexts below have a different set of available objects, while using the same language lookup and invocation rules.

The visitor bootstrap implements this entry through BootstrapRuntime.instantiateModule(source, maxSteps, arguments...). It accepts named and anonymous class literals with zero, one or multiple constructor parameters, preserves argument identity/sharing through the ordinary boundary, and rejects arity mismatches. It creates an empty top activation with no platform/service bindings, parent or receiver, uses only structural root Object inheritance, and rejects every explicit top-level superclass or mixin clause. Constructor arguments do not make such clauses legal.

The result is the constructed module instance as an Expat. The host explicitly chooses any subsequent entry message; the service does not guess main or run. Definition, construction and synchronous callbacks share one transition budget. Supplied objects retain their reachable capabilities and lexical captures. See the entry contract.

BootstrapRuntime.evaluate remains a distinct tooling expression context with the assembled kernel as its lexical parent and receiver. It does not enrich the empty module root. Nested classes can use explicitly available superclass and direct mixin definitions, with initializer arguments routed from their own constructor bindings. See the implemented construction contract for composition limits and the bootstrap roadmap.

Development and Debugging Contexts

Tools may explicitly supply capabilities for development, debugging and design-time expression evaluation. For example, an evaluator can provide a console, test objects or a mirror service through its evaluation activation or an enclosing tooling object. A debugger can evaluate in an explicitly selected activation, using that activation’s existing lexical bindings. These contexts need not be empty.

This uses the same object-based lexical scope, lookup, invocation and Alien/Expat protocol as ordinary execution. It is not an ambient global registry or a fifth capability mechanism: the tool explicitly supplies objects to the evaluation context. It must distinguish this context from normal module entry and must not silently enrich the empty root used by ordinary modules.

Objects, closures and classes created in a tooling context retain their actual definition scopes. A class evaluated with tool-supplied lexical bindings may resolve superclass or mixin objects from that scope under the usual rules; it is not an isolated module defined over an empty top activation. Moving such a class to normal module entry requires making its dependencies explicit, rather than silently dropping captured references or preserving hidden tool authority. See Tooling Architecture.

Error Handling

Status: v1 design is intentionally minimal.

The bootstrap reports fatal runtime errors, including:

  • Missing selector — an ordinary send finds no exact selector, or invocation exhausts exact operations and eligible generated callable bindings at the requested arity. The bootstrap reports a diagnostic; it does not invoke a language-level doesNotUnderstand: handler.
  • Dead context — a ^ return targets a method or initializer home that has retired. See Literals — Early Return.
  • Premature initializer completion — a return targets an initializer whose slot phase has not completed, including its final slot expression. See Initializer completion.

These are fatal language failures with diagnostic messages, not recoverable language exception values in the current bootstrap. Public failures do not expose raw activation addresses or host exceptions. Boundary failures preserve their defined kinds; see Foreign Objects. See Future Directions for DNU plans.
