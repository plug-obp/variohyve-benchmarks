VarioHyve Language Specification

VarioHyve for Systems-of-Systems and Federated Modeling

Most programming languages are designed around a single application: one runtime, one concurrency model, one object model, one team, one semantic universe. Heterogeneity — different languages, different tools, different organizations, different timing models — is treated as an exception to be bridged from the outside.

Systems-of-Systems (SoS) work the opposite way. Multiple partially-autonomous subsystems, implemented by different teams with different tools under different governance regimes, must still compose into a coherent whole. Heterogeneity is not the exception — it is the structure. VarioHyve is designed from first principles around that reality.

This section explains why each architectural choice in VarioHyve maps directly to the demands of SoS design and federated behavioral modeling.

Heterogeneity as the Default, Not the Exception

The VarioHyve spec opens with a design statement that sets the tone:

“multiple subsystems (potentially implemented in different languages, running on different runtimes, governed by different concurrency models) must compose into a coherent whole.”

This is not a use case. It is the baseline design constraint. Every structural decision — no global environment, constructor-parameter injection, the Alien/Expat boundary model, the AAM-style interpreter — flows from this commitment.

Explicit Constructor Dependencies

VarioHyve has no global environment and no import statements. Named and anonymous class literals obtain capabilities through superclass inheritance, mixin composition, lexical nesting, and constructor parameters. Normal module evaluation has an empty top activation at its base, with no enclosing application scope. The top-level class inherits only from root Object and composes no mixins. Its external dependencies therefore arrive through its constructor parameters. See Program Structure.

Development and debugging tools may explicitly provide richer evaluation contexts under the same language rules. These contexts do not silently enrich normal module roots, and results may capture the supplied tooling objects.

class Mission(consoleService, clockService, communicationBus) {
    console = consoleService;
    clock = clockService;
    bus = communicationBus;
}

An instantiation service supplies existing objects it has acquired or already holds. There can be any declared number of arguments. A kernel object may bundle several dependencies, but neither its name nor a single-argument signature is required. The service’s remaining capabilities do not become a lexical scope for the module. Access to further objects through a supplied service is part of that service’s authority.

In SoS terms, this means:

  • Partitioning follows object reachability. A module obtains another participant’s services only through the object graphs made available to it.
  • Deployment can replace dependencies independently. Supply a mock clock, a real communication bus, or a recording console without changing lookup.
  • Analysis has explicit inputs. All constructor arguments and their reachable behavior must be modeled; this is not restricted to one kernel object.

Optional bundles can simplify repeated deployment configurations:

Bundle conventionExample contentsUse case
ConcreteKernelReal I/O, real clock, real busDeployment
SimKernelVirtual clock, mock sensors, replay busSimulation
TestKernelRecording console, fault injectorTesting
AbstractKernelAbstract input values and effect modelsFuture analysis
ModelCheckKernelState-logging inputs and effect modelsFuture model checking

These are ordinary objects chosen by the instantiation service. The language commitment is explicit object parameters, with a fixed lookup and invocation semantics across configurations. Abstract inputs still require an implemented abstract interpreter; changing a bundle alone does not supply one.

Structural Encapsulation and Governance Boundaries

Nesting grants access to enclosing scope. Two objects nested under the same capability-rich module do not become isolated merely because each stores a different service in one slot: both can still reach their common outer scope. Inheritance and mixin definition scopes are additional capability routes.

For independent authority boundaries, use separate top-level modules and pass restricted object graphs to each. For example, these are two separate module expressions instantiated by an external service:

class Avionics(flightBus) {
    flightComputer = flightBus;
}

class Entertainment(mediaStream) {
    mediaServer = mediaStream;
}

Neither module has an outer path to the instantiation service or to the other module. Isolation still depends on the supplied objects: a mediaStream that returns the flight bus would intentionally grant that access. Lexical nesting is useful where authority is meant to be shared; it is not a substitute for restricting the reachable capability graph.

The Alien/Expat Federation Protocol

The most operationally significant SoS feature in VarioHyve is the Alien/Expat boundary model — the formal protocol for interaction between VarioHyve and foreign runtimes.

VarioHyve federates with external systems without absorbing them. Legacy subsystems in C++, controllers in Simulink, business logic in Java, and formal models in TLA+ can all remain in their original form. What VarioHyve provides is a behavioral bridge with precisely defined semantics.

Aliens are references to foreign semantic values or entities. An object-oriented adapter may expose message forwarding, for example:

VarioHyve code              Alien proxy              Foreign runtime
─────────────               ──────────               ───────────────
aServer.start(port)  ──►  expatriate args  ──►   server.start(8080)
         result      ◄──  alienate result  ◄──   return value

An explicit Alien send crosses to its adapter: arguments are expatriated, the selected foreign operation runs, and its result is alienated. The foreign domain defines the operation. An opaque handle may support no direct sends; explicit capabilities can operate on it instead. Aliens do not acquire native classes, mixins, lexical outers or VarioHyve lookup. Native wrappers supply those abstractions explicitly.

Expats are the symmetric inverse — foreign proxies for VarioHyve objects:

Foreign runtime              Expat proxy              VarioHyve store
───────────────              ──────────               ───────────────
server.start(8080)  ──►  alienate args  ──►   vh_server.start(8080)
       result       ◄──  expatriate result  ◄──  return value

When Python or Java code calls a method on an Expat, the Expat alienates the foreign arguments into VarioHyve values, dispatches the message to the wrapped VarioHyve object, and expatriates the result back.

The protocol preserves compatible reference round trips: exporting an Alien to its originating domain recovers the foreign entity, and importing a runtime’s own Expat recovers the native value. Identity-bearing values preserve aliases; marshalled primitives instead follow their defined value conversions.

This matters for SoS because:

  • No forced monoculture. Legacy subsystems stay in their original language. VarioHyve provides the behavioral coordination layer, not a migration target.
  • Explicit interaction contracts. VarioHyve uses sends to request foreign operations; each adapter specifies how those requests map to its domain. The domains need not share an object model.
  • A principled seam for interface evolution. The Alien and Expat surfaces are explicit. When a foreign subsystem changes its API, the change is localized to the proxy layer and the constructor-argument wiring — not scattered across the model.
  • Instantiation supplies explicit wiring. The service passes Alien-backed or native objects as constructor arguments, independently or in optional bundles. Language-visible VM services use the same Alien/Expat boundary.

Behavioral Lingua Franca: One Interaction Model

Behavioral interactions in VarioHyve use (name, arity) message sends. Operators, slot access and function application use that common interaction form. Native receiver origins, lexical binding and construction still have specified language semantics; they are not foreign protocol requirements.

This is not minimalism for its own sake. In a federated system, adapters must bridge foreign systems to VarioHyve. A message-centric core means every adapter bridges exactly one concept:

incoming event    →  message send to a VarioHyve handler
RPC call          →  message send to an Alien proxy
simulation tick   →  message send to a simulation coordinator
hardware callback →  message send to a driver object

This common request form gives adapters a small language-facing transport surface. It does not remove the foreign domain’s own semantic obligations.

The native lookup algorithm terminates at the Alien boundary. The adapter may expose method forwarding, a function call, a memory capability or another domain operation. This common transport does not make every participant an object or make adapter semantics trivial. Signatures, failure, identity, lifetime and effects remain explicit adapter obligations.

Composable Structure for Heterogeneous Participants

Not every SoS participant is “an instance of a class.” VarioHyve provides a spectrum of participant styles with a unified interaction model:

Participant styleVarioHyve constructExample
Unique serviceSingleton object literalRadar = { ... }
Family of instancesClassclass Sensor(id) { ... }
Namespace/registrySingleton with nested structureProtocol = { v1 = ..., v2 = ... }
Configurable factoryClass with factory apply variantsMultiple construction paths
Delegation wrapperObject with apply methodCallable proxy
Dynamic coalitionObjects assembled at runtimeFirst-class object composition

A coordinator can use sensor.detect(target) with a native object or an Alien adapter when both support the required behavioral contract. Native receivers use fixed VarioHyve lookup; Alien receivers cross to their foreign domain. Common invocation syntax alone does not make arbitrary participants interchangeable: signatures, results, effects and failure behavior must agree.

The factory apply pattern is particularly relevant for federated deployment. A subsystem class can define multiple construction signatures for different operational contexts:

class Sensor(id, config) {
    factory apply(id, config) { new(id, config) }        // normal deployment
    factory apply(id) { new(id, SimConfig()) }            // simulation mode
    factory apply() { new(#mock, MockConfig()) }          // test/verification
}

This is a nested-class fragment: SimConfig and MockConfig must be available in its definition scope. The instantiating code selects a factory and supplies its arguments; there is no implicit kernel argument.

Mixins for Cross-Cutting Federation Concerns

SoS systems share cross-cutting concerns across subsystem boundaries: logging, tracing, fault tolerance, redundancy voting, time synchronization, cybersecurity guards, safety wrappers. These are not part of any one subsystem’s functional behavior — they are federation-level concerns that must be applied uniformly.

In the following nested-class fragment, the enclosing scope supplies the superclass and mixins. Mixins in VarioHyve are the mechanism for this. A mixin is a regular object whose class holds methods. It becomes a behavioral layer applied to a class without forcing that class into a particular inheritance hierarchy:

class Drone(id) <: Logging, SecureComm, FaultTolerant, TimeStamped < Vehicle {
    sId = id
    fly(trajectory) { ... }
}

Each mixin contributes behavior, member declarations and, if parameterized, initialization to the composed class. Physical slots may live on one instance; that representation must not erase declaration or application origins. The initial policy selects contributions in declared order with overriding. Deep family composition with state in members is an intended later increment, not an implemented bootstrap feature.

For SoS this matters because:

  • Concerns can be added or removed without changing the subsystem model. Adding a mixin to a class requires no change to its internal logic.
  • Mixin composition retains its structure. Reified definitions and their origins remain available internally. A public mirror API is deferred.
  • Order and overrides are explicit. Own contributions precede composed entries in declaration order and inherited behavior. Determinism does not remove state collisions or initialization-effect dependencies; those require explicit composition contracts and, later, state/adaptation operators.

Lexical Nesting Mirrors System Hierarchy

Lexical nesting can represent organizational hierarchy. Member classes bind to enclosing instances, while qualified outer ClassName selects a lexical receiver without exposing internal activations or a universal parent accessor:

class Mission(consoleService) {          // mission-level scope
    console = consoleService;
    class Fleet(id) {                    // fleet scope
        class Platform(pid) {            // platform scope
            class Subsystem(sid) {       // subsystem scope
                log(msg) {
                    outer Mission.console.print(msg)  // explicit lexical mission receiver
                }
            }
        }
    }
}

Each level of nesting shares authority with its enclosing scope through lexical lookup and qualified outer. Constructor parameters are initializer-only inputs: the mission explicitly stores its console service in a slot for member behavior. A member declaration cannot recover an unstored constructor argument. Ordinary lambdas and class expressions created in an initializer can deliberately capture its parameters, with names retained only for named class expressions. Nested subsystems can also receive capabilities through inheritance, mixins and their own constructor parameters. The top-level mission has only the empty top activation beneath it, with no enclosing application scope; it receives its console as an explicit argument.

This structural alignment between language semantics and governance structure means the model itself expresses the authority hierarchy — it is not an external documentation artifact.

Late Binding for Evolving Systems

All names in VarioHyve are late-bound. A bare name is an implicit message send resolved at runtime through the lexical and inheritance chains. No name is resolved at compile time to a specific object address.

In SoS, this matters because:

  • Supplier replacement does not break callers. A subsystem that calls kernel.radar.detect(target) does not bind to a specific Radar implementation. The instantiation service can supply a different bundle with the same behavioral interface without modifying the caller.
  • Interface versioning is handled by the message protocol. A new version of a subsystem that adds methods does not break existing callers — unused methods are simply not called. A removed method surfaces as doesNotUnderstand at the call site, which can be caught and handled.
  • Dynamic coalition formation is natural. Objects can be assembled and rewired at runtime. A coordination object can be handed a different set of participants without requiring structural changes to the coordination logic.

The apply protocol extends this: any object that implements apply is callable. A mock object, a proxy, a recorded trace, and a live hardware driver can all sit in the same slot and receive the same messages — the calling code has no way to distinguish them and no reason to care.

Execution and Verification from the Same Core

Many SoS efforts maintain separate artifacts for execution and verification: a simulation model, a formal model, a code implementation, a documentation model. These quickly diverge. VarioHyve unifies them by design.

The VarioHyve interpreter is an AAM-style CESK machine. The machine has four components (Control, Environment, Store, Kontinuation) and a single parameterization point: the Alloc function that determines how store addresses are allocated:

  • Concrete Alloc (fresh integer per allocation) → the v1 deterministic interpreter. Runs the model.
  • Abstract Alloc (k-CFA, bounded by call site and environment prefix) → a sound abstract interpreter. Explores all reachable abstract states. Computes program properties.

The step function — the semantic core — is the same in both cases. This is the key commitment: the verification artifact and the execution artifact share one semantic definition. There is no translation layer between them, no semantic gap to manage, no risk of the verification model drifting from the implementation.

For SoS this enables:

ActivityMechanism
SimulationConcrete CESK with SimKernel
Unit and integration testingConcrete CESK with TestKernel
Type inference / interval analysisAbstract CESK with abstract kernel values
State space explorationAbstract CESK with nondeterministic abstract transitions
Model checking foundationsAbstract CESK with state-logging ModelCheckKernel
Trace replay and runtime monitoringConcrete CESK with a trace-recording store

This is what SoS engineering desperately lacks: behavioral models that are simultaneously executable and formally analyzable, with no semantic mismatch between the two.

Descriptors: Multi-Stakeholder Semantic Layers

A federated system has multiple stakeholders, each with different concerns about the same behavioral model: safety engineers, cybersecurity analysts, simulation teams, certification bodies, code generators. These stakeholders need to attach their own metadata to model elements without altering the execution semantics.

Descriptors are VarioHyve’s mechanism for this. They are ordinary expressions that annotate syntactic elements — slots, methods, classes, lambdas, parameters — and are completely ignored by the core interpreter. A program with all descriptors stripped executes identically to the annotated version.

class Sensor(id, config) {
    reading = 0 : immutable : serializedAs("json") : safetyLevel(4)
    calibrate(ref) {
        ...
    } : cached : realTime : certified(DO178C)
} : module : traceable(reqId= "SYS-042")

Since descriptors are expressions, they can be message sends that return descriptor objects:

{
    altitude = 0 : constrained(0, 50000) : units("feet") : safetyLevel(4)
    velocity = 0 : constrained(0, 3000)  : units("knots")
} : module : certifiedBy("avionics-safety-team")

The same model element carries annotations for:

  • Safety engineers: safetyLevel(4), certified(DO178C), constrained(0, 50000)
  • Simulation teams: realTime, cached
  • Serialization/integration: serializedAs("json"), units("feet")
  • Traceability/audit: traceable(reqId= "SYS-042"), certifiedBy(...)
  • Documentation tooling: anything else

Each tool layer reads the descriptors it understands and ignores the rest. The core interpreter runs through all of them unchanged. This is federated modeling in its direct form: one behavioral model, multiple stakeholder interpretations, cleanly separated.

In Summary

VarioHyve is uniquely equipped for heterogeneous SoS design because its architecture directly encodes the structural realities of SoS:

SoS requirementVarioHyve mechanism
Implementation diversityAlien/Expat protocol — foreign runtimes stay foreign
Governance partitioningNo globals; restricted constructor arguments and reachable object graphs
Uniform interaction across boundariesEverything is a message send — one adapter model
Participant diversityObjects, classes, singletons, callables — same dispatch
Cross-cutting concernsMixins — behavioral layers without forced hierarchy
Organizational hierarchyMember-class nesting and qualified lexical receivers
Evolving interfacesLate binding — names resolve at runtime
Executable + analyzableAAM-parameterized CESK — same core, swap Alloc
Multi-stakeholder viewsDescriptors — optional, execution-transparent annotations
Context-specific deploymentConstructor arguments, optionally bundled — same model, different contexts

Most languages tolerate heterogeneity from the outside. VarioHyve is built for it from the inside.
