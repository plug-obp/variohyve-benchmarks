VarioHyve Language Specification

Behavioral Federation

VarioHyve investigates how programs can coordinate systems that keep their own meaning, execution mechanisms and authority. A model repository, a simulator and a running controller can cooperate without becoming objects of one universal model or processes of one execution engine. The difficult part is making the agreements between them explicit enough to understand, change and examine.

We call this behavioral federation. The experiment combines an object language, a native/foreign boundary and an explicit execution model. Its working hypothesis is that a small, coherent set of mechanisms can make coordination behavior easier to reuse and its assumptions easier to inspect. An executable bootstrap now allows that hypothesis to be investigated through programs and tests. Whether the combination improves real engineering workflows remains an empirical question.

Cooperation Without Complete Control

A system-of-systems brings together participants that retain substantial operational and managerial independence. Their owners, release cycles and objectives need not coincide. Engineering environments encounter a related problem when requirements, designs, simulations and operational records live in different tools. The engineered product need not itself be a system-of-systems for its engineering models to require federation.

Consider a pumping station. A requirements model states a minimum flow, a hydraulic simulator predicts performance, and maintenance records describe the installed equipment. Each may refer to the same pump while expressing different facts about it. Assessing a proposed replacement requires a correspondence between those references, compatible units, an agreed revision of the design and a policy for interpreting the analysis. Authorizing the replacement requires additional authority. A successful assessment alone does not supply it.

API connectivity solves only part of this problem. A simulator may finish after the relevant design has changed. A service may fail after accepting a request, leaving its effects uncertain. A callback may arrive while the coordinator is waiting for a result. The engineer needs to know which observations support a decision, which assumptions remain in force and what a failed interaction means. Replacing the simulator with a recorded trace should expose the changed assumptions while preserving the intended coordination protocol.

These needs become language and tooling questions when the workflow must be maintained across many projects. Builders of modeling environments need reusable behavior over heterogeneous models, traceable evidence and controlled access to tools. Moving every model into a new metamodel can be expensive or inappropriate; reimplementing every participant’s behavior can lose exactly the semantics that made it useful. Existing federation and model-management tools already address substantial parts of this problem. VarioHyve asks what a compact coordination language can contribute alongside them, and what it costs compared with their own workflows or direct host-language code.

Agreements Expressed Through Objects

The approach starts with supplied capabilities: objects whose behavior grants access to particular services or resources. A coordinator receives the capabilities it needs and exchanges objects by sending messages. Its inputs can represent a narrow model query, an analysis operation or permission to record evidence. The supplying system determines the available authority; the coordinator’s source makes its use visible.

This is also a commitment to semantic sovereignty. Foreign participants retain their own execution and interpretation of operations. The boundary states how messages, values, identity, failures and callbacks cross between them. An operation may return an ordinary value or promise an explicit outcome protocol, just as a native method may. A shared message syntax does not establish agreement about units, revisions or successful completion: those remain part of the supplied operation’s contract.

Here, “contract” means an agreement about behavior and authority, not an implemented contract language or automatic proof system. The boundary makes such agreements a subject of design. It also makes their limits visible. For example, foreign code running in the same host process can terminate that process; a capability interface alone does not provide process containment.

A Language for Explicit Dependencies

The following module illustrates the shape of a coordinator:

class Assessment(modelSource, checker, evidenceSink) {
    models = modelSource;
    analysis = checker;
    evidence = evidenceSink;

    assess(item) {
        var snapshot = models.snapshot(item);
        evidence.record(snapshot, analysis.check(snapshot))
    }
}

The host supplies three existing objects when it constructs Assessment; it later requests an assessment by sending assess. The module retains its inputs in slots because constructor parameters belong to initialization, rather than becoming instance-method bindings. Nothing in this code requires the three services to be implemented in VarioHyve. Their selectors are application agreements, and the example deliberately leaves their failure and evidence policies to those agreements.

A normal module begins over an empty top activation. It receives external capabilities through explicit constructor inputs and, subsequently, message arguments and the behavior of objects already available to it. There is no ambient application namespace. Supplied objects keep their own authority and captured scopes, so a short parameter list is not by itself an isolation proof. The program-structure chapter defines this entry contract precisely.

Within the language, objects and message sends also organize access and reuse. Slots are accessed through messages; lexical scopes are activation objects and ordinary objects. Classes are first-class values. Composition uses reified contributions and application occurrences, retaining the declaration origins that determine scope and invocation. A reusable analysis stage can therefore keep access to its defining provider even when applied in a receiving module with similarly named bindings. The rules aim to make that behavior predictable without merging independently defined models into a deep class family.

For language design, the question is whether these mechanisms work together without hidden exceptions at each point of reuse. Definition scope, receiver identity and contribution selection must remain intelligible when code moves between modules or across a foreign boundary. The specification fixes these rules independently of the Java representation, giving alternative implementations a contract to preserve. That precision also exposes costs in notation, implementation and debugging that the experiments must assess.

Foreign values appear inside the language as Aliens; native behavior is exported as Expats. Sending a message to an Alien uses the ordinary source syntax. The adapter mediates the operation, and foreign code may call an Expat while the native caller waits. Language-visible VM services use this same boundary, with separately granted privileged capabilities. Explicit mirrors can offer information beyond ordinary behavior. The boundary chapter defines these interactions, including identity, failure and the default prohibition on non-local returns crossing a foreign call.

Making Execution Available for Inquiry

Coordination becomes easier to investigate when execution itself has a precise description. VarioHyve’s machine exposes configurations and transitions for evaluation, invocation, storage and control. This supports a correspondence between language rules, executable behavior and observations made by tools. It does not by itself establish that correspondence as a proved theorem.

The current sequential execution agreement uses a conceptual control token for ordinary native execution. A native-to-foreign call transfers control to the foreign side; an admitted callback can return it to native execution before the original call completes. Multiple callback workers must negotiate admission, and the current implementation serializes their native execution. The token need not be a runtime object. Its purpose is to describe an agreement that an implementation must realize.

That agreement leaves room for explicitly confined extensions. A collector may perform concurrent maintenance if it preserves the required abstract behavior. A monitor may have a separately specified intervention capability. A future parallel machine may execute proven-independent transitions under an appropriate execution agreement. These possibilities have distinct obligations; granting one does not silently grant unrestricted execution authority. The formal appendix states the model and its limits, while Future Directions separates accepted extension principles from mechanisms still to be developed.

This opens two different lines of inquiry for formal methods. A coordinator can call an external checker as a supplied capability. Separately, an analyzer can be derived for the coordinator’s own execution semantics. The first requires an agreement about the checker’s inputs, results and assumptions; the second needs an abstraction and soundness argument, including a treatment of foreign effects. Neither alone verifies a complete federation or its physical environment. Descriptors can carry tooling information, but attaching information does not establish its truth. Keeping these distinctions explicit makes proposed claims testable and clarifies the evidence still required.

What the Bootstrap Establishes

The present result is an executable language bootstrap centered on VisitorSemanticsVM. It includes parsing and lowering, explicit module entry, object and class construction, reified composition, lexical lookup, closures and return-home checks, a native heap collector, and a synchronous Java Alien/Expat boundary. Semantic regressions exercise the interactions between these mechanisms. The implementation chapters identify concrete policies and remaining limitations; executable tests are evidence about those policies, not a substitute for their specification.

The composition case study provides a small but concrete federation slice. Native source coordinates Java fixture services for model observations, validation, capacity checking and evidence. Reusable stages preserve their defining checker capabilities despite competing bindings in the receiving module. Its acceptance cases cover successful and rejected assessments, early failure and a selected foreign operation failing without being replayed. This tests capability flow and composition using controlled participants.

The slice does not yet integrate an industrial model repository or simulator, and it establishes no comparative productivity or performance advantage. The case-study catalog develops the next experiments around explicit baselines, measurable outcomes and failure conditions. Useful findings include cases where an existing tool or direct adapter is simpler. Current measurement infrastructure also supports language implementation experiments, with workload and measurement boundaries documented separately.

Positioning and Reading the Experiment

VarioHyve draws on object languages, capability security, behavioral reflection and explicit operational semantics. Openflexo, Epsilon and CorrLang provide important comparisons for model federation and coordination; Smalltalk and Newspeak inform the language lineage. Work on monitoring and analysis supplies ways to formulate the questions raised by observable execution. The Related Works part explains the relevant connections and differences without treating them as delivered integrations or inherited proofs.

The rest of the book moves from agreement to realization. Specification defines language behavior, including the foreign boundary. Implementation describes the Java bootstrap and its tooling. Future records extension principles, proposals and unresolved work. Related Works situates the experiment, and the Appendix gives the formal rules. This opening Motivation supplies the questions behind those parts: can explicit capabilities and preserved semantic boundaries make coordination easier to understand, and can explicit execution make its behavior easier to investigate?
