VarioHyve Language Specification

Objects and Classes

This chapter defines class and object literals, member declarations, composition, and factories. Name Resolution defines lexical receivers; Message Sends defines invocation; Literals defines initializer completion and returns. Backend records belong to Runtime Object Representation.

Operational definition: SOS class and construction rules.

Top and the Class Algebra

Top is the empty constructor of the mixin–class algebra. At the level of instance-side composition, the inductive structure is:

ClassShape ::= Top | Apply(Mixin, ClassShape)
Object       = Apply(ObjectMixin, Top)

Like zero in an inductive definition of natural numbers, Top supplies the base case. Every nonempty class shape is a mixin applied to another shape, so even Object follows the same construction rule. Apply here is mathematical composition, not the source apply selector or a factory invocation.

Top contributes no methods, slots, member declarations, definition scope, capabilities or initialization. Lookup ends there with a miss and its layout is empty. Only Object has Top as its direct superclass; other native class chains reach it through Object. The owned Object mixin supplies the root protocol below. Thus adding the empty base does not remove that protocol or change the capabilities available through it.

The algebra describes composition structure, not class identity. A realized class retains its owned contribution, ordered direct applications, superclass, routes and metaclass. Expanding its shape neither manufactures intermediate class objects nor erases contribution scopes or occurrence identities. The formal rules give this projection precisely.

Top is a distinguished semantic base, not an instantiable class or a language-visible value in the current contract. It has no metaclass, factory, owned mixin to import, or public mirror reference. The class/metaclass rules below apply to realized classes. No built-in Top binding or new reserved name is introduced, and omitted superclass clauses still select Object. The empty top activation for module entry is a separate execution frame. Aliens acquire no native hierarchy through this definition.

The VM may represent the terminal case without allocating an object: the implementation refinement states the mapping and the conditions for reconsidering runtime reification.

The class Keyword

class distinguishes an instantiable class from an immediately evaluated object:

FormResult
class { body } or class() { body }Anonymous zero-parameter class
class(params) { body }Anonymous class with constructor parameters
class Name { body } or class Name() { body }Named zero-parameter class
class Name(params) { body }Named class with constructor parameters
{ body }One object, allocated and initialized on each evaluation
<: Mixins(args) < Base(args) { body }One object with the selected mixins and superclass

Class Literal Syntax

namedClassLiteral
    : CLASS IDENT arguments mixinApplications superclassApplication
      LB classBodyElement* initializerBody? RB (COLON descriptorList)* ;
anonymousClassLiteral
    : CLASS arguments mixinApplications superclassApplication
      LB classBodyElement* initializerBody? RB (COLON descriptorList)* ;
classLiteral         : namedClassLiteral | anonymousClassLiteral ;
arguments            : (LP formalList? RP)? ;
mixinApplications    : (WITH expressionList)? ;
superclassApplication: (EXTENDS expression)? ;
classBodyElement     : namedClassLiteral SEMICOLON? | methodDecl SEMICOLON?
                     | slotDecl SEMICOLON | factoryDecl SEMICOLON? ;
factoryDecl          : FACTORY methodDecl ;
initializerBody      : PIPE statementList? ;

WITH is <: or with; EXTENDS is < or extends. Empty parameter parentheses are optional. Class bodies contain slots, methods, member classes and factories, followed by an optional final | statement section. Slot declarations require semicolons; methods, members and factories permit them. Descriptor chains retain their annotation syntax.

Object Literals

objectLiteral    : mixinApplications superclassApplication
                   LB objectBodyElement* initializerBody? RB (COLON descriptorList)* ;
objectBodyElement: namedClassLiteral SEMICOLON? | methodDecl SEMICOLON?
                | slotDecl SEMICOLON ;

An object literal has no constructor parameter list or factories. Its optional mixin and superclass clauses have the same syntax, order and meaning as class clauses: mixins precede the superclass; <:/with and </extends are synonyms. Omitting the superclass selects structural root Object, without name lookup. Slot declarations still require their terminating semicolon.

<: M1(p1), M2(p2) < S(p3) { x = 5; }
< S(p) { x = 5; }
with M(p) { x = 5; }

Each evaluation realizes a fresh anonymous zero-parameter class, then immediately sends its generated primary new/0 using ordinary exact message dispatch. Thus <: M(p) < S(q) { body } is equivalent to (class <: M(p) < S(q) { body }).new, with a factory-free body. Successful evaluation returns the initialized object. Repeated evaluation creates distinct class, metaclass and instance identities; it does not cache a singleton. Contributor factories and custom apply methods are not called or imported.

All constructor-clause rules apply. Targets resolve left-to-right for direct mixins, then the superclass, in the literal’s evaluation scope before allocation. Routed arguments run later in its own initializer activation, immediately before their contribution is initialized. In particular, self in a target computation denotes the enclosing receiver, while self in a routed argument denotes the new object. Ordinary initializer lookup also applies: an own slot can shadow an enclosing name and is still uninitialized during routing. For example, < S(x) { x = 5; } cannot use its own pending x as an argument; use a distinct captured binding or a qualified outer receiver when that is intended.

The anonymous class captures the literal’s evaluation scope, including deliberate creation inside another initializer. Contributors retain their own definition scopes and initializer-only constructor parameters; parameters are not added to instance-method bindings. Each contribution keeps its normal initialization order, occurrence, storage rules and private return home. Anonymous objects introduce no new outer qualifier.

An object literal remains an expression, not a valid normal module entry. Nested literals may use explicitly supplied module inputs, under the existing module restrictions.

Zero-Parameter Classes vs Singletons

For class Config { debug = false; }, Config() invokes its apply/0 factory; Config.new and Config.new() each perform primary construction once. For config = { debug = false; };, the slot already holds the initialized object. See zero-arity invocation.

Root Object Protocol

In the current runtime seed, native objects, including lambdas, inherit these ordinary methods from root Object:

equals(other) { _vm.same(self, other) }
hash { _vm.identityHash(self) }
toString { "an Object" }

These are normative defaults of this seed. Another seed may choose different root methods without changing lookup, invocation or boundary laws. Replacing an application kernel does not replace the structural root; selecting another seed is not a current runtime API.

Root Object does not supply same or identityHash. Reliable identity and classification observations belong to an explicitly supplied IdentityMirror capability. The mirror observes subjects without invoking their methods. Defining these selector names on an application object cannot intercept mirror observations or the root defaults’ direct use of _vm; no selector is thereby reserved on Aliens.

equals defaults to native identity equality, including identity recovered from an owned Expat. Canonical null and Booleans participate with their native identities. The default hash returns an integer stable for the identity’s lifetime; equal identities have equal hashes, but collisions are permitted. Hashes are neither addresses nor persistent identifiers across runtime sessions.

equals, hash and toString remain overridable. Equality overrides should define a reflexive, symmetric, transitive relation with compatible hashes. The defaults provide identity-derived results without a separately supplied mirror; the mirror grants observation independent of subject behavior.

The default toString returns exactly "an Object". It reveals neither a class name nor an instance or class identity hash. Named and anonymous instances, class objects, metaclasses and lambdas retain this generic answer unless they override it. Canonical values keep their explicit null, true and false overrides. Diagnostic detail is therefore chosen by the object’s own protocol.

_vm is a narrow seed capability in Object’s detached definition scope, not an inherited slot, ambient module binding or accessor for IdentityMirror. Its operations cross the normal Alien/Expat boundary and expose no backend representation. Aliens retain their own protocols and do not acquire these methods by inheritance. Scalar Object behavior and identity remain subject to the scalar design decision.

Capabilities and Definition Scope

The capability sources do not change definition scope: calling a class does not capture its caller’s scope. Named and anonymous classes follow the same rule. Examples with custom contributors or enclosing bindings assume an appropriate enclosing context; isolated modules and tooling evaluation have distinct entry contracts.

Constructor parameters are immutable bindings available only during initialization. Methods cannot resolve their own constructor arguments, even when called during initialization. Store persistent dependencies in slots. Lambdas and class expressions deliberately evaluated in an initializer may capture its parameters. Each contribution receives its own argument bindings; composition does not replace its captured definition dependencies.

Member Declarations and Class Expressions

A named class in body-declaration position declares a member class:

class Container(input) {
    value = input;
    class Member { read { value } }
    Captured = class { read { input } };
    NamedCapture = class Snapshot { read { input } };
}

Member binds to the enclosing receiver and its declaration/application origin. Its zero-argument accessor lazily realizes and caches one class per enclosing receiver and declaration occurrence. Repeated access returns that identity; different enclosing receivers or application occurrences obtain distinct classes. The member binds to the actual enclosing receiver while retaining the selected occurrence’s captured lexical ancestry at every depth, including when selected through super. Its factories retain that same definition parent. Ordinary messages to the enclosing receiver still honor overrides; retaining ancestry does not restrict virtual sibling selection to the originating contribution. See lexical receiver selection.

The member can use stored value, but cannot acquire Container’s constructor binding input. Members are available regardless of their position among slot initializers.

Captured and NamedCapture are slots initialized by class expressions. Both capture the evaluation scope, including input. An expression’s optional name is declaration metadata, not a binding introduced in the surrounding body. Anonymous forms occur only as expressions; named forms can be expressions or member declarations. Lowering must preserve this distinction.

Member and slot names share a namespace; duplicates in one body are errors. A member also conflicts with a zero-argument method of the same name and has no setter. A stored class is callable through its current value; a member advertises the selected declaration’s constructor and owned factory apply arities before realization. Wrong-arity invocation evaluates no contributor targets. Selected realization failures, including cycles or abandonment during non-local return, are cached without replay. See member invocation for selection and overriding.

Initializer Bodies

The optional final | section executes after the contribution’s ordered slots. Constructor parameters remain available. No member, method, slot or factory declarations follow the delimiter; ordinary statements, including local var and class expressions, may occur there. Its ordinary result or permitted early-return value is ignored. The complete phase, home-lifetime and failure rules are in Initializer completion.

Inheritance

< Base(args) selects a native class and inherits its complete instance-side chain: owned contribution, applied mixins and ancestors. Omitting the clause uses structural root Object, without looking up the name Object. An instance or Alien is not a class target; no implicit instance.class conversion occurs. Native super cannot be a contributor target.

Construction runs the superclass’s complete initializer schedule on the newly allocated receiver. Inheritance imports no factories; factories belong to the declaring class.

Mixins

<: A(args), B(args) applies the owned reified contribution of each selected native class: directly declared methods, slots, member classes, constructor formals and own initializer. It imports no source superclass, applied mixins, factories or argument routes. The definition scope remains captured. Resolving the source class itself still realizes its targets normally; applying its owned contribution does not evaluate those original constructor argument routes.

For example, if A <: M1, M2 < S1, B <: M3, M4 < S2, and C <: A < B, the contribution order is:

own(C), own(A), own(B), own(M3), own(M4), then the complete S2 chain

own(X) means X’s owned contribution. No intermediate classes are introduced. Repeated applications share the reified definition but have distinct application occurrences and initializer invocations. A contributed method’s super resumes from its application occurrence; see Name Resolution. Public mixin extraction and reflection are not part of the current language.

Constructor Clauses

The terminal application in a superclass or mixin clause has construction semantics. It selects a contributor during class realization and retains the argument expressions for each later construction; it does not call a factory. Bare targets route zero arguments, and parentheses around the whole clause do not change its meaning.

Computed Contributor Targets

For < registry.choose(kind).Base(x), realization evaluates registry.choose(kind) and reads Base; construction later evaluates x. Receiver subexpressions perform ordinary computations. Direct mixin targets run left-to-right, then the superclass target. Their choices are fixed for the realized class. This applies to class expressions and cached member classes.

Construction Order

For class C(x) <: A(a), B(b) < S(s) { ... }, successful primary construction:

  1. Allocates one receiver with fresh uninitialized storage for its complete layout.
  2. Evaluates s and runs S’s complete initialization schedule on that receiver.
  3. Evaluates b and runs B’s owned initializer, then does the same for a and A.
  4. Runs C’s own ordered slots and final body, then returns the allocated receiver.

Each argument list is evaluated once, left-to-right, immediately before its private target invocation. Argument expressions run in the declaring contribution’s initializer activation, with its constructor parameters bound. Superclass and applied-mixin calls receive their own bindings and fresh homes. The declaring routes and owned body share one logical home, established before routing begins. Routing precedes slot completion, so returning to that home from a route cannot finish construction early. Each contribution completes its slots and final body before the next contribution runs.

These calls are private identity-bound routines, never selectors named initialize or public operations on arbitrary receivers. Initializer writes bypass overridable setters. No component instances are allocated, no effects are replayed or rolled back, and escaped partial receivers are not retracted. Return and failure handling follows Initializer completion.

Ordered Overrides and Shared State

Own declarations have precedence, followed by direct mixins left-to-right, then the superclass recursively. At each contribution, selector/accessor choice follows Message Sends. A member override selects the whole declaration and its origin; it does not merge nested families automatically. Duplicate slots, members or exact method selectors within one body remain errors; an explicit method may override a generated slot accessor.

Every slot retains its logical identity (applying class, occurrence, local slot). Same-named contributions share storage. Initialization runs in the reverse contribution order above, so later writes replace earlier values. Every occurrence still initializes, including repeated applications. Surviving methods may therefore observe shared state; this policy does not promise independent stateful mixins. Getter/setter eligibility and mutability belong to the selected declaration, even when storage is shared. Renaming, explicit state mapping and deep family composition require future rules.

Factories

A factory method is sent to the class object; an ordinary method is sent to its instances. Both use ordinary method invocation and lexical scope.

The Primary Factory (new)

Every source class and root Object has a generated, non-overridable primary new/N, where N is its constructor arity. Successful invocation allocates a fresh receiver, executes the complete construction schedule and returns that receiver. Its selector uses ordinary lookup; only its generated body contains private construction operations. Object literals automatically send this primary new/0 to their newly realized anonymous class.

factory new is forbidden. An ordinary instance method named new is allowed. This restriction preserves a primary entry that guarantees fresh allocation and the complete initialization schedule, while apply and named factories retain control over their results. It does not make an arbitrary new send an allocation primitive. Inheriting Object does not add new/0 to a class with parameters, and neither inheritance nor mixin application imports contributor factories.

The Callable Protocol (apply)

At constructor arity N, the default apply/N makes an exact self.new/N send. An owned factory apply at N replaces that default; factories at other arities coexist with it. A custom factory controls its result and causes no automatic allocation or initialization. It may call new, return a cached instance, or return another value.

class Point(xInput, yInput) {
    x = xInput;
    y = yInput;
    factory apply() { new(0, 0) }
    factory copy(point) { new(point.x, point.y) }
}

Point(2, 3) uses default apply/2; Point() uses the custom apply/0; Point.new(2, 3) performs primary construction directly. General callable selection belongs to Message Sends.

Named Factory Methods (factory)

Named factories such as Point.copy(p) are ordinary class-side methods with full result control. In a factory, self is the class object; lexical sends and qualified outer use the factory’s declaration origin and the class’s definition scope. A factory on a member class can therefore access its bound enclosing receiver. Invoking it does not capture the caller or instantiation service.

Bootstrap Metaclasses

Each source class C has a distinct metaclass C class, containing only C’s owned factories, with direct superclass Class and structural class Metaclass. Factory super continues at Class, independently of C’s instance superclass. The root relationships are:

IdentityStructural classDirect superclass
ObjectObject classTop
ClassClass classObject
MetaclassMetaclass classClass
Each of the three root metaclassesMetaclassClass

Thus Metaclass and Metaclass class form a shared two-object class-of cycle. Top terminates superclass chains without participating in this class-of graph. Object retains its empty initializer and new/0/default apply/0. Class, Metaclass and metaclass objects have no public construction factories; the common instance protocol of Class is initially empty. Structural links create no public class or outer selector, ambient binding or reflection API.
