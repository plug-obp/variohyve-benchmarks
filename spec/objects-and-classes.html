VarioHyve Language Specification

Objects and Classes

This section covers the semantics of object and class literals: nesting, inheritance, mixins, and naming conventions. For the syntax of all literal forms (including number, string, and lambda), see Literals.

Capabilities and Definition Scope

Named and anonymous class literals receive capabilities through superclass inheritance, mixin composition, their enclosing lexical scope, and constructor parameters. These routes preserve the distinction between lexical and inherited lookup; they do not give a class access to its caller’s scope.

A normal top-level class is a module whose lexical base is an empty top activation. It has no enclosing application scope, only root Object inheritance, and no mixin composition. Its external capabilities arrive solely as existing objects passed to its constructor by an instantiation service. Neither a single argument nor the name kernel is required. Constructor parameters can supply class/mixin objects for nested class definitions, but cannot supply the top-level class’s own superclass or mixin clauses. See Program Structure.

Tools may explicitly provide a richer context for development-time evaluation. Classes created in that context retain its lexical bindings, so they are not isolated module definitions over the empty root. They use the same class and lookup semantics; see Evaluation Contexts.

Examples below that refer to enclosing bindings, custom superclasses or mixins are fragments within an appropriate enclosing scope, not standalone top-level modules. A zero-parameter nested class can still receive capabilities through the other three routes; a zero-parameter module over the empty top activation has no external inputs.

The class Keyword

The class keyword is required for all class definitions. It is the sole discriminator between classes and singleton objects:

  • class { ... } or class(params) { ... } — a class (instantiable via .new or the apply protocol).
  • { ... } — a singleton object (evaluated immediately, one instance).

Zero-Parameter Classes vs Singletons

class Config {
    debug = false
    verbose = true
}

Config is a class — Config() selects its advertised apply/0, realizes the class if needed, and invokes that factory. Config.new and Config.new() both invoke primary construction once. See zero-arity invocation. By contrast:

config = {
    debug = false
    verbose = true
}

config is a slot holding a singleton object — there is only one instance, created at definition time.

Member Declarations and Class Expressions

A named class in body-declaration position declares a member class:

class Container(input) {
    value = input;
    class Member { read { value } }
    Captured = class { read { input } };
    NamedCapture = class Snapshot { read { input } };
}

Member binds to the enclosing Container instance and its declaration origin. It can access that instance’s stored value, but cannot implicitly use the instance’s constructor parameter input. Its zero-arity accessor caches the bound class per enclosing receiver and declaration occurrence. Repeated access returns the same class, and different enclosing instances obtain distinct class objects. Member declarations are available regardless of their textual position among ordinary slot initializers.

Captured and NamedCapture are ordinary slots initialized by class expressions. Both expressions capture the initializer scope, including input. Naming an expression does not change this rule or declare a member in the surrounding body. Class expressions may occur wherever expressions are allowed.

These forms share callable class behavior, but are not semantically equivalent. Lowering must preserve member declarations instead of turning them into slot assignments. Member names and slot names share the same namespace; a duplicate in the same body is an error. A member accessor has no setter. An ordinary mutable slot holding a class can be changed through its setter. Both support invocation at their available apply/N arities. A stored class is checked through its callable capability; a member declaration advertises its constructor arity and owned factory apply signatures before realization. A wrong-arity member candidate is skipped without executing its definition clauses.

Methods do not implicitly retain their own class’s constructor parameters. Initialization must bind the values needed by later methods into slots. Ordinary lambdas and named/anonymous class expressions evaluated during initialization may deliberately retain their lexical captures. See Name Resolution.

Initializer Bodies

An optional final | section runs statements after the contribution’s ordered slots. Constructor parameters remain available there. For example:

class Config(input) {
    saved = input;
    read { saved }
    |
    ^ input
}

Construction returns the allocated Config, ignoring the initializer’s return value. Each invocation has a fresh return home. Returns to it during slot initialization are errors; post-slot returns complete only that contribution, without skipping others. Objects use the same final-section syntax and home lifecycle. Methods and deliberately captured data keep the scope distinctions above. See Initializer completion.

Nesting

Classes and objects nest lexically. Inner objects access outer slots via the lexical chain:

{
    config = { debug = false }
    class Server(port) {
        start() {
            // 'config' resolves via lexical chain to the enclosing object's config
            config.debug
        }
    }
}

Inheritance

Classes can extend a superclass:

class Animal() {
    speak() { "..." }
}
class Dog() < Animal {
    speak() { "woof" }
}

The < (or extends) clause specifies a native class as superclass. It inherits that class’s complete chain: its owned contribution, applied mixins and ancestors. Lookup reaches that chain after the receiving class’s own and applied contributions. Construction runs the superclass’s complete initialization schedule on the same allocated receiver. This is instance-side inheritance: it does not import the superclass’s factories. Each class’s metaclass contains only its own class-side contribution and directly extends common Class; see Bootstrap Metaclasses.

Note that class Animal() uses the class keyword, making it a class. Writing Animal = { speak() { "..." } } would create a singleton object instance — not a class — and < Animal would pass that instance where a class is expected. Always use the class keyword when defining types intended for inheritance.

The runtime does not auto-dereference singletons. Given a singleton instance, the runtime will not silently follow instance.class to obtain its anonymous class. This is a deliberate design choice:

  • Ambiguity: both classes and instances are objects. The runtime cannot reliably distinguish “you passed a class” from “you passed an instance whose anonymous class you intended.” Auto-deref would guess wrong in the common case of a slot holding a class reference.
  • Mixin composability: super dispatch depends on a well-defined class chain. Silently inheriting from an anonymous class that was never designed for subclassing produces fragile, hard-to-debug lookup chains.
  • Static analysis: a clear “this must be a class” constraint at < sites is easy to verify abstractly. Auto-deref adds a branching point that complicates hierarchy tracing.

Mixins

The <: (or with) clause applies mixins:

class Serializable() {
    serialize() { ... }
}
class Loggable() {
    log() { ... }
}
class Dog() <: Serializable, Loggable < Animal {
    speak() { "woof" }
}

A <: A(args) application selects only the owned reified mixin of A: its directly declared methods, slots, member classes and own initializer. It imports neither A’s applied mixins nor its superclass or factory methods. The routed arguments bind A’s formals for this invocation; A’s original superclass/mixin argument routes are not evaluated. Its definition scope remains captured normally. This holds even when A itself is inherited or composed.

Thus class A <: M1, M2 < S1, class B <: M3, M4 < S2 and class C <: A < B give the lookup order M(C), M(A), M(B), M(M3), M(M4), then the full S2 chain. Here M(X) means X’s owned mixin. Initialization runs in reverse contribution order, with a fresh home for each invocation. See Mixin Application for scope, occurrence identity and state rules.

Computed Contributor Targets

Superclass and mixin receiver expressions may perform ordinary computations to select their contributor classes. For example, < registry.choose(kind).Base(x) evaluates registry.choose(kind) and reads its Base class during class realization. Only the terminal .Base(x) application has construction semantics: x is routed when constructing an instance, rather than invoking a factory at class realization. Parentheses around the whole clause do not change that rule.

This applies to member classes as well as class expressions. Direct mixin targets run left-to-right, followed by the superclass target. A member accessor realizes and caches its class for the enclosing receiver and declaration occurrence; subsequent constructions reuse those contributor choices. Invocation first checks member factory signatures, so rejecting a wrong-arity candidate evaluates none of its target computations. A selected realization failure is propagated and cached. See constructor-clause semantics and member-class invocation.

Descriptors

Object and class literals can carry optional descriptor chains for use by future tooling, compiler, or runtime extension layers. See Descriptors for details. Descriptors have no effect on raw execution.
