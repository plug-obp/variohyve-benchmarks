Objects and Classes

This chapter defines class and object literals, member declarations, composition, and factories. Name Resolution defines lexical receivers; Message Sends defines invocation; Literals defines initializer completion and returns. Backend records belong to Runtime Object Representation.

Operational definition: SOS class and construction rules.

Top and the Class Algebra

Top is the empty constructor of the mixin–class algebra. At the level of instance-side composition, the inductive structure is:

ClassShape ::= Top | Apply(Mixin, ClassShape)
Object       = Apply(ObjectMixin, Apply(M1, ... Apply(Mn, Top)))

Like zero in an inductive definition of natural numbers, Top supplies the base case. Every nonempty class shape is a mixin applied to another shape, so even Object follows the same construction rule. Apply here is mathematical composition, not the source apply selector or a factory invocation.

Top contributes no methods, slots, member declarations, definition scope, capabilities or initialization. Lookup ends there with a miss and its layout is empty. Only Object has Top as its direct superclass; other native class chains reach it through Object. The fixed Object contribution is empty and stateless, has no direct applications and captures no library capability. Its shape is Apply(ObjectMixin, Top). The structural root cannot be replaced. Optional library base classes use ordinary subclassing and explicit inputs.

The algebra describes composition structure, not class identity. A realized class retains its owned contribution, ordered direct applications, superclass, routes and metaclass. Expanding its shape neither manufactures intermediate class objects nor erases contribution scopes or occurrence identities. The formal rules give this projection precisely.

Top is a distinguished semantic base, not an instantiable class or a language-visible value in the current contract. It has no metaclass, factory, owned mixin to import, or public mirror reference. The class/metaclass rules below apply to realized classes. No built-in Top binding or new reserved name is introduced, and omitted superclass clauses still select Object. The empty top activation for module entry is a separate execution frame. Aliens acquire no native hierarchy through this definition.

The VM may represent the terminal case without allocating an object: the implementation refinement states the mapping and the conditions for reconsidering runtime reification.

Realized Hierarchy Invariant

Every published native class or metaclass has one unique identity and one fixed superclass edge. Its superclass is either an already realized class identity or, for Object alone, Top. Superclass references are closed within the realized class store. The superclass graph is well-founded: a finite rank can be assigned to every realized class, strictly decreasing at each superclass edge. Thus no superclass chain repeats a class identity, and every chain terminates at Object and then Top. The graph of class-of links is separate; its specified metaclass cycle does not violate this invariant.

Structural startup establishes these conditions. Ordinary class realization adds fresh class/metaclass identities with edges to validated existing targets and does not rewrite existing superclass edges. It therefore preserves the invariant and existing superclass chains. Direct mixin applications reuse owned contributions and do not add superclass edges to their source classes. The formal invariant makes these premises explicit; it does not constrain target computations to terminate.

The class Keyword

class distinguishes an instantiable class from an immediately evaluated object:

FormResult
class { body } or class[] { body }Anonymous zero-parameter class
class[params] { body }Anonymous class with constructor parameters
class Name { body } or class Name[] { body }Named zero-parameter class
class Name[params] { body }Named class with constructor parameters
{ body }One object, allocated and initialized on each evaluation
<: Mixins[args] < Base[args] { body }One object with the selected mixins and superclass

Class Literal Syntax

Constructor formals use brackets: class C[x, y] { body }. Empty brackets may be omitted. A class header contains formals first, then comma-separated composition directives, with at most one trailing comma. Parentheses remain ordinary message arguments; class C() is invalid.

Methods, factories, member classes and slots are private unless prefixed pub. Slots are immutable unless marked var; the canonical combined spelling is pub var x = value;. Duplicate/reversed modifiers, var on a method, class or factory, and visibility on locals/formals are invalid. Named class expressions at expression or module entry have no visibility modifier. pub class declares a public member. Generated new/N, default apply/N, and lambda apply/N are public protocols. An explicit private factory at the default apply arity replaces that default before public filtering. Possessing a privately acquired class value permits its public construction protocol; it grants no private authority over the resulting instance.

Class bodies contain slots, methods, member classes and factories, followed by an optional final | statement section. Slot declarations require semicolons; methods, members and factories permit them. Descriptor chains retain their annotation syntax.

Object Literals

An object may begin with a bracket header containing composition directives only. It then has optional direct applications and a superclass application, followed by its body. For example, [hide super.x/0] < Base { body } adapts Base’s public interface at the object’s owned boundary.

An object literal has no constructor parameter list or factories. Its optional mixin and superclass clauses have the same syntax, order and meaning as class clauses: mixins precede the superclass; <:/with and </extends are synonyms. Omitting the superclass selects structural root Object, without name lookup. Slot declarations still require their terminating semicolon.

{
    class M1[input] { pub first = input; }
    class M2[input] { pub second = input; }
    class S[input] { pub base = input; }
    pub composed = <: M1[1], M2[2] < S[3] { pub x = 5; };
    pub inherited = < S[4] { pub x = 5; };
    pub mixed = with M1[6] { pub x = 5; };
}

Each evaluation realizes a fresh anonymous zero-parameter class, then immediately sends its generated primary new/0 using ordinary exact message dispatch. Thus <: M[p] < S[q] { body } is equivalent to (class <: M[p] < S[q] { body }).new, with a factory-free body. Successful evaluation returns the initialized object. Repeated evaluation creates distinct class, metaclass and instance identities; it does not cache a singleton. Contributor factories and custom apply methods are not called or imported.

All constructor-clause rules apply. Targets resolve left-to-right for direct mixins, then the superclass, in the literal’s evaluation scope before allocation. Routed arguments run later in its own initializer activation, immediately before their contribution is initialized. In particular, self in a target computation denotes the enclosing receiver, while self in a routed argument denotes the new object. Ordinary initializer lookup also applies: an own slot can shadow an enclosing name and is still uninitialized during routing. For example, < S[x] { x = 5; } cannot use its own pending x as an argument; use a distinct captured binding or a qualified outer receiver when that is intended.

The anonymous class captures the literal’s evaluation scope, including deliberate creation inside another initializer. Contributors retain their own definition scopes and initializer-only constructor parameters; parameters are not added to instance-method bindings. Each contribution keeps its normal initialization order, occurrence, storage rules and private return home. Anonymous objects introduce no new outer qualifier.

An object literal remains an expression, not a valid normal module entry. Nested literals may use explicitly supplied module inputs, under the existing module restrictions.

Zero-Parameter Classes vs Singletons

For class Config { debug = false; }, Config() invokes its apply/0 factory; Config.new and Config.new() each perform primary construction once. For config = { debug = false; };, the slot already holds the initialized object. See zero-arity invocation.

Root Object Protocol

The fixed root has an empty instance protocol. Native objects and lambdas do not inherit equality, hash, display, null tests or conditional behavior. Their generated class/accessor/lambda operations remain available where applicable.

A library may explicitly define such methods and supply that class to clients. This example uses an injected IdentityMirror and ordinary source methods:

class Example[vm] {
    _vm = vm;
    pub class Value {
        pub equals(other) { _vm.same(self, other) }
        pub hash { _vm.identityHash(self) }
        pub toString { "an Object" }
    }
}

The returned Boolean and hash are foreign values under the selected boundary agreement. A native Boolean library can instead use sameSelect(self, other, yes, no) with its explicitly supplied objects. Selection returns the chosen object without invoking a callback. The client controls any later branch send.

Independent identity observations belong to the explicitly supplied IdentityMirror capability. It observes subjects without invoking their methods. Defining equals, hash, same or identityHash cannot intercept it. Library equality overrides should define a reflexive, symmetric, transitive relation with compatible hashes. Identity hashes are stable during the identity’s lifetime, may collide, and are not persistent identifiers or addresses. These optional library contracts add no inherited service or ambient authority to unrelated native objects or Aliens.

Capabilities and Definition Scope

The capability sources do not change definition scope: calling a class does not capture its caller’s scope. Named and anonymous classes follow the same rule. Examples with custom contributors or enclosing bindings assume an appropriate enclosing context; isolated modules and tooling evaluation have distinct entry contracts.

Constructor parameters are immutable bindings available only during initialization. Methods cannot resolve their own constructor arguments, even when called during initialization. Store persistent dependencies in slots. Lambdas and class expressions deliberately evaluated in an initializer may capture its parameters. Each contribution receives its own argument bindings; composition does not replace its captured definition dependencies.

Member Declarations and Class Expressions

A named class in body-declaration position declares a member class:

class Container[input] {
    pub value = input;
    pub class Member { pub read { value } }
    pub Captured = class { pub read { input } };
    pub NamedCapture = class Snapshot { pub read { input } };
}

Member binds to the enclosing receiver and its declaration/application origin. Its zero-argument accessor lazily realizes and caches one class per enclosing receiver and declaration occurrence. Repeated access returns that identity; different enclosing receivers or application occurrences obtain distinct classes. The member binds to the actual enclosing receiver while retaining the selected occurrence’s captured lexical ancestry at every depth, including when selected through super. Its factories retain that same definition parent. Ordinary public messages to the enclosing receiver still honor overrides; retaining ancestry does not restrict virtual sibling selection to the originating contribution. See lexical receiver selection.

The member can use stored value, but cannot acquire Container’s constructor binding input. Members are available regardless of their position among slot initializers.

Captured and NamedCapture are slots initialized by class expressions. Both capture the evaluation scope, including input. An expression’s optional name is declaration metadata, not a binding introduced in the surrounding body. Anonymous forms occur only as expressions; named forms can be expressions or member declarations. Lowering must preserve this distinction.

Member and slot names share a namespace; duplicates in one body are errors. A member also conflicts with a zero-argument method of the same name and has no setter. A stored class is callable through its current value; a member advertises its effective public factory arities before realization, as defined by member invocation. Wrong-arity invocation evaluates no contributor targets. Selected realization failures, including cycles or abandonment during non-local return, are cached without replay.

Initializer Bodies

The optional final | section executes after the contribution’s ordered slots. Constructor parameters remain available. No member, method, slot or factory declarations follow the delimiter; ordinary statements, including local var and class expressions, may occur there. Its ordinary result or permitted early-return value is ignored. The complete phase, home-lifetime and failure rules are in Initializer completion.

Inheritance

< Base[args] selects a native class and inherits its complete instance-side chain: owned contribution, applied mixins and ancestors. Omitting the clause uses structural root Object, without looking up the name Object. An instance or Alien is not a class target; no implicit instance.class conversion occurs. Bare super is a lookup origin, not a first-class expression. An ordinary expression such as super.Base or super.choose(config) may be a contributor target; it uses the surrounding definition scope’s super origin.

Construction runs the superclass’s complete initializer schedule on the newly allocated receiver. Inheritance imports no factories; factories belong to the declaring class.

Mixins

<: A[args], B[args] applies the owned reified contribution of each selected native class: directly declared methods, slots, member classes, constructor formals and own initializer. It imports no source superclass, applied mixins, factories, argument routes or prior composition policies. The definition scope remains captured. Resolving the source class itself still realizes its targets normally; applying its owned contribution does not evaluate those original constructor argument routes.

For example, if A <: M1, M2 < S1, B <: M3, M4 < S2, and C <: A < B, the contribution order is:

own(C), own(A), own(B), own(M3), own(M4), then the complete S2 chain

own(X) means X’s owned contribution. No intermediate classes are introduced. Repeated applications share the reified definition but have distinct application occurrences and initializer invocations. A contributed method’s super resumes from its application occurrence; see Name Resolution. Public mixin extraction and reflection are not part of the current language. Both clause forms select a class value; <: extracts its owned contribution internally and does not accept a standalone contribution value.

Constructor Clauses

Contributor targets are complete ordinary expressions, subject to the usual source-admission and lexical-scope rules. There is no additional syntactic restriction to names, paths or expressions statically known to return classes. Explicit brackets carry construction actuals and, for direct mixins, composition directives. Empty brackets may be omitted. Superclass brackets accept actuals only. Inputs precede the first directive; later inputs are invalid. No terminal call is split into a constructor route: < S(x) evaluates that ordinary call during realization and routes no arguments. < S[x] evaluates S during realization and evaluates x during each construction.

These clauses are available on ordinary class and object literals, including nested classes. Normal top-level module classes instead follow the isolated module-entry restrictions, which reject explicit contributor clauses before evaluating their targets.

Computed Contributor Targets

For < registry.choose(kind).Base[x], realization evaluates registry.choose(kind) and reads Base; construction later evaluates x. < choose(config)[arg] similarly evaluates the complete choose(config) call as its target. Targets run in the surrounding definition scope, including its super origin; the class being realized does not yet supply its own outer qualifier. Actuals run in the declaring class’s initializer scope and may qualify it. Direct mixin targets run left-to-right, then the superclass target. Each result is checked immediately and must be a native, non-metaclass class. A nonclass result, including an instance, lambda or Alien, or a metaclass result raises a runtime invalid-contributor error during realization, before any later target or routed argument runs. Errors or non-local returns from evaluating the target itself retain their ordinary behavior; target evaluation need not terminate.

After target evaluation, assemble the complete superclass, then direct owned contributions right-to-left, then the owned boundary. Every boundary binds its written directives against its unchanged lower public input and original current declarations. This work executes no source expression.

Sovereign publication and binding

A header supports rename super.x/0 as y, hide super.x/0, and delegate x/0 to super.y/0. These words are contextual at complete directive forms; ordinary expressions named rename, hide and delegate remain inputs before wiring begins. Rename/hide address the entire lower candidate family at an exact selector. Delegation replaces a current public owned operation with the first exact public lower target of equal explicit arity. The anchor keeps its original declaration category; execution uses the target’s effective kind, original occurrence, captures, slot/member identity and retained super input. Binding uses structural exact selection, never a getter read or a probe of its possible returned callable. Directive endpoints use explicit selector spellings, including outer and super with optional bang suffixes. These names do not select lexical receivers inside a directive. Parsing a directive does not validate its native signature: reserved native names fail composition validation when the class is realized. Consequently, an uncalled lambda containing class[hide super.outer/0] {} is valid source; evaluating that class fails realization. Only public effective declarations participate; wiring cannot recover private operations. Form each effective table before filtering visibility: an explicit private method replacing a public generated getter suppresses that getter.

The exposure and binding policies are simultaneous partial maps. Repeating an exposure source or binding anchor is invalid, including identical directives. Two surviving sources at one exact output selector within the same contribution position are a collision. Different positions retain ordinary lookup order. Identity rename adds no precedence. Swapping a and b is valid; renaming a to an unchanged b at the same position requires also hiding or moving b.

Validate written directives in order, source/anchor before destination/target, then equal arity and key uniqueness. After all directives bind, diagnose output collisions in contribution order, then selector-name order and numeric arity. Invalid signatures, absent public sources/anchors/targets, arity mismatch, repeated exposure or binding keys and collisions fail realization before construction effects. Valid source syntax alone cannot establish that these dynamic references and output signatures will succeed.

Publication changes never rename lexical declarations or requests in method bodies. Public requests remain virtual at their original spelling. A retained route survives hiding its target; a later boundary cannot acquire that hidden target through the restricted output. Hiding removes the entire lower family, without revealing deeper same-name candidates, reserving a spelling or providing a fallback. Two anchors bound to one target remain distinct publication sources. Complete superclass reuse preserves established boundaries/routes. Fresh owned reuse imports only the selected definition and receives fresh occurrence/policy.

Construction Order

For class C[x] <: A[a], B[b] < S[s] { ... }, successful primary construction:

  1. Allocates one receiver with complete occurrence, route, cell and member-cache associations and fresh uninitialized storage for its complete layout.
  2. Evaluates s and runs S’s complete initialization schedule on that receiver.
  3. Evaluates b and runs B’s owned initializer, then does the same for a and A.
  4. Runs C’s own ordered slots and final body, then returns the allocated receiver.

Each argument list is evaluated once, left-to-right, immediately before its private target invocation. Argument expressions run in the declaring contribution’s initializer activation, with its constructor parameters bound. Superclass and applied-mixin calls receive their own bindings and fresh homes. The declaring routes and owned body share one logical home, established before routing begins. Routing precedes slot completion, so returning to that home from a route cannot finish construction early. Each contribution completes its slots and final body before the next contribution runs.

These calls are private identity-bound routines, never selectors named initialize or public operations on arbitrary receivers. Initializer writes bypass overridable setters. No component instances are allocated, no effects are replayed or rolled back, and escaped partial receivers are not retracted. Return and failure handling follows Initializer completion.

Ordered Overrides and Disjoint State

Current public declarations precede the adapted lower interface. Direct mixins retain their declared left-to-right search positions, followed by the complete superclass. At each position, effective selector/accessor choice follows Message Sends. Private declarations are absent from public search and do not mask a lower public operation. A member override selects its whole declaration and origin; it does not merge families. Duplicate explicit declarations remain errors; explicit methods replace generated accessors before visibility filtering.

Slot storage is disjoint by receiver, application occurrence and local slot. Publication changes affect accessors, not cell identity or initialization. An immutable slot has no generated setter; a surviving mutable lower setter changes only its own cell. Immutability fixes the stored reference after initialization, not the referenced object’s state.

Storage and Contributor Contracts

The logical-slot mapping is total, functional and injective, and all selected accessors and initializer writes use that mapping. Member cache keys remain separate: two aliases of one member share one cache on a receiver, while separate occurrences remain distinct. Establishing routes and logical associations causes no getter read, callable probe, member realization or source effect.

Availability does not imply readiness. A public virtual read in a lower initializer can select an uninitialized upper cell and fail. There is no fallback to another initialized cell, no initializer replay, and no construction repair. Explicit state/provider objects can supply deliberate shared state through their public protocols.

Correct composition preserves contributors’ stated invariants under their stated preconditions and phases. The runtime does not check or repair these contracts. Public overriding, shared referents, callbacks/reentrancy, escaped partial receivers and supplied values still need their stated assumptions. Disjoint cells prevent one contribution’s primitive setter from writing another’s cell; they do not establish behavioral substitution. Appendix A states the injectivity and write-frame requirements.

Factories

A factory method is sent to the class object; an ordinary method is sent to its instances. Both use ordinary method invocation and lexical scope.

The Primary Factory (new)

Every source class and root Object has a generated, non-overridable primary new/N, where N is its constructor arity. Successful invocation allocates a fresh receiver, executes the complete construction schedule and returns that receiver. Its selector uses ordinary lookup; only its generated body contains private construction operations. Object literals automatically send this primary new/0 to their newly realized anonymous class.

factory new is forbidden. An ordinary instance method named new is allowed. This restriction preserves a primary entry that guarantees fresh allocation and the complete initialization schedule, while apply and named factories retain control over their results. It does not make an arbitrary new send an allocation primitive. Inheriting Object does not add new/0 to a class with parameters, and neither inheritance nor mixin application imports contributor factories.

The Callable Protocol (apply)

At constructor arity N, the default apply/N makes an exact self.new/N send. An owned factory apply at N replaces that default; factories at other arities coexist with it. A custom factory controls its result and causes no automatic allocation or initialization. It may call new, return a cached instance, or return another value.

class Point[xInput, yInput] {
    pub var x = xInput;
    pub var y = yInput;
    pub factory apply() { new(0, 0) }
    pub factory copy(point) { new(point.x, point.y) }
}

Point(2, 3) uses default apply/2; Point() uses the custom apply/0; Point.new(2, 3) performs primary construction directly. General callable selection belongs to Message Sends.

Named Factory Methods (factory)

Named factories such as Point.copy(p) are ordinary class-side methods with full result control. In a factory, self is the class object; lexical sends and qualified outer use the factory’s declaration origin and the class’s definition scope. A factory on a member class can therefore access its bound enclosing receiver. Invoking it does not capture the caller or instantiation service.

Bootstrap Metaclasses

Each source class C has a distinct metaclass C class, containing only C’s owned factories, with direct superclass Class and structural class Metaclass. Factory super continues at Class, independently of C’s instance superclass. The root relationships are:

IdentityStructural classDirect superclass
ObjectObject classTop
ClassClass classObject
MetaclassMetaclass classClass
Each of the three root metaclassesMetaclassClass

Thus Metaclass and Metaclass class form a shared two-object class-of cycle. Top terminates superclass chains without participating in this class-of graph. Object retains its empty initializer and new/0/default apply/0. Class, Metaclass and metaclass objects have no public construction factories; the common instance protocol of Class is initially empty. Structural links create no public class or outer selector, ambient binding or reflection API.
