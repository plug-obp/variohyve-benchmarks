VarioHyve Language Specification

Tooling Architecture

This chapter defines reusable frontend and tooling contracts, followed by the starter editor’s supported scope. Descriptors define inert annotation syntax; runtime diagnostics define detached failures. Tooling does not add an operational meaning to either annotations or syntactic observations.

Contract ownership has four layers: language semantics (scope, sends, construction and return homes); runtime/boundary services (source entry, receipts, adapters and admission); package/world conventions (explicit inventory, startup and native composition); and tool conventions (sidecars, project markers, editor commands and publication). The latter two do not add language semantics. An embedding can supply the same module inputs without any IDE or launch metadata; a particular launcher still requires its own declared configuration. The conformance map links these distinctions to executable evidence and selected profiles.

Optional Metadata and Source Coordinates

Each layer requires only its semantic input. Surface syntax stands alone without ANTLR tokens or contexts; core syntax stands alone without surface syntax; the runtime requires core code but no parser or source information. Required execution information missing from core is a defect in core/lowering; the runtime must never consult surface syntax to compensate. Position maps, core-to-surface mappings and descriptor associations are optional tooling data outside the trees. Execution diagnostics may use separately supplied evidence, but its absence must preserve coherent failure kinds, reasons, messages and semantic traces. It is a defect to fabricate a source location or recover absent surface/parser data through another execution’s metadata.

Declaration-relative scopes, contribution/application identities and return homes are required semantic information, not optional source provenance. Removing diagnostic evidence must not remove these language distinctions.

The implementation shares the reader-infra 2.0.0 SourceText coordinate basis: zero-based lines, zero-based UTF-16 columns and absolute UTF-16 offsets, with half-open ranges. LF, CRLF and CR each delimit one line. ANTLR code-point indices are converted at the reader boundary; lowering, runtime source projection and LSP consume the resulting coordinates without another conversion. EOF is a zero-width position at the actual end of the snapshot; recovery ranges are bounded by that snapshot, never by synthetic token spellings. Human-readable CLI formatting alone adds one for conventional line/column display.

The coordinate contract follows the LSP position and range contracts, selecting UTF-16. Revision digests hash the exact UTF-16 code units.

Inert Core Metadata

vh.syntax.core.metadata stores opaque descriptor data independently of surface syntax, parser objects and runtime values. CoreSyntax(root, descriptors) pairs an executable core root with an optional CoreDescriptorMap; an artifact without descriptors uses an empty map. Core nodes hold no pointer to it. CoreLoweringResult.core() exposes this artifact without retaining the frontend tracing maps.

CoreDescriptor.Entry.text() returns exact raw payload text. Identity-bearing entries and groups retain nesting, ordering and repeated occurrences; equal text does not merge entries. CoreDescriptorAttachment adds a stable occurrence and role, such as EXPRESSION, STATEMENT, RETURN or SLOT. Queries return immutable snapshots. descriptorsOf(owner) preserves groups; descriptorEntriesOf(owner) and descriptorTextsOf(owner) explicitly flatten those groups. describedElements(descriptor) and attachmentsOf(descriptor) provide reverse queries. Text that resembles nested annotations inside a payload is opaque; it creates no inner AST or reverse index automatically.

var root = num("42");
var map = new CoreDescriptorMap();
var entry = new CoreDescriptor.Entry("@foreign any syntax");
var attachment = map.attach(root, CoreDescriptorAttachment.Role.EXPRESSION,
                            List.of(entry));
var syntax = new CoreSyntax(root, map);
syntax.descriptors().descriptorEntriesOf(root); // [entry]
syntax.descriptors().describedElements(entry);  // [root]
syntax.descriptors().ownerOf(attachment);       // Optional containing root

A member class’s declaration and class literal intentionally share the same entry/group identities through CLASS_DECLARATION and CLASS attachments. A local declaration has one CoreBindStep and one LOCAL attachment. A final ordinary statement moves its attachment to the surviving expression, retaining STATEMENT. A final return keeps RETURN on its surviving return operation, separate from annotations on the returned value. Rewritten constructor roots move their attachments to the application edge. Relocation preserves attachment identity and role, rather than cloning payloads or leaving orphaned owners.

DescriptorProjection only copies raw leaves and groups, caching occurrence identities. Optional MetadataOriginMap traces entries, groups and attachments to surface nodes; no metadata entry retains this map. CoreOriginMap separately records executable origins and aliases for eliminated wrappers. directlyFromSurface() selects produced roots; originsOf() returns recorded associations; originOf() retains the preferred diagnostic origin. Adding an alias must not replace an expression’s narrower diagnostic origin.

Explicit interpretation by tools

VarioHyve is one available payload language, not the required one. A tool chooses which entries to interpret and may call existing capabilities separately:

var entry = new CoreDescriptor.Entry("types.answer");
ForeignObject toolTypes = (selector, arity) -> selector.equals("answer") && arity == 0
        ? arguments -> 42L : null;
// Opt into VarioHyve syntax, without source-admissibility checks or execution.
var parsed = Reader.parseExpression(entry.text());
// Alternatively opt into chosen checks, including the standard collection.
var checked = Reader.readExpression(entry.text(), SyntacticChecks.standard());
// After explicitly accepting a successful result, obtain ordinary core syntax.
var lowered = new SurfaceToCore().lower(checked.result().toOptional().orElseThrow());
// Execution is another explicit choice, with tool-provided capabilities/budget.
var runtime = new BootstrapRuntime(Map.of("types", toolTypes));
var meaning = runtime.evaluate(entry.text(), 10_000);

These are the normal APIs; no duplicated descriptor AST, automatic parse cache, or separate descriptor evaluator exists. A tool can use another parser, skip checks, analyze without execution, or supply an explicit type module/capability when executing. Attaching metadata imports neither the enclosing program’s lexical scope nor its authority into the tool’s interpretation. Any such binding must be part of the tool’s explicit agreement and capability inputs.

Payload parsing returns an independent read result with payload-local zero-based UTF-16 ranges. Its errors belong to the tool and never invalidate the surrounding program’s read result. When retained, a SimpleDescriptor source range denotes its exact payload substring, excluding verbatim fence markers. A tool may use that evidence to translate local ranges back to the containing document; without it the tool reports payload-local diagnostics. Whole-source snapshots and locations remain optional even though an entry retains its own required text.

The default editor highlights descriptor islands as opaque annotations. Its API-help consumer is an explicit opt-in interpretation, described under Starter Editor.

Source Checks

The frontend rejects language-invalid constructs established from source alone, including in unexecuted method and lambda bodies. It does not evaluate code or resolve ordinary sends against a presumed runtime world. Dynamic calls, computed contributor targets, holes and valid numeric syntax remain admissible even when a particular execution will fail. Descriptor payloads are excluded under the descriptor contract.

Reader.readExpression parses a complete expression and runs selected checks before lowering; the bootstrap source runner and LSP use this checked entry. Reader.parseExpression is the parser-only entry for syntax tools and fragments without their enclosing context. Results separate admission, diagnostics and analysis completion:

ResultRetained information
Completed, no errorsSuccessful surface tree and positions. Warnings remain in diagnostics() and do not skip later checks.
Parser errorDiagnostics and a recovery AST when available; source checks do not run.
Source-check errorDiagnostics, complete surface tree and positions as a partial result.
Cancellation/resource limitDistinct completion(), no successful execution tree and a tooling warning; source validity is unknown.

Callers must inspect ReadResult.diagnostics() even on success. The bootstrap execution entry currently consumes admission but does not print successful-read warnings; CLI analysis clients can consume the same Reader result directly.

Each SyntacticCheck owns its rule and traversal. SyntacticChecks selects an immutable ordered collection using standard(), none(), with(check) and without(id). Independent rules share a diagnostic collector, not semantic state. The check catalog lists standard rules and their stable identifiers. Disabling a check is tooling configuration, not a different language contract. Runtime guards remain necessary for direct core or unchecked inputs; source checks prove neither binding nor executability.

Bounded reading and delimited fragments

ReadLimits selects source-size, delimiter-depth, parse-tree-depth, work and elapsed-time limits per request. These are implementation policies, not language limits. Default batch reads use structural and work bounds without a wall-clock deadline (Duration.ZERO), so ordinary execution does not fail merely because the machine is slow or busy. Interactive reads retain their 750 ms deadline; callers may explicitly select a positive elapsed-time limit. Cancellation remains active in both policies. The reader checks cancellation during lexing, token prediction and between source checks, bounds token storage and prediction configurations/caches, and guards tree depth before mapping or recursive consumers. Prediction caches belong to the request. SLL parsing with bail falls back to ordinary LL recovery within the same budget. A stack exhaustion is reported as incomplete analysis rather than escaping as a JVM error. A caller-supplied check must bound and cooperate inside its own work; these APIs cannot preempt arbitrary foreign Java code.

Reader.parseMethodBody("{ ... }") invokes the same delimited-body rule used by methods, factories and lambdas and requires end of input. It returns statements, positions and diagnostics without synthesizing a class, formals, receiver or return home. It does not run enclosing-context source checks. The overload taking a parent string and start/end offsets returns a FragmentResult with explicit parent-snapshot range translation. The fragment retains its own exact source; it must never borrow the full document’s revision digest for execution results.

This permits small, independently selected regions to be parsed now. Automatic incremental replacement is not yet implemented: it needs reliable token-level boundaries through comments, strings and descriptor islands, rebuilt ancestor nodes and ranges, and invalidation of affected source checks. A parsed statement list alone does not establish those conditions or the enclosing lookup context.

vh.syntax.analysis.SnapshotAnalysis owns replaceable document analysis outside the LSP: it coalesces pending edits, cooperatively cancels obsolete work and uses two workers. Exact submission identity distinguishes even reopenings with the same revision number. Consumers recheck that identity under their publication lock before applying a result. The LSP invalidates old syntax/runtime ranges before scheduling work; queries await their snapshot without holding that lock. A resource outcome appears as a document-level warning, never a red syntax error.

Analysis Evidence and Client Policies

Analysis belongs to the frontend or explicitly selected tools. The LSP adapts requests, ranges and presentation; the same APIs serve CLI analysis, tests and documentation tools. It owns no language facts or second operational semantics. A future VarioHyve-specific protocol could use these APIs too, but is not implemented.

AnalysisResult<T> reports must ⊆ actual ⊆ may for a stated query domain, snapshot, model and accepted assumptions. These qualifications travel with the result; a guaranteed fact must not be presented as an unconditional claim about an arbitrary foreign system.

BoundMeaning under the recorded assumptions
Inside mustDefinitely present.
Outside a sound mayDefinitely absent. An open upper bound excludes nothing.
Inside may, outside mustUnresolved: possible, not guaranteed.

Equal finite bounds are exact. An informative upper bound alone is an overapproximation; an informative lower bound alone is an underapproximation; both provide mixed knowledge. Empty lower and open upper bounds mean unknown. Suggested candidates are separate: a finite completion list is not an exhaustive upper bound, and absence from it proves nothing. Evidence explains syntax, repairs, profiles and contract locations. Results with different domains, snapshots or assumptions cannot be combined without justification; no automatic cross-analysis proof/trust aggregation exists.

Initially, exact facts concern structural declaration occurrences in a complete matching syntax snapshot. A selector declared in a local mixin does not establish receiver selection, accessor eligibility, dispatch, execution success or absence of dynamic references. There is no conventional static binder inferred from enclosing declarations. Independently justified source checks remain separate. Starter API suggestions have empty runtime must, open runtime may and possible labels explaining the selected documentation contract.

Alien providers may supply analysis-specific contracts about selectors, results, effects or callbacks. A consumer decides whether it trusts the identified provider’s promise and evidence for its purpose. Universal fully proved bounds are not required: proofs have model/checker assumptions, while tests, attestations or accountable promises may suffice for one mission and not another.

Evidence separates these records:

  • Provider attribution, which is not authentication; a file path establishes neither.
  • The promised contract, applicability and optional revision. An absent revision is not an immutable identity.
  • Evidence kind/artifact. A proof claim is not a verified proof.
  • The consumer’s purpose and rationale, with an unassessed, accepted-for-purpose or rejected trust assessment.

Accepting evidence neither runs an analysis nor promotes candidates to must. Recording an assessment does not mutate reported bounds. Missing/rejected evidence leaves usable knowledge open where no independent accepted model supports a bound; it does not block ordinary execution or replace foreign semantics. Descriptors may carry agreements but establish no trust merely by being present. The implementation carries records, not a universal trust policy or proof checker.

Client purposeRequired evidence
Red errorsEstablished language violations or definite failures under stated accepted assumptions. Unknown/incomplete/possible failures and rejected provider evidence alone are not source errors.
CompletionFavor coverage; distinguish guaranteed, possible and unknown. Claim exhaustiveness only with a justified upper bound.
NavigationJump to an execution target only when uniquely established; otherwise show alternatives or unknown. Starter API links navigate selected documentation.
RefactoringRequire coverage of affected references and preservation of relevant behavior. Unique navigation or absence of diagnostics is insufficient; unknown dynamic references cannot be silently skipped.

Bounded ambient authority may enable finite upper bounds through explicit module inputs and accepted models of reachable capabilities. Unmodeled foreign behavior and reflection remain open where necessary. AAM derivation, semantic dispatch analysis and guaranteed refactoring are deferred; this protocol implements none of them.

Runtime Diagnostics

An explicit evaluation may produce a detached runtime diagnostic. Optional origins and excerpts describe the compiled snapshot and its revision digest; the runtime chapter defines failure payloads, semantic traces and source-free formatting.

Lowering preserves the most specific recorded occurrence for generated code. Each cascade send uses its original message arm; failures in its receiver or arguments retain their narrower origins. Enclosing fallback evidence must not overwrite those sites. Constructor-target rewrites and synthetic return wrappers follow the same rule. Generated temporaries remain private, and absent provenance still produces a coherent source-free failure.

RuntimeDiagnosticAdapter in vh-lsp maps a diagnostic to an LSP error only when the caller supplies a document URI, source name and revision digest that match its primary site. Zero-based, end-exclusive UTF-16 ranges are already LSP ranges. The stable reason becomes the diagnostic code; matching declaration, call and definition sites become related information. Absent primary origins, stale revisions and unmapped cross-source sites are not assigned invented ranges. The caller is responsible for verifying the document snapshot before publication.

The adapter itself neither executes nor publishes. The language server records each open document’s URI, version, absolute source name and digest of its exact UTF-16 code units. The explicit vh/runtimeDiagnostics notification publishes a runner result only when all four match the current snapshot, then combines it with source-check diagnostics. Editing clears prior runtime results immediately; closing clears all results. Open, edit and save never execute source.

Starter Editor

For files without adjacent recipe launch metadata, the VS Code extension selects the JavaHostKernel starter world explicitly. Run File saves a local module and launches vh.host.Main run in a separate JVM; Test File selects the SUnit runner. The module receives its kernel (and, for tests, testing library) through ordinary constructor inputs. Console input and output use an integrated terminal separate from LSP traffic. Stop Program terminates that run’s process. Restart Language Server restarts editor assistance. Starting Java or running programs requires workspace trust. Run/Test uses its own Java/runner preparation; unavailable or still-starting assistance does not block execution. Runtime Problems publication is best effort when the language server is available; the terminal retains execution results.

Source analysis and API assistance support local files and untitled VarioHyve buffers; only file execution requires a saved local path. The status item separates restricted/unavailable assistance, server startup, pending analysis, completed source checks and incomplete/failed analysis. A completed status requires a matching document URI, version and source digest; empty Problems alone is not proof that analysis ran. Source-error/warning counts remain distinct from completion. The checkmark means source checks completed, not that execution will succeed. TextMate highlighting remains available without Java or workspace trust; its word selection includes legal bang selectors. Opaque descriptor payloads have the dedicated semantic token type descriptor and TextMate scope comment.block.descriptor.vh, with comment-style theme fallback so inert metadata is distinguishable from executable parameters and names. Themes and user token customizations retain control of the actual colors; payload content is never highlighted as program declarations.

The language server distinguishes shutdown from exit. Shutdown releases document state and cancels pending diagnostic publication before replying; later requests receive InvalidRequest. The subsequent exit notification terminates the server process, with status 0 after shutdown and 1 otherwise. The process entry point owns termination; embedded services can be closed without exiting their host JVM. Client disconnection also releases the launcher and document services.

The packaged runner writes a detached diagnostic sidecar for the executed snapshot. The extension verifies it against the launch snapshot and the current document before forwarding it; the server independently verifies the snapshot. Source changed while a run is active therefore cannot receive obsolete ranges. An explicit run may still report its original failure in the terminal.

Run/Test retains the requested document across saves, Save As, server startup and disk verification. A newer Run/Test supersedes older preparation and execution; Stop also cancels a launch that has not spawned yet. Snapshot changes during preparation require another explicit run. Switching the active editor never changes the file selected by a pending command.

The program console provides line input with Backspace, Enter, EOF and interrupt. Unsupported terminal navigation/control sequences are consumed as whole sequences, including when split across input events, rather than leaking their bytes into program input. Multiline pasted text submits successive lines. This is a line console, not a terminal emulator with cursor-based editing.

Completion, hover, signature help and API-definition navigation read the bundled class-shaped API contract. Its consumer parses only the documented literal host, doc and returns schema; malformed/unknown payloads are ignored, and annotations are never evaluated. The analysis evidence policy defines the conditional status of these suggestions and documentation links.

The declared starter convention supports:

  • Literal receivers and documented result chains.
  • The plain module’s first constructor input during slot/final initialization, including nested lambdas, regardless of parameter spelling.
  • Direct unmodified slots retaining that input or one of its selected services in instance code. Constructor parameters do not become method bindings and factories do not receive instance-slot evidence.

Only enclosing routine parameters/locals shadow this structural evidence; unrelated routines do not. A lambda’s own declarations can invalidate it. Any matching executable setter marker conservatively invalidates retained-slot help, even if it might target a different object/local: resolving writes would require operational analysis. Absence of such a marker proves neither absence of mutation nor absence of overrides.

Named receivers across nested classes/objects, invoked getters, mutable aliases, slot-to-slot propagation, composition and unknown dynamic receivers receive no guessed protocol. Editing repairs may fill a missing selector/argument or close delimiters for parsing; arbitrary recovery does not establish a protocol. These are structural filters for the starter convention, not lexical selection, accessor resolution or execution simulation.

Folding uses mapped class, method, factory, lambda and initializer ranges, plus multiline opaque descriptor ranges. Selection returns one entry per requested cursor, in the same order. Unmapped text, including trailing comments or an empty document, receives a zero-width fallback. Parent selections strictly contain their children; absent, duplicate or incompatible recovery ranges are skipped.

Independent scratch evaluation

Evaluate Selection in Scratch copies exactly one nonempty selection into a separate, editable untitled VarioHyve document and evaluates its complete text. Evaluate Scratch reruns that document. Each invocation uses a fresh process with the declared starter tooling context: kernel is JavaHostKernel, alongside the bootstrap Object, null, true and false. These are explicit tool inputs, not ambient module authority. No receiver, locals or return home is captured, and no earlier evaluation state is reused. Each invocation’s effects remain real and are not rolled back.

The ordinary checked expression entry remains in force. The tool introduces no wrapper, relaxes no source check and executes no unrelated source text. Multiple statements can be written explicitly as (fun { ... }).apply(). Native/foreign object results get generic labels; displaying a result performs no extra message send or arbitrary foreign toString. Returned native receipts are released.

The host entry is vh eval <file> [--source-name <label>] [--diagnostics <file>]. The label is diagnostic identity, never a path to reopen. The editor writes the exact scratch snapshot to a temporary UTF-8 transport file and uses the scratch URI as its source name; invalid UTF-16 is rejected rather than silently replaced. Runtime Problems are published only to the matching scratch URI/version/digest. The original document and its diagnostics are unaffected. Stop and newer explicit execution cancel pending scratch launches too; temporary files are removed when the run ends or preparation is cancelled.

Scratch context membership lasts for the editor session and is not inferred from a saved filename. Saving the text does not turn ordinary Run File into expression evaluation. Object inspection, persistent sessions, customizable contexts and debugger activation evaluation remain independent future features.

Evaluation Contexts

A tool can evaluate with explicitly supplied objects or select a debug activation. The context uses activation objects, ordinary lexical lookup and the same Alien/Expat and return rules. It introduces neither a separate Environment namespace nor a global service registry. Language-visible debugger and mirror services must be explicitly supplied boundary capabilities. Internal activation selection does not make activations public language values.

OperationContext
Module instantiationEmpty top activation; explicit constructor inputs
Tool expression evaluationExplicitly supplied objects, such as sample data or a console
Proposed debugger evaluationSelected activation’s bindings plus explicitly supplied services

A tool must identify its context and additional capabilities. It cannot silently enrich normal module entry. Results retain actual lexical captures, including classes that resolve superclass/mixin targets there; export and persistence must preserve or explicitly account for those dependencies.

The Java entry paths implement module and supplied-expression evaluation, not a general selected-activation debugger API.

Admitted Source Services

P2 supplies two separately granted callable services from BootstrapRuntime:

Host provisionOrdinary callContext and result
moduleImporter()importModule(snapshot, input1, ..., inputN)Fresh isolated class and instance, empty top activation, exactly N constructor inputs
expressionEvaluator()evaluate(snapshot, context)Evaluate in the supplied native object’s lexical scope and return the ordinary expression result

SourceSnapshot(name, source) is immutable source transport, not executable AST or filesystem authority. The name labels captured diagnostic evidence and is never reopened. The services accept at most 1,048,576 UTF-16 source code units and 4,096 name code units. A resolver can impose tighter file limits. Parsing and source checks occur inside the selected Alien operation, before admitted native execution; their ordinary preparation exceptions become foreign failures. Runtime language/ownership/policy failures retain their existing kinds. A bad snapshot type is a conversion failure. These services do not change the ordinary host source-entry methods or make arbitrary new-VM reentry legal.

Expression evaluation adds no kernel, canonical-name bindings, caller locals or return home. Its context must be a native object. Lookup follows that object’s actual lexical parents; methods and returned closures retain their real captures. An arbitrary context object is therefore not a confinement claim. Packaging constructs its context through an isolated module with explicitly selected slots and inputs. Canonical values remain available to runtime literals/empty results according to the selected profile, even when names such as true are unbound. Passing an enriched context as an input to an imported module still does not lend the module that context’s lexical scope.

Source entry uses ordinary boundary admission and the currently admitted machine. Nested source execution shares the active step budget and callback-depth limit; it cannot replenish either. Independent service entry uses the runtime’s immutable ExecutionPolicy (100,000 steps by default), selected before application execution. Existing explicit host source-entry budgets remain supported. Compilation and foreign I/O costs are not native transition counts. Source maps are installed under admission; contexts, input aliases and intermediate class definitions remain rooted through construction, callbacks and collections. Native results are invocation-attached during a foreign call and owned receipts at independent host entry, following the ordinary Alien/Expat contract. No implicit detachment or raw runtime representation is exposed. Return barriers, failure effects and the prohibition on retry remain unchanged.

The packaging resolver and native realizer are application code over these services; they do not add another lookup or wiring language. Interactive IDE launch metadata and general activation reflection remain separate work.

Packaged Alien Realizers

The selected first packaging contract is loadAlien(folder) returning a callable realizer, followed by an ordinary apply/N send with explicit inputs. The loader is an explicitly granted capability; imported foreign behavior receives no native lexical scope. Loading may execute foreign initialization, while separate metadata inspection must not execute provider code. The returned realizer’s selected operation declares retention permissions before argument conversion; the loader does not bypass that send or forward a reconstructed argument list.

The host owns package-file/classloader resources for the execution session. Releasing them requires ending their use; it is not universal revocation or permission to close arbitrary exported capabilities. Selected failures preserve their boundary kinds and do not cause fallback or automatic retry. Package metadata describes declared ingredients and compatibility, not verified behavior.

P0 and P1 implement this contract in vh-packaging. The first native client uses existing isolated module entry with the loader as its explicit input. P2 adds the separately granted source services, as described in the packaging plan.

Native Recipe Launches

P3 associates a library with one launch through adjacent <file>.vh.launch.json metadata. The inert variohyve-launch-1 format requires format, root, recipe, selector and arguments, with optional startup, execution, test and packaging objects, plus an optional alienRoot path. Unknown or duplicate fields are rejected. The root is relative to that metadata file; the recipe is a source path within the root; arguments are bounded JSON scalars. The packaging guide defines the concrete limits, examples and CLI. Reading metadata performs no native evaluation or provider loading and gives no completeness claim about the world.

WorldLaunchMain receives a tool distribution and launch file. The distribution supplies the native realizer/context and an independently root-bounded Alien loader; the metadata root supplies read-only source access. Optional alienRoot selects a provider root relative to the sidecar instead of the tools directory. The same root supplies startup adapters and recipe providers. It is an explicit filesystem grant, with no search, root merging or fallback. Native packaging policy captures project-owned providers through sources.alien and declares their deployment paths through output.alien; no provider registration is needed. The fresh runtime defaults to HOST_SCALARS with the existing integer/double/string protocols selected through a narrow scalar adapter. The native recipe context explicitly exposes files, importModule, loadAlien, true and false. It does not supply the JavaHostKernel bundle. Recipes perform imports, pattern construction, wiring, and suite execution through ordinary native sends. The host retains the world under an owned Expat receipt and sends the configured public message once. Temporary/result holds close before the Alien loader session ends.

The launcher displays transported scalars or generic object labels without invoking result behavior. false remains a valid result. The shipped native suite runner returns false for recorded assertion failures; an uncaught runtime failure aborts the attempt, produces no result, and triggers no retry. This is a native application contract, separate from the starter host SUnit driver’s per-case recovery policy. The combined regex recipe eagerly requires RE2 even for its native launch; the separate native-only recipe loads no Alien provider.

Run File and Test File use the adjacent metadata when present; explicit Run Recipe requires it. Invalid metadata fails rather than selecting another runner. Before launch, the editor saves dirty open VarioHyve documents within the selected source root and verifies their snapshots and the metadata. A pinned metadata digest is checked against the text actually read by the CLI. Every attempt is a fresh process with existing workspace-trust, cancellation and stop behavior.

Reports carry the actual primary failure’s source name and revision digest, including imported modules. The editor verifies the captured open document’s identity, version and digest before sending each source’s report through the existing runtime-diagnostic channel. It never attributes an imported failure to the initiating file by default. Stale, closed, reopened or unmapped snapshots remain terminal evidence; cross-source related trace sites remain there too. Exact absolute source-name matching may leave filesystem aliases unmapped.

Adjacent launch metadata or an ancestor .variohyve-project marker removes the starter assumption that a module’s first constructor input is JavaHostKernel. The inert project marker covers nested imported modules without a launch file; it does not supply capabilities or configure execution. Assistance rechecks presence for each request, even for malformed metadata; scalar literal help remains conditional on the selected scalar documentation and excludes String split and its host-collection result chain. No recipe execution is used to infer inputs, selectors or dependency graphs.

Development startup uses the same exact four fields, adapter loading, boundary profile and explicit stream grants as deployment startup. It changes runtime construction before publication, never an existing runtime. Without it the previous scalar context remains the default. result: "discard" releases the result without displaying it.

An optional execution: {"maxSteps": 1000000} selects the positive, JSON-safe integer transition limit for each independent entry into that runtime. Recipe realization, imports and callbacks within an entry share its remaining budget. The same declaration is accepted in deployment metadata, where native packaging policy records it with output.execution(maxSteps). The default remains 100,000; an exhausted entry reports STEP_LIMIT_EXCEEDED with its captured source evidence. No callback-depth change, execution mirror, live policy mutation or foreign-code timeout is implied. vh-package --launch also uses the selected limit for its native policy execution; the policy explicitly chooses the deployed limit.

An optional test: {"selector": "test", "arguments": []} declares a separate ordinary world send. vh-world --test requires this entry and a transported Boolean result: true prints PASS with status 0, false prints FAIL with status 1. Non-Boolean results and execution failures return status 1; missing test metadata returns status 2. Suite iteration and assertion policy remain native. Ordinary Run still accepts false as a successful value.

An optional packaging: {"policy": "Package.vh", "selector": "build"} selects an isolated native policy under the same source root. vh-package <tools> --launch <metadata> <new-output-dir> reads that entry; --launch-id can pin its text. The existing explicit policy invocation remains supported. The metadata contains no dependency inventory: the native policy declares sources, providers, startup and deployment launch through the existing output capability.

Declared Deployments

P4 implements native packaging policy over explicit artifact capture and output capabilities. An isolated policy module selects source files, packaged providers, runtime artifacts and concrete launch inputs using ordinary sends. The output service consumes captured bytes and writes a pinned inventory; it does not interpret native wiring, enumerate a realized object graph or infer dependency closure from execution. Packaging validates its artifacts without evaluating the application recipe or initializing providers. The packaging guide defines the concrete protocol, format, limits and commands.

A deployment session eagerly captures and verifies every declared file before realization. Its files.resolve capability admits only declared source names and returns captured source snapshots. Its loadAlien capability admits only declared provider folders and activates private verified copies. Neither may fall back to neighboring files, development roots or application-classpath providers. Native context/realizer helpers are captured ingredients too. Missing, changed, incompatible or unsupported declared ingredients fail even if the selected launch would not use them. Additional runtime inputs can reach deferred imports only when those ingredients were declared; one observed trace is not evidence of complete future dependency closure.

The Java Alien manifest can additionally declare deployment provisioning and pinned resources. P4 deployment accepts only provisioning none: foreign implementation resources and notices are local declared files, and the loader supplies no ambient services. Explicit arguments to a realizer are separate from loader provisioning. Missing declarations, session-only or development-only provisioning, and other unsupported requirements are errors. Ordinary development loading retains the earlier contract. A replacement for a development service is explicit recipe/policy selection; deleting an inventory entry cannot remove authority already captured by a live object.

Deployment re-evaluates the pinned recipe through the native world realizer and ordinary source-entry services. Each attempt creates fresh objects with explicit capabilities; it does not persist a heap or promise identical external effects. The host owns the session’s private files/classloaders and ends world use before releasing them. Closing resources is not universal revocation. Uncaught failures do not produce a successful world or trigger retry/rollback. Publication itself is an effect: a policy failure after a successful finish cannot undo it.

The format uses SHA-256 pins as revision evidence, not publisher authentication. It also cannot authenticate bootstrap code the JVM has already loaded. Java providers retain normal host-process authority. Filesystem roots must remain stable during capture; pinning does not imply an adversarial concurrent filesystem snapshot protocol. Runtime/launch assembly remains separate from native seeding, and deployment gives no permission to reseed a published runtime.

Explicit deployment startup

The optional startup declaration selects a declared, pinned Alien package whose entry additionally implements the shared Java HostValueAdapter interface. The launcher verifies the complete deployment before loading that entry, then passes the adapter to the existing runtime constructor. It does not invoke the entry’s ordinary apply outside a boundary or modify a published runtime. Package inspection/publication remains inert; an incompatible adapter facet fails at activation. The owning deployment session outlives the runtime/world uses.

Native packaging policy chooses the adapter folder, boundary profile (host-values or host-scalars), provisioning (none or stdio) and result presentation (display or discard) through output.startup/4. The format and validation limits live in the packaging guide. Without this declaration, the existing scalar adapter, five-input recipe context and displayed result remain unchanged. Older readers reject the new optional field explicitly rather than silently launching with a different configuration.

A startup-configured recipe uses an isolated context with files, importModule, loadAlien, true, false, null and provisions. Canonical values are imported according to the selected profile. none supplies a provisions object with no operations. stdio exposes only input/0 and output/0, returning streams explicitly supplied by the launcher/embedder; neither the provider nor the recipe implicitly discovers process streams. The caller owns these streams. The recipe chooses whether to pass them to a console realizer. Imported modules still receive only their constructor inputs, without recipe-context inheritance.

discard releases the returned boundary hold without printing a result; it does not suppress effects such as Console output or turn failures into success. This supports the unchanged tutorial run convention. A native Kernel module assembles independently packaged parser, collection and Console services. Kernel assembly does not select literal protocols; startup adapter selection remains separate. The shipped native SUnit runner returns a Boolean for assertion results and aborts on execution failure, retaining the distinction from the host test driver’s recovery and per-case entry budgets.

Execution, Observation and Intervention

The execution agreement distinguishes ordinary evaluation, representation maintenance and explicitly authorized observation/intervention. Tools use that contract rather than gaining execution rights from possession of a configuration. Backend preparation and retention follow the Java coordination rules.

For example, an immutable published observation can be consumed while ordinary execution continues. Reading live slots needs a specified consistency model; changing one is an intervention whose effective ordering must be defined. Replacing or resuming a continuation also needs an ownership-transfer protocol so its previous owner cannot continue. These examples do not imply a general monitor or selected-activation intervention API in the current prototype.

A model checker is another explicitly supplied tool: a supporting parallel VM could honor its request for independent simultaneous transitions under the parallel-agreement requirements. The execution capability, proof evidence and concrete implementation must meet that agreement; a saved configuration alone supplies none of them.

Descriptors as the Naming Bridge

Intrinsic declaration names identify many syntax elements. A descriptor can name an otherwise anonymous expression, for example (compute(x) : intermediate). It attaches information without changing execution. Name resolution for tool references is separate from language message lookup.

External Annotation Files

Each tool may keep a separate external file associating syntax identities with its own facts: a type, interval, units assumption, proof obligation or diagnostic. Formats and interpretations belong to the tool. Adding or changing annotations does not alter raw execution, supply runtime capabilities or establish that an asserted property holds. Different tool views need not use a shared format.

Qualified Naming

Paths such as module.Class.method.local are proposed tooling conventions, not language selectors. Tools must resolve collisions and preserve references when source changes. Descriptor-supplied names can identify subexpressions, but a stable AST/source-mapping scheme is still required; spelling a name alone does not solve identity across edits.

Connection to Abstract Interpretation

The explicit-state visitor machine provides a starting point for analysis. AAM and ADI are research approaches, not modes enabled by an allocator or an “abstract kernel.” The required derivation is described under Persistence and Analysis.

Annotations may supply domains or assumptions subject to the analysis evidence policy. General semantic analysis, mirror tooling and persistence remain future work.
