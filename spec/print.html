VarioHyve Language Specification

Behavioral Federation

VarioHyve investigates how programs can coordinate systems that keep their own meaning, execution mechanisms and authority. A model repository, a simulator and a running controller can cooperate without becoming objects of one universal model or processes of one execution engine. The difficult part is making the agreements between them explicit enough to understand, change and examine.

We call this behavioral federation. The experiment combines an object language, a native/foreign boundary and an explicit execution model. Its working hypothesis is that a small, coherent set of mechanisms can make coordination behavior easier to reuse and its assumptions easier to inspect. An executable bootstrap now allows that hypothesis to be investigated through programs and tests. Whether the combination improves real engineering workflows remains an empirical question.

Cooperation Without Complete Control

A system-of-systems brings together participants that retain substantial operational and managerial independence. Their owners, release cycles and objectives need not coincide. Engineering environments encounter a related problem when requirements, designs, simulations and operational records live in different tools. The engineered product need not itself be a system-of-systems for its engineering models to require federation.

Consider a pumping station. A requirements model states a minimum flow, a hydraulic simulator predicts performance, and maintenance records describe the installed equipment. Each may refer to the same pump while expressing different facts about it. Assessing a proposed replacement requires a correspondence between those references, compatible units, an agreed revision of the design and a policy for interpreting the analysis. Authorizing the replacement requires additional authority. A successful assessment alone does not supply it.

API connectivity solves only part of this problem. A simulator may finish after the relevant design has changed. A service may fail after accepting a request, leaving its effects uncertain. A callback may arrive while the coordinator is waiting for a result. The engineer needs to know which observations support a decision, which assumptions remain in force and what a failed interaction means. Replacing the simulator with a recorded trace should expose the changed assumptions while preserving the intended coordination protocol.

These needs become language and tooling questions when the workflow must be maintained across many projects. Builders of modeling environments need reusable behavior over heterogeneous models, traceable evidence and controlled access to tools. Moving every model into a new metamodel can be expensive or inappropriate; reimplementing every participant’s behavior can lose exactly the semantics that made it useful. Existing federation and model-management tools already address substantial parts of this problem. VarioHyve asks what a compact coordination language can contribute alongside them, and what it costs compared with their own workflows or direct host-language code.

Agreements Expressed Through Objects

The approach starts with supplied capabilities: objects whose behavior grants access to particular services or resources. A coordinator receives the capabilities it needs and exchanges objects by sending messages. Its inputs can represent a narrow model query, an analysis operation or permission to record evidence. The supplying system determines the available authority; the coordinator’s source makes its use visible.

This is also a commitment to semantic sovereignty. Foreign participants retain their own execution and interpretation of operations. The boundary states how messages, values, identity, failures and callbacks cross between them. An operation may return an ordinary value or promise an explicit outcome protocol, just as a native method may. A shared message syntax does not establish agreement about units, revisions or successful completion: those remain part of the supplied operation’s contract.

Here, “contract” means an agreement about behavior and authority, not an implemented contract language or automatic proof system. The boundary makes such agreements a subject of design. It also makes their limits visible. For example, foreign code running in the same host process can terminate that process; a capability interface alone does not provide process containment.

A Language for Explicit Dependencies

The following module illustrates the shape of a coordinator:

class Assessment(modelSource, checker, evidenceSink) {
    models = modelSource;
    analysis = checker;
    evidence = evidenceSink;

    assess(item) {
        var snapshot = models.snapshot(item);
        evidence.record(snapshot, analysis.check(snapshot))
    }
}

The host supplies three existing objects when it constructs Assessment; it later requests an assessment by sending assess. The module retains its inputs in slots because constructor parameters belong to initialization, rather than becoming instance-method bindings. Nothing in this code requires the three services to be implemented in VarioHyve. Their selectors are application agreements, and the example deliberately leaves their failure and evidence policies to those agreements.

A normal module begins over an empty top activation. It receives external capabilities through explicit constructor inputs and, subsequently, message arguments and the behavior of objects already available to it. There is no ambient application namespace. Supplied objects keep their own authority and captured scopes, so a short parameter list is not by itself an isolation proof. The program-structure chapter defines this entry contract precisely.

Within the language, objects and message sends also organize access and reuse. Slots are accessed through messages; lexical scopes are activation objects and ordinary objects. Classes are first-class values. Composition uses reified contributions and application occurrences, retaining the declaration origins that determine scope and invocation. A reusable analysis stage can therefore keep access to its defining provider even when applied in a receiving module with similarly named bindings. The rules aim to make that behavior predictable without merging independently defined models into a deep class family.

For language design, the question is whether these mechanisms work together without hidden exceptions at each point of reuse. Definition scope, receiver identity and contribution selection must remain intelligible when code moves between modules or across a foreign boundary. The specification fixes these rules independently of the Java representation, giving alternative implementations a contract to preserve. That precision also exposes costs in notation, implementation and debugging that the experiments must assess.

Foreign values appear inside the language as Aliens; native behavior is exported as Expats. Sending a message to an Alien uses the ordinary source syntax. The adapter mediates the operation, and foreign code may call an Expat while the native caller waits. Language-visible VM services use this same boundary, with separately granted privileged capabilities. Explicit mirrors can offer information beyond ordinary behavior. The boundary chapter defines these interactions, including identity, failure and the default prohibition on non-local returns crossing a foreign call.

Making Execution Available for Inquiry

Coordination becomes easier to investigate when execution itself has a precise description. VarioHyve’s machine exposes configurations and transitions for evaluation, invocation, storage and control. This supports a correspondence between language rules, executable behavior and observations made by tools. It does not by itself establish that correspondence as a proved theorem.

The current sequential execution agreement uses a conceptual control token for ordinary native execution. A native-to-foreign call transfers control to the foreign side; an admitted callback can return it to native execution before the original call completes. Multiple callback workers must negotiate admission, and the current implementation serializes their native execution. The token need not be a runtime object. Its purpose is to describe an agreement that an implementation must realize.

That agreement leaves room for explicitly confined extensions. A collector may perform concurrent maintenance if it preserves the required abstract behavior. A monitor may have a separately specified intervention capability. A future parallel machine may execute proven-independent transitions under an appropriate execution agreement. These possibilities have distinct obligations; granting one does not silently grant unrestricted execution authority. The formal appendix states the model and its limits, while Future Directions separates accepted extension principles from mechanisms still to be developed.

This opens two different lines of inquiry for formal methods. A coordinator can call an external checker as a supplied capability. Separately, an analyzer can be derived for the coordinator’s own execution semantics. The first requires an agreement about the checker’s inputs, results and assumptions; the second needs an abstraction and soundness argument, including a treatment of foreign effects. Neither alone verifies a complete federation or its physical environment. Descriptors can carry tooling information, but attaching information does not establish its truth. Keeping these distinctions explicit makes proposed claims testable and clarifies the evidence still required.

What the Bootstrap Establishes

The present result is an executable language bootstrap centered on VisitorSemanticsVM. It includes parsing and lowering, explicit module entry, object and class construction, reified composition, lexical lookup, closures and return-home checks, a native heap collector, and a synchronous Java Alien/Expat boundary. Semantic regressions exercise the interactions between these mechanisms. The implementation chapters identify concrete policies and remaining limitations; executable tests are evidence about those policies, not a substitute for their specification.

The composition case study provides a small but concrete federation slice. Native source coordinates Java fixture services for model observations, validation, capacity checking and evidence. Reusable stages preserve their defining checker capabilities despite competing bindings in the receiving module. Its acceptance cases cover successful and rejected assessments, early failure and a selected foreign operation failing without being replayed. This tests capability flow and composition using controlled participants.

The slice does not yet integrate an industrial model repository or simulator, and it establishes no comparative productivity or performance advantage. The case-study catalog develops the next experiments around explicit baselines, measurable outcomes and failure conditions. Useful findings include cases where an existing tool or direct adapter is simpler. Current measurement infrastructure also supports language implementation experiments, with workload and measurement boundaries documented separately.

Positioning and Reading the Experiment

VarioHyve draws on object languages, capability security, behavioral reflection and explicit operational semantics. Openflexo, Epsilon and CorrLang provide important comparisons for model federation and coordination; Smalltalk and Newspeak inform the language lineage. Work on monitoring and analysis supplies ways to formulate the questions raised by observable execution. The Related Works part explains the relevant connections and differences without treating them as delivered integrations or inherited proofs.

The rest of the book moves from agreement to realization. Specification defines language behavior, including the foreign boundary. Implementation describes the Java bootstrap and its tooling. Future records extension principles, proposals and unresolved work. Related Works situates the experiment, and the Appendix gives the formal rules. This opening Motivation supplies the questions behind those parts: can explicit capabilities and preserved semantic boundaries make coordination easier to understand, and can explicit execution make its behavior easier to investigate?

Program Structure

Operational definition: SOS entry rules.

A Program Is a Single Expression

The grammar entry is top: expression? EOF. Empty input is an empty expression; normal expression evaluation returns canonical null. A named or anonymous class literal can instead serve as a module. Naming it retains declaration metadata without creating an ambient binding. Module instantiation requires a class literal and rejects empty input or other expression forms without executing them.

The introductory Assessment example is such a module. Its instantiation service supplies the three existing objects modelSource, checker and evidenceSink; a caller later sends assess(item). These selectors are application contracts, not built-in services.

Sources of an Object’s Capabilities

An object’s behavior can access capabilities through inherited behavior, mixin contributions, lexical nesting and explicitly supplied inputs. Inputs include constructor arguments during initialization and arguments to later messages. Further capabilities may become available through message results.

These routes do not change lookup order. Contributions retain their definition scopes; calling a class from another scope does not supply the caller’s bindings.

Constructor parameters are available only during initialization. Retaining these inputs for later use requires slots or deliberate captures, as specified by the definition-scope rules. These rules apply equally to native and foreign capabilities.

A capability can be a native object, including a class with factory behavior, or an Alien. Its offered behavior may return further objects or create new ones. Authority therefore includes behavior and captured scopes, not merely objects present in an initial heap. Nesting shares enclosing capabilities; it is not an isolation boundary.

Top-Level Classes and Instantiation

Normal module definition evaluates the class over a fresh empty top activation. The execution frame exists, but has no capability accessors, lexical parent, receiver or enclosing application scope. The class inherits only from structural root Object and composes no mixins. This structural relationship supplies neither an Object binding nor a platform namespace. Every explicit top-level superclass or mixin clause is rejected before its expressions execute, including a clause spelled Object.

At entry, the module’s declared constructor arguments are its only external capability inputs. Zero, one or multiple arguments are allowed, with exact arity. The service passes existing objects, preserving identity and sharing through the ordinary boundary. It does not lend the module its own scope, registry or other services. Supplied objects retain their capabilities and captures; later explicit message arguments are additional inputs.

Class definition precedes construction, so constructor arguments cannot provide that top-level class’s superclass or mixins. They can be stored and used when realizing nested classes:

class Module(baseClass, loggingMixin) {
    Base = baseClass;
    Logging = loggingMixin;
    class Worker(identifier) <: Logging < Base { id = identifier; }
}

The host receives the constructed module instance and explicitly chooses any entry message. Instantiation does not guess or send main or run. Construction failure does not return a successful instance; effects already performed are not rolled back, and an initializer may deliberately share self.

The Kernel Parameter

A kernel is an optional ordinary bundle, not a reserved name, mandatory parameter or global lookup mechanism. Services may be separate inputs or grouped in native/Alien bundles. Passing a narrow object does not remove authority already retained by its methods, enclosing scopes or composed contributions.

Optional Bootstrap Bundle

A platform may bundle canonical values, libraries and I/O capabilities. Bundle inventory and the behavior of its selectors are platform contracts. Source names such as null, true and false select behavior through ordinary lookup; their spelling establishes no canonical identity. See names and contracts. The current tooling bundle is described in the Java implementation.

Bootstrap Conformance Requirements

Definition, construction and synchronous callbacks share the requested execution budget. Host sends supply an empty caller activation; the target’s definition supplies its lexical scope. The concrete APIs and validation are documented under module entry and in the implemented entry decision.

Development and Debugging Contexts

Richer tool evaluation contexts are distinct from normal module entry. A class created with tooling authority retains those captures and cannot silently be treated as an isolated module.

Error Handling

Current execution failures abort their native continuation; they are not catchable language values. A failed FN callback reports its diagnostic to foreign code, which may handle it and complete the enclosing NF call normally. Missing dispatch does not invoke a language-level doesNotUnderstand handler. Uninitialized reads, unresolved holes, invalid contributors and invalid returns also fail explicitly; return rules specify dead homes, initializer completion and callback barriers. Public diagnostics expose neither raw activation addresses nor host exceptions. The boundary preserves its defined failure kinds. Conditions and restarts remain proposed work.

Literals

The literal forms are numbers, strings, holes, lambdas, classes and objects. Class and object syntax is defined in Objects and Classes; this chapter owns scalar syntax, closure returns and initializer completion.

null, true and false are ordinary source names, not literal forms. Their occurrences are message sends under name resolution. Canonical null for omitted initializers or empty bodies is supplied directly by the language; it does not depend on a declaration named null.

Hole Literals

? is an explicit incomplete expression, valid wherever an expression is expected. It has its own AST node and differs from both an omitted initializer and canonical null. A missing initializer supplies null; a hole remains unresolved.

Descriptors on Holes

Use parenthesized descriptor syntax, for example (? : expected(Controller) : reason("integration input")). Descriptors can inform diagnostics or a separately selected analysis tool; they do not silently change raw execution.

Runtime Semantics

A hole supplies no normal value by itself. Reaching it must invoke the execution context’s explicit hole policy. The concrete bootstrap reports UnresolvedHole. Interactive suspension, externally supplied replacements, abstract values, branching and synthesis are possible richer tooling policies, not implemented guarantees. Their interpretation must be specified by that context; accepting partial syntax does not imply an abstract interpreter.

Hole Identity

Each syntactic occurrence denotes a distinct hole. Tools should retain a stable internal identity, normally based on AST/source identity, for diagnostics, annotations, filling, traces or replay. A descriptor-supplied name or qualified source path may identify a hole to a tool. Two occurrences of ? do not become one hole merely because their spelling is equal.

Lambda Literals

fun and λ introduce lambdas. Parentheses around the parameter list are optional when it is empty. Bodies are semicolon-separated statement lists; an empty body and a trailing semicolon are allowed.

fun { 42 }
fun(x) { x.plus(1) }
λ(x, y) { x.plus(y) }

A lambda captures its evaluation scope, current receiver, contribution origin and lexical return home. It does not capture its later caller’s scope. Captured activation data can outlive the creating invocation. A lambda supplies exact apply/N at its declared parameter count; binding invocation uses the ordinary eligibility rules. Optional descriptors follow the closing brace.

A lambda is a native object with its own identity and the inherited root Object protocol. Distinct evaluations create distinct objects. Object-method sends use the lambda as receiver; its apply/N body instead uses the captured receiver and return home. Inheritance neither changes lexical self nor exposes captures. There is no public Lambda factory or ambient Lambda binding; the private representation is described in Core Structures.

Implicit Return

Methods and lambdas return their final expression’s value on normal completion. An empty body returns canonical null. This normal result returns from the current invocation; it does not perform a non-local return.

Early Return with ^

^ expression first evaluates its operand, then returns to the lexically enclosing method or initializer home. Lambda invocation creates no new home.

Creation contextTarget of ^
Method body or a lambda created thereThat method invocation
Initializer or a lambda created thereThat initializer contribution invocation
Supplied outside lambdaIts original home, even when called during construction

A missing or retired home causes a dead-context error. Captured data does not preserve return authority. A return crossing foreign execution is governed by the boundary agreement. The default agreement requires a live home reachable without crossing an active Alien callback barrier; supporting agreements must preserve these native home and initializer rules. Successful unwinding retires intervening invocation homes. Operand failure propagates as failure rather than completing a return.

Class expressions retain definition-time bindings, but each later initializer invocation creates a fresh home. An outside lambda can unwind construction to its own live accessible home; it is never rebound to the initializer.

Class Literals

The class keyword creates a named or anonymous class value. See class literal syntax and the distinction between member declarations and class expressions.

Object Literals

{ body }, optionally prefixed by mixin and superclass clauses such as <: M(p) < S(q) { body }, realizes a fresh anonymous zero-parameter class and immediately sends its primary new/0. It has no constructor parameter list or factories; contributor arguments and initialization follow the class rules. See object literals.

Initializer completion

A class or object body may end with | and an optional ordinary statement list. This section executes after that contribution’s ordered slot initializers:

class Config(input) {
    saved = input;
    value { saved }
    |
    ^ "done"
}

Primary construction returns the allocated receiver, not "done". No member, method, factory or slot declarations follow the delimiter; ordinary statements, including var and class expressions, are allowed. An empty | section is valid.

Descriptor lists also use |. Terminate a preceding described member, method or factory with ; to separate post-slot code: value { saved } : Tag; | performWork.

Each contribution invocation has a fresh private return home:

  • Slot phase: returning to that home is an error, including during the final slot expression. The phase ends only after its final value is written.
  • Post-slot phase: normal completion or ^ value completes that contribution and ignores the value. Subsequent contributions still run.
  • Every exit: normal completion, early return, failure and unwinding retire the home. Escaped data remain usable without retaining return authority.

Constructor parameters are visible in both initialization phases, under the construction scope rules. An outside lambda retains its original home. The default Alien callback barrier remains in force; any future crossing support must preserve these initializer phase restrictions. Failures neither replay initialization nor roll back effects or retract an escaped receiver. See the accepted policy.

Objects and Classes

This chapter defines class and object literals, member declarations, composition, and factories. Name Resolution defines lexical receivers; Message Sends defines invocation; Literals defines initializer completion and returns. Backend records belong to Runtime Object Representation.

Operational definition: SOS class and construction rules.

Top and the Class Algebra

Top is the empty constructor of the mixin–class algebra. At the level of instance-side composition, the inductive structure is:

ClassShape ::= Top | Apply(Mixin, ClassShape)
Object       = Apply(ObjectMixin, Top)

Like zero in an inductive definition of natural numbers, Top supplies the base case. Every nonempty class shape is a mixin applied to another shape, so even Object follows the same construction rule. Apply here is mathematical composition, not the source apply selector or a factory invocation.

Top contributes no methods, slots, member declarations, definition scope, capabilities or initialization. Lookup ends there with a miss and its layout is empty. Only Object has Top as its direct superclass; other native class chains reach it through Object. The owned Object mixin supplies the root protocol below. Thus adding the empty base does not remove that protocol or change the capabilities available through it.

The algebra describes composition structure, not class identity. A realized class retains its owned contribution, ordered direct applications, superclass, routes and metaclass. Expanding its shape neither manufactures intermediate class objects nor erases contribution scopes or occurrence identities. The formal rules give this projection precisely.

Top is a distinguished semantic base, not an instantiable class or a language-visible value in the current contract. It has no metaclass, factory, owned mixin to import, or public mirror reference. The class/metaclass rules below apply to realized classes. No built-in Top binding or new reserved name is introduced, and omitted superclass clauses still select Object. The empty top activation for module entry is a separate execution frame. Aliens acquire no native hierarchy through this definition.

The VM may represent the terminal case without allocating an object: the implementation refinement states the mapping and the conditions for reconsidering runtime reification.

Object Literals

objectLiteral    : mixinApplications superclassApplication
                   LB objectBodyElement* initializerBody? RB (COLON descriptorList)* ;
objectBodyElement: namedClassLiteral SEMICOLON? | methodDecl SEMICOLON?
                | slotDecl SEMICOLON ;

An object literal has no constructor parameter list or factories. Its optional mixin and superclass clauses have the same syntax, order and meaning as class clauses: mixins precede the superclass; <:/with and </extends are synonyms. Omitting the superclass selects structural root Object, without name lookup. Slot declarations still require their terminating semicolon.

<: M1(p1), M2(p2) < S(p3) { x = 5; }
< S(p) { x = 5; }
with M(p) { x = 5; }

Each evaluation realizes a fresh anonymous zero-parameter class, then immediately sends its generated primary new/0 using ordinary exact message dispatch. Thus <: M(p) < S(q) { body } is equivalent to (class <: M(p) < S(q) { body }).new, with a factory-free body. Successful evaluation returns the initialized object. Repeated evaluation creates distinct class, metaclass and instance identities; it does not cache a singleton. Contributor factories and custom apply methods are not called or imported.

All constructor-clause rules apply. Targets resolve left-to-right for direct mixins, then the superclass, in the literal’s evaluation scope before allocation. Routed arguments run later in its own initializer activation, immediately before their contribution is initialized. In particular, self in a target computation denotes the enclosing receiver, while self in a routed argument denotes the new object. Ordinary initializer lookup also applies: an own slot can shadow an enclosing name and is still uninitialized during routing. For example, < S(x) { x = 5; } cannot use its own pending x as an argument; use a distinct captured binding or a qualified outer receiver when that is intended.

The anonymous class captures the literal’s evaluation scope, including deliberate creation inside another initializer. Contributors retain their own definition scopes and initializer-only constructor parameters; parameters are not added to instance-method bindings. Each contribution keeps its normal initialization order, occurrence, storage rules and private return home. Anonymous objects introduce no new outer qualifier.

An object literal remains an expression, not a valid normal module entry. Nested literals may use explicitly supplied module inputs, under the existing module restrictions.

Zero-Parameter Classes vs Singletons

For class Config { debug = false; }, Config() invokes its apply/0 factory; Config.new and Config.new() each perform primary construction once. For config = { debug = false; };, the slot already holds the initialized object. See zero-arity invocation.

Root Object Protocol

In the current runtime seed, native objects, including lambdas, inherit these ordinary methods from root Object:

equals(other) { _vm.same(self, other) }
hash { _vm.identityHash(self) }
toString { "an Object" }

These are normative defaults of this seed. Another seed may choose different root methods without changing lookup, invocation or boundary laws. Replacing an application kernel does not replace the structural root; selecting another seed is not a current runtime API.

Root Object does not supply same or identityHash. Reliable identity and classification observations belong to an explicitly supplied IdentityMirror capability. The mirror observes subjects without invoking their methods. Defining these selector names on an application object cannot intercept mirror observations or the root defaults’ direct use of _vm; no selector is thereby reserved on Aliens.

equals defaults to native identity equality, including identity recovered from an owned Expat. Canonical null and Booleans participate with their native identities. The default hash returns an integer stable for the identity’s lifetime; equal identities have equal hashes, but collisions are permitted. Hashes are neither addresses nor persistent identifiers across runtime sessions.

equals, hash and toString remain overridable. Equality overrides should define a reflexive, symmetric, transitive relation with compatible hashes. The defaults provide identity-derived results without a separately supplied mirror; the mirror grants observation independent of subject behavior.

The default toString returns exactly "an Object". It reveals neither a class name nor an instance or class identity hash. Named and anonymous instances, class objects, metaclasses and lambdas retain this generic answer unless they override it. Canonical values keep their explicit null, true and false overrides. Diagnostic detail is therefore chosen by the object’s own protocol.

_vm is a narrow seed capability in Object’s detached definition scope, not an inherited slot, ambient module binding or accessor for IdentityMirror. Its operations cross the normal Alien/Expat boundary and expose no backend representation. Aliens retain their own protocols and do not acquire these methods by inheritance. Scalar Object behavior and identity remain subject to the scalar design decision.

Capabilities and Definition Scope

The capability sources do not change definition scope: calling a class does not capture its caller’s scope. Named and anonymous classes follow the same rule. Examples with custom contributors or enclosing bindings assume an appropriate enclosing context; isolated modules and tooling evaluation have distinct entry contracts.

Constructor parameters are immutable bindings available only during initialization. Methods cannot resolve their own constructor arguments, even when called during initialization. Store persistent dependencies in slots. Lambdas and class expressions deliberately evaluated in an initializer may capture its parameters. Each contribution receives its own argument bindings; composition does not replace its captured definition dependencies.

Member Declarations and Class Expressions

A named class in body-declaration position declares a member class:

class Container(input) {
    value = input;
    class Member { read { value } }
    Captured = class { read { input } };
    NamedCapture = class Snapshot { read { input } };
}

Member binds to the enclosing receiver and its declaration/application origin. Its zero-argument accessor lazily realizes and caches one class per enclosing receiver and declaration occurrence. Repeated access returns that identity; different enclosing receivers obtain distinct classes. The member can use stored value, but cannot acquire Container’s constructor binding input. Members are available regardless of their position among slot initializers.

Captured and NamedCapture are slots initialized by class expressions. Both capture the evaluation scope, including input. An expression’s optional name is declaration metadata, not a binding introduced in the surrounding body. Anonymous forms occur only as expressions; named forms can be expressions or member declarations. Lowering must preserve this distinction.

Member and slot names share a namespace; duplicates in one body are errors. A member also conflicts with a zero-argument method of the same name and has no setter. A stored class is callable through its current value; a member advertises the selected declaration’s constructor and owned factory apply arities before realization. Wrong-arity invocation evaluates no contributor targets. Selected realization failures, including cycles or abandonment during non-local return, are cached without replay. See member invocation for selection and overriding.

Initializer Bodies

The optional final | section executes after the contribution’s ordered slots. Constructor parameters remain available. No member, method, slot or factory declarations follow the delimiter; ordinary statements, including local var and class expressions, may occur there. Its ordinary result or permitted early-return value is ignored. The complete phase, home-lifetime and failure rules are in Initializer completion.

Inheritance

< Base(args) selects a native class and inherits its complete instance-side chain: owned contribution, applied mixins and ancestors. Omitting the clause uses structural root Object, without looking up the name Object. An instance or Alien is not a class target; no implicit instance.class conversion occurs. Native super cannot be a contributor target.

Construction runs the superclass’s complete initializer schedule on the newly allocated receiver. Inheritance imports no factories; factories belong to the declaring class.

Mixins

<: A(args), B(args) applies the owned reified contribution of each selected native class: directly declared methods, slots, member classes, constructor formals and own initializer. It imports no source superclass, applied mixins, factories or argument routes. The definition scope remains captured. Resolving the source class itself still realizes its targets normally; applying its owned contribution does not evaluate those original constructor argument routes.

For example, if A <: M1, M2 < S1, B <: M3, M4 < S2, and C <: A < B, the contribution order is:

own(C), own(A), own(B), own(M3), own(M4), then the complete S2 chain

own(X) means X’s owned contribution. No intermediate classes are introduced. Repeated applications share the reified definition but have distinct application occurrences and initializer invocations. A contributed method’s super resumes from its application occurrence; see Name Resolution. Public mixin extraction and reflection are not part of the current language.

Constructor Clauses

The terminal application in a superclass or mixin clause has construction semantics. It selects a contributor during class realization and retains the argument expressions for each later construction; it does not call a factory. Bare targets route zero arguments, and parentheses around the whole clause do not change its meaning.

Computed Contributor Targets

For < registry.choose(kind).Base(x), realization evaluates registry.choose(kind) and reads Base; construction later evaluates x. Receiver subexpressions perform ordinary computations. Direct mixin targets run left-to-right, then the superclass target. Their choices are fixed for the realized class. This applies to class expressions and cached member classes.

Construction Order

For class C(x) <: A(a), B(b) < S(s) { ... }, successful primary construction:

  1. Allocates one receiver with fresh uninitialized storage for its complete layout.
  2. Evaluates s and runs S’s complete initialization schedule on that receiver.
  3. Evaluates b and runs B’s owned initializer, then does the same for a and A.
  4. Runs C’s own ordered slots and final body, then returns the allocated receiver.

Each argument list is evaluated once, left-to-right, immediately before its private target invocation. Argument expressions run in the declaring contribution’s initializer activation, with its constructor parameters bound. Superclass and applied-mixin calls receive their own bindings and fresh homes. The declaring routes and owned body share one logical home, established before routing begins. Routing precedes slot completion, so returning to that home from a route cannot finish construction early. Each contribution completes its slots and final body before the next contribution runs.

These calls are private identity-bound routines, never selectors named initialize or public operations on arbitrary receivers. Initializer writes bypass overridable setters. No component instances are allocated, no effects are replayed or rolled back, and escaped partial receivers are not retracted. Return and failure handling follows Initializer completion.

Ordered Overrides and Shared State

Own declarations have precedence, followed by direct mixins left-to-right, then the superclass recursively. At each contribution, selector/accessor choice follows Message Sends. A member override selects the whole declaration and its origin; it does not merge nested families automatically. Duplicate slots, members or exact method selectors within one body remain errors; an explicit method may override a generated slot accessor.

Every slot retains its logical identity (applying class, occurrence, local slot). Same-named contributions share storage. Initialization runs in the reverse contribution order above, so later writes replace earlier values. Every occurrence still initializes, including repeated applications. Surviving methods may therefore observe shared state; this policy does not promise independent stateful mixins. Getter/setter eligibility and mutability belong to the selected declaration, even when storage is shared. Renaming, explicit state mapping and deep family composition require future rules.

Factories

A factory method is sent to the class object; an ordinary method is sent to its instances. Both use ordinary method invocation and lexical scope.

The Primary Factory (new)

Every source class and root Object has a generated, non-overridable primary new/N, where N is its constructor arity. Successful invocation allocates a fresh receiver, executes the complete construction schedule and returns that receiver. Its selector uses ordinary lookup; only its generated body contains private construction operations. Object literals automatically send this primary new/0 to their newly realized anonymous class.

factory new is forbidden. An ordinary instance method named new is allowed. This restriction preserves a primary entry that guarantees fresh allocation and the complete initialization schedule, while apply and named factories retain control over their results. It does not make an arbitrary new send an allocation primitive. Inheriting Object does not add new/0 to a class with parameters, and neither inheritance nor mixin application imports contributor factories.

The Callable Protocol (apply)

At constructor arity N, the default apply/N makes an exact self.new/N send. An owned factory apply at N replaces that default; factories at other arities coexist with it. A custom factory controls its result and causes no automatic allocation or initialization. It may call new, return a cached instance, or return another value.

class Point(xInput, yInput) {
    x = xInput;
    y = yInput;
    factory apply() { new(0, 0) }
    factory copy(point) { new(point.x, point.y) }
}

Point(2, 3) uses default apply/2; Point() uses the custom apply/0; Point.new(2, 3) performs primary construction directly. General callable selection belongs to Message Sends.

Named Factory Methods (factory)

Named factories such as Point.copy(p) are ordinary class-side methods with full result control. In a factory, self is the class object; lexical sends and qualified outer use the factory’s declaration origin and the class’s definition scope. A factory on a member class can therefore access its bound enclosing receiver. Invoking it does not capture the caller or instantiation service.

Slots and Accessors

Slots hold object state and expose it through generated accessor messages.

Operational definition: SOS accessor rules.

Slot Declaration

class Point(a, b) {
    x = a;
    y = b;
    label;
}

A slot declaration ends with ;. Its = introduces initialization, whereas expression assignment invokes a setter. An omitted initializer supplies canonical null; storage awaiting its initializer is uninitialized, and reading it is an error.

Contribution Slots and Storage

Each contributed slot retains its application occurrence and local position. The actual receiver’s complete layout maps these logical identities to storage. The current policy shares one location among same-named slots, while preserving their separate initializers and effects. A selected accessor uses its own logical identity in that layout.

Declaration initialization writes through this mapping without calling an overridable setter. Later initializer writes to shared storage replace earlier ones. Sharing and construction order are specified in Objects and Classes; explicit sharing policies and contribution-private access remain deferred.

The apply Protocol and Callable Objects

Generated getters may supply invocation through their returned value. Eligibility, exact arity, zero-argument behavior and retained selection evidence are defined by Message Sends; the Apply guide introduces callable values.

Setter Return Value

A generated setter returns the new value, not self. Consequently p.x!(2).y!(3) sends y!/1 to 2. Use p..x!(2)..y!(3) to keep both messages on p. A custom setter returns its body result; assignment syntax does not force it to return the argument or perform a storage write.

Shadowing Accessors

An explicit method with the same selector overrides a generated accessor. Generated-accessor invocation eligibility then follows the masking rule.

Calling x!(v) inside a custom x!/1 dispatches normally, potentially back to that method; it does not expose the overridden storage primitive. There is no public raw-slot operation. Use a distinct backing slot when needed:

{
    _x = 0;
    x { _x }
    x!(v) { validate(v); _x!(v) }
}

The underscore is only a naming convention, not access control.

var Locals

var count = 0; declares a mutable local with getter/setter messages on a backend-private activation object. All locals in a source scope are reserved before its initializers run. A reference to a later local therefore selects that local and fails if it is still uninitialized; it does not fall through to an outer name. This supports mutual recursion when the lambdas run after their bindings are initialized.

Parameter Immutability

Parameters have immutable getter accessors and no synthesized setter. A request for parameter! therefore cannot mutate the parameter; ordinary lookup may find another applicable setter or fail. Use a var local for a mutable copy. Constructor-parameter lifetime is specified with construction scopes.

The ! Convention

! suffixes are allowed only on method/message selectors, including repeated suffixes. Slot, parameter and local names are plain identifiers. A slot x thus generates unambiguous selector x!.

The suffix convention signals mutation or effects; it is not a static effect system. A plain-named slot may hold an effectful lambda, and invoking that lambda need not display ! at the call site. An explicit forwarding method such as commit!(v) { callback(v) } can communicate that intent. User-defined bang methods need not be setters.

Descriptors on Slots

Descriptors may annotate slots and locals. They do not change raw accessor behavior or make a slot immutable.

A selector is a name/arity pair. Ordinary access, invocation and assignment all send messages; there is no public direct field access or separate binding namespace. Receiver origins are defined in Name Resolution.

Arithmetic and comparisons use messages. Consequently 3.plus(4).times(2) groups as (3.plus(4)).times(2); use 3.plus(4.times(2)) for the other grouping. General operator syntax is deferred.

Dispatch Rules

The following rules own invocation selection for methods, generated accessors, lambdas, native callable objects and member factories. Invocation preserves the selected behavior’s receiver, declaration origin, lexical captures and return home. Parameters and locals expose generated accessors on private activation objects; direct backend reads may implement these messages.

Candidate Selection

For name/N, examine each searched hierarchy contribution in order: owned contribution, direct mixins left-to-right, then the superclass recursively.

  1. Prefer an exact operation name/N. At N = 0, a generated getter goes through the next rule instead of satisfying invocation by returning a value.
  2. Otherwise consider the effective generated name/0 accessor. A storage accessor qualifies when its value supplies exactly apply/N. A member accessor qualifies through its effective declaration’s factory signatures.
  3. Continue only on a miss. Exhausting the search produces a missing-selector diagnostic.

Exact-operation preference is local to each contribution: a nearer eligible accessor can beat a farther method. super starts after the executing contribution’s exact occurrence.

Getter masking. The first name/0 operation masks later getters in that hierarchy search, even when its candidate is ineligible. An ordinary overriding getter is never executed to discover a callable, and its hidden storage is never inspected. Later exact name/N methods can still match. A super search starts masking afresh at its redirected origin.

Callable capability. Native values qualify through an exact apply/N method, including inherited methods, or a lambda’s declared arity. A stored apply accessor does not recursively make its containing object callable. A stored Alien can qualify through effect-free boundary selection of apply/N, including ForeignCallable. An explicit Alien receiver instead selects the requested foreign name/arity directly: no foreign getter is probed for a callable result.

Implicit invocation. First perform declaration-relative receiver selection, using these same candidates. Then dispatch the original invocation on that selected receiver. Method and eligible-accessor overrides both participate. Eligibility does not freeze the implementation, and final dispatch failure does not resume lexical search.

Evidence and failures. Retain an eligible accessor’s value and selected callable operation through final dispatch. Revisiting the same candidate reuses them without rereading storage or resolving a foreign operation. Changing a stored value can change eligibility for a later invocation.

Member-Class Invocation

A generated member accessor advertises its effective declaration’s constructor arity and owned factory apply arities. An overriding declaration supplies its own signatures. Flat metaclasses import no contributor factories, so candidate testing needs neither contributor lookup nor class realization.

class Widget(x, y) { factory apply(x) { new(x, x) } } supplies invocation arities one and two. Widget() is a miss without evaluating definition clauses, whether its cache is empty, successful or failed.

Metadata eligibility first selects the lexical receiver. If final dispatch chooses an overriding method, the member remains unrealized, even if its cache already holds a failure. When dispatch selects the member factory, commit to that candidate, realize it through its receiver-and-declaration-occurrence cache, then invoke exact apply/N with the saved arguments. Bare access also realizes through that cache. A selected failure is cached and propagated.

Realization evaluates direct mixin targets left-to-right, then the superclass target; their computations may have effects and must produce native classes, excluding metaclasses. Terminal constructor arguments remain deferred until construction. See class realization and the accepted decision.

Cascade (..)

A cascade evaluates its receiver once and sends every arm to that saved receiver. Arms execute left-to-right; each arm’s arguments execute immediately before its send. Preserve each arm’s exact-access versus invocation mode and any setter sugar:

p..x!(2)..y!(3)..describe

The intermediate results are discarded. By contrast, p.x!(2).y!(3) sends y!/1 to the result of x!/1, which is 2 for a generated setter. A failed arm or non-local return prevents later arms and their arguments from running. Earlier effects are neither undone nor replayed.

Lowering uses a fresh private temporary and ordinary sends; it must preserve captures and return homes without exposing the temporary scope to programs.

Cascade Return Value

The whole cascade returns its last arm’s result, not necessarily the receiver. To return an existing receiver, write p..a..b; p.

Implicit-Receiver Cascade (Leading ..)

..m..n means self..m..n and skips lexical receiver selection. m..n..p instead evaluates implicit m first, then sends n and p to its result. Thus a leading cascade and a cascade whose receiver is an implicit send select different receivers.

Apply and Callable Values

apply/N is the callable capability at arity N. A lambda supplies it at its declared arity; a class’s generated apply/N delegates to primary new/N; an ordinary object can define it as a method. Owned custom class factories may replace or add apply arities; see factories.

The language fixes apply/N as the protocol connecting invocation syntax to callable values, so methods and stored callables can participate in the same selection rules. Its implementation and result belong to the selected receiver; the spelling does not imply allocation, lambda execution or any other particular body on an arbitrary object.

{
    handler = fun(request) { request };
    run(request) { handler(request) }
}

Retrieving handler returns the lambda. handler(request) can use the generated getter and invoke its result. Exact methods and accessor routes compete under the selection rules, so invocation is not unconditional getter-then-apply. A computed getter’s result can be called explicitly with object.handler.apply(request).

Bare object.m sends m/0; it does not produce a bound method. For the distinction between f and f(), see zero-argument invocation. Member declarations use deferred factory selection.

Method reification is a future tear-off proposal. No tear-off syntax or public method-reification API is part of the executable language.

Name Resolution

Implicit sends first select a receiver from lexical declarations, then dispatch on that receiver. Lookup is fixed by the language; there is no global environment or platform-selectable lookup policy.

Operational definition: SOS lexical receiver selection.

Names and Contracts

An ordinary name selects behavior through message lookup; its spelling alone does not identify a value, grant authority or impose a protocol. The selected object’s behavior and the contract with its clients give that name meaning. This applies equally to null, true, false, Object, kernel and application selectors such as ifTrue or plus. They introduce no ambient bindings. Parameters, locals, slots and methods may use these names, subject to the ordinary declaration rules. Without an applicable declaration, a send fails under the ordinary lookup rules.

Canonical null and Boolean identities, and structural root Object, are governed by the seed and core-object contracts. Those identities do not reserve source names for obtaining them. An omitted initializer supplies canonical null directly; an explicit initializer null sends null/0 in its lexical context. A name or a matching protocol never establishes canonical identity at the foreign boundary.

The specification explicitly fixes grammar keywords and the receiver forms below. It also fixes the callable selector apply/N, the generated primary factory new/N and the setter selector mapping x!/1. These contracts connect syntax to messages; the selected operations still use ordinary dispatch. They do not give other selectors intrinsic behavior. Seed methods and explicitly supplied foreign/tooling capabilities have their own stated contracts, not meanings inferred from names on arbitrary objects.

Lookup Order

Search the current method/lambda’s parameter and local accessors, then enclosing lexical scope objects from nearest to farthest. An activation contributes its own accessors. A lexical object scope contributes only declarations from its originating contribution, associated with its bound receiver. Arbitrary members added by a subclass do not become lexical declarations.

For an exact send, the nearest scope declaring the selector selects its receiver; exact dispatch then honors overrides on that receiver. For invocation, use the candidate rules:

  1. A declared exact name/N operation qualifies the scope, except that a generated getter at arity zero must establish callable eligibility.
  2. Otherwise, if the scope declares name/0, select its effective getter on the associated receiver. An eligible generated accessor qualifies the scope. At arity zero, an ordinary method overriding that getter also qualifies directly.
  3. A miss continues outward; an eligibility error stops selection.
  4. Once qualified, dispatch the original invocation uniformly on that receiver, retaining successful accessor evidence.
  5. If all lexical scopes miss, dispatch on current self through its owned contribution, direct mixins left-to-right, then superclass chain.

A subclass name/N alone cannot make an ineligible declared getter qualify. Once eligible, that receiver’s overrides apply normally. An operation added on a different inner receiver cannot capture an enclosing dependency.

{
    class Base {
        f = fun(x) { 7 };
        run { f(1) }
    }
    class Child < Base { f(x) { 42 } }
}.Child().run // 42: Base selects the receiver; Child overrides f/1

If Base.f instead holds a non-callable or wrong-arity value, lexical search continues before the final self invocation. Getter masking, failure handling and retained callable evidence are specified once in Message Sends.

Capabilities and declaration scopes

The instantiating caller does not supply a class’s lexical scope. Constructor parameters, member declarations and class expressions obey the construction scope rules. Normal module entry and explicit tooling scopes are distinguished in Program Structure.

self — Current Receiver

self denotes the current native receiver with fixed meaning. It parses as an identifier but is not an ordinary getter; native declarations cannot shadow it. It can be passed as a value and used in chains such as self.x. An explicit native receiver has no self selector. alien.self is instead an ordinary foreign selector with adapter-defined meaning.

Leading-Dot Shorthand for Self

.m(args) equals self.m(args); ..m..n equals self..m..n. Both bypass lexical receiver selection. See cascades.

outer — Qualified Lexical Receiver

outer ClassName selects the ordinary receiver for the nearest matching named lexically enclosing declaration, including the immediately containing class. Subsequent messages dispatch normally on that receiver.

class Counter(start) {
    n = start;
    class Stepper {
        step { outer Counter.n!(outer Counter.n.plus(1)) }
        current { outer Stepper }
    }
}

outer Stepper selects the current Stepper instance. The qualifier is declaration metadata, not a variable, evaluated accessor or dynamic class name. Repeated class names choose the nearest matching declaration. An unrelated subclass or superclass name is not thereby an enclosing qualifier.

Lambdas retain their enclosing declaration context. Named class expressions introduce qualifiers for their bodies; anonymous class expressions and object literals introduce no invented name. They preserve access to enclosing named declarations. Captured parameters and locals remain internal dependencies, not activation objects exposed by outer.

Contributed methods preserve their definition and application origins; applying a mixin elsewhere cannot substitute the receiving class’s outer scope. Member classes also retain their bound receiver and declaration origin. The deeper repeated-parent case is an unresolved documented choice; do not claim complete Newspeak equivalence.

outer C is a standalone receiver value: grouping, passing it as an argument and ordinary sends are allowed. It grants no public parent getter, activation reflection or additional access authority. Bare outer, unqualified outer.message and native object.outer are invalid. alien.outer is an ordinary foreign selector; repeated sends follow that adapter’s protocol.

An unknown or non-enclosing qualifier is a semantic error. The bootstrap validates it when evaluated, before evaluating arguments of a send using that receiver. Static qualifier validation is deferred. Qualifying a normal module’s own declaration can select its instance; it cannot expose the instantiation service, tooling capabilities or empty top activation.

super — Lookup Redirector

super.m(args) retains self and starts lookup immediately after the executing contribution’s exact application occurrence. It continues through later mixins and the superclass chain, preserving the send mode and using fresh getter masking. Repeated applications of one mixin remain distinct; lookup does not restart after the first occurrence of its definition.

super is not a value: standalone use, assignment and super.. are invalid. Its native meaning cannot be overridden. The explicit selector in alien.super belongs to the foreign protocol.

Recursion

Recursion uses ordinary late-bound messages and lexical captures; it requires no special recursive declaration form. It remains subject to normal selection, including overrides and callable eligibility.

Named Method Recursion

A method can send its own selector or another method’s selector. Declarations are available regardless of textual order, enabling mutual recursion. Use self.m(...) when current-receiver dispatch is intended; implicit m(...) still performs lexical receiver selection.

Slot-Bound Lambda Recursion

A stored lambda can refer to the accessor holding it:

{
    fact = fun(n) {
        n.eq(0).ifTrue(fun { 1 }, fun { n.times(fact(n.minus(1))) })
    };
}

Its body resolves fact when invoked, after the slot is initialized. Arithmetic and branching here assume suitable capabilities. Normal expression results return through recursive invocations. A ^ would target the creating initializer, normally already retired; see return homes.

Local Lambda Recursion

A var local can similarly hold a recursive lambda. Its accessor belongs to the captured activation. A lambda’s caller supplies no replacement lexical scope or implicit self-name.

Mutual Recursion

All locals in a source scope are reserved before initialization. Lambdas may therefore capture references to later local declarations, provided they run after those bindings are initialized. Reading a reserved but uninitialized local is an error, not an outer lookup. See locals.

Passing Recursive Lambdas as Arguments

Passing or returning a recursive lambda preserves its captured accessors. The caller’s parameter name does not become visible in the lambda body. Captured data may survive the defining method, but its return home does not: ordinary results remain valid, while ^ to a retired home fails.

For name-based recursion, place the lambda in a captured slot or local. An unbound anonymous lambda has no automatically provided name for itself.

Tail-Call Optimization

The prototype uses explicit continuations for native execution but does not implement tail-call elimination. This is not a bounded-memory guarantee. Foreign callback depth and other execution limits are separate; see implementation and future TCO.

Foreign Semantic Values and the Alien/Expat Boundary

Foreign systems retain their semantics and execution mechanisms. An Alien makes a foreign value reachable inside VarioHyve; it supplies no native class, mixins or lexical outer. An Expat exposes native behavior to a foreign participant. Arguments, results, identity, failures and callbacks obey the same boundary contract in both directions, including language-visible VM services. Native lookup and receiver-origin semantics remain fixed.

The chapter follows values through selection, conversion and control transfer, then defines the VM-service and mirror capabilities. Operational rules are in the formal appendix.

Aliens — Foreign Semantic Values Inside VarioHyve

An Alien may denote an object, function, pointer, struct, resource handle, simulator model or remote endpoint. It need not support direct operations. Storing it in a slot does not make that slot’s owner its lexical outer.

Alien Dispatch

After receiver and argument evaluation, an Alien send selects the adapter’s exact (name, arity) operation. Native class/mixin lookup does not continue through the Alien. Selection must distinguish absence from failure, perform no operation or callback, and retain the selected operation for execution. A resolution or execution failure never restarts lookup or replays effects.

A foreign getter is not a generated native accessor: alien.f(args) does not read f/0 to discover a callable. Write alien.f.apply(args) for that behavior. A stored Alien can qualify for native callable-binding invocation when its adapter advertises exact apply/N; the eligibility check’s selected operation is reused. See Message sends.

Explicit Alien selectors self, outer and super use the foreign protocol. They do not navigate native scope. Native self, qualified outer ClassName and super.message keep their receiver-origin meanings; native declarations do not acquire those reserved selector names through this exception.

Arity Mismatch

An adapter defines how name/arity requests map to foreign behavior. Foreign methods, explicit capability operations and opaque handles need not share one object model. Overloads, defaults, ABI layout and lifetime are adapter concerns; automatic host reflection is not implied.

Alien Identity

Each adapter defines identity and lifetime for its foreign domain and preserves sharing on repeated compatible crossings. Numeric address equality alone is insufficient for pointer identity, provenance or reused allocations. Alienation does not synthesize an eq method. Concrete Java identity caching is an implementation policy, not a universal foreign identity law or an implemented C FFI.

Expats — VarioHyve Objects Outside VarioHyve

An Expat reenters native semantics through a behavioral interface. Its public contract exposes no store, address, activation, private initializer or VM representation. Adapters may privately retain what execution requires. The current exact-send interface, VHExpat.send, includes zero-argument access; it does not apply source invocation’s callable-binding fallback. To use a stored callable, read the binding and send apply/N to the result explicitly.

Expat Surface

Without language access control, an Expat exposes the same source-visible behavior available to an external native caller, including generated accessors. Backend-private construction routines are not selectors. Proposed export control must preserve equality of the native external interface and the foreign export interface.

Expat Identity

A native object has at most one Expat proxy per compatible foreign runtime. Exporting it repeatedly through different paths returns the same proxy.

Primitive Marshalling

Numbers, strings, booleans and null may cross by value instead of through proxies. Each adapter must state its supported domains and reject unsupported conversions. A numeric encoding must not silently turn a pointer into an integer while claiming to preserve its provenance.

Canonical null and Booleans are ordinary native objects with language methods. Their Java boundary representations are exactly null, Boolean.TRUE and Boolean.FALSE, never Expats. Incoming scalars recover the corresponding canonical native identities, equally for arguments, results and callbacks. Conversion recognizes those identities; it never invokes toString, isNull, not or a truth-testing protocol to classify another native object. Similar behavior or a source name such as null, true or false does not make an object canonical. The internal core null constant and empty expressions select canonical null directly; those source names use ordinary message lookup. The current integer/string subset is recorded in the implementation.

Explicit Wrappers

A native wrapper supplies its own identity, scope and behavior around foreign values. Multiple wrappers may share one Alien without sharing native identity. For example, a callable capability can operate on an opaque handle:

    handle = deviceHandle;

This is explicit adaptation, not a built-in calling convention. Persistent dependencies use slots under the ordinary constructor-scope rules.

Constructor Arguments and Optional Bundles

Aliens, native objects and bundles can be ordinary module constructor inputs. The same conversion contract applies in richer tooling contexts; it does not add capabilities to an isolated module root.

Control and Failure Agreements

Error Propagation

Selector absence is distinct from a selected operation’s failure. Failures cross as defined diagnostics, never as retained host exception objects, classes or causes. The Java categories FOREIGN_FAILURE, CONVERSION, OWNERSHIP and EXECUTION_POLICY survive machine execution and callback propagation; native lookup/control errors use LANGUAGE_FAILURE.

Callbacks use ordinary native semantics and preserve state changes. A failed callback aborts its own native continuation, retires its invocation homes and reports a defined diagnostic to its foreign caller. It does not automatically fail the suspended native caller. Foreign code may handle the diagnostic, make further callbacks and return normally, or propagate a failure. The outer NF send observes the foreign operation’s completion, subject to normal result conversion and execution limits. A propagated diagnostic preserves its kind; a later foreign failure is reported as that failure, not replaced by an earlier handled one.

Effects already performed are not rolled back. Handling a callback failure does not resume the aborted callback, revive its homes, replay the operation or grant NLR crossing. The suspended caller’s homes remain live until its own completion or failure. Callbacks continue to share the active execution budget; handling an exhaustion diagnostic does not replenish it. There are no native resumable conditions in the current language. See the accepted recovery agreement.

Non-local Returns Across the Boundary

The boundary is the agreement between native and foreign participants. That agreement owns whether a non-local return may cross a foreign invocation and how the crossing is handled. The native language cannot prescribe how arbitrary foreign execution unwinds or otherwise transfers control.

The default agreement forbids crossing. A callback may return to an accessible home created inside that callback; an attempt to reach a live home across an active foreign-call barrier fails with LANGUAGE_FAILURE. The failure is reported to the foreign caller under the recovery agreement above. This is the only crossing agreement implemented by the current Java boundary.

A boundary may explicitly support crossing under a future agreement. It is responsible for implementing that agreement, including its observable control flow and treatment of intervening foreign work; the foreign-side mechanism is not fixed by VarioHyve. Every intervening boundary must support the requested transfer. Such support does not change the lexical target of ^, revive a retired home, or bypass initializer phase restrictions. Crossing support and its transfer protocol are deferred; the default barrier must not be disabled without implementing a supporting agreement. See the accepted decision and examples.

Control Tokens and Execution Agreements

Ordinary native transitions require execution authority under an explicit execution agreement. The current sequential agreement has one conceptual control token per live runtime. It governs advancement of ordinary native continuations and their NF/FN control transfers. A suspended continuation has no independent authority to advance. The token is neither a language value nor an additional capability that programs must pass; implementations need not reify it. A refinement argument must account for the authority using the implementation’s actual synchronization and state.

The token may be idle at the boundary, assigned to a native continuation, or assigned to a foreign invocation. Independent FN entry acquires the existing idle token. NF transfers it to the selected foreign invocation; admitted callback entry transfers it to a new native continuation. Callback success or failure returns it to that invocation; foreign completion transfers it to the suspended native caller only after admitted descendants finish. Independent native completion returns it to the idle boundary. Nested calls retain suspended continuations and interaction state, not additional control tokens. Backend tooling may also yield after a requested step and later reacquire authority to advance its retained successor. Yielding is not native completion and does not retire homes; storing a configuration grants neither execution authority nor a snapshot of the mutable runtime.

This is an execution discipline, not exclusive physical access to all runtime memory. It permits three distinct forms of activity:

ActivityAuthority and correctness obligation
Ordinary evaluation and callbacksExecution authority under the active agreement; preserve continuations, admission and boundary transfers.
Representation maintenance and optimizations, including concurrent GCImplementation refinement of the agreed semantics and observations; no second ordinary native continuation is implied by concurrent implementation work.
Explicit observation or interventionA granted capability with a declared effect and coordination contract; it may intentionally change abstract program state without owning the ordinary control token.

An observation or intervention contract must specify its subjects and scope, permitted effects, consistency and coordination with execution, authority lifetime, and completion/failure behavior. Reading live state requires a defined consistency model. Changing a slot, pausing execution or replacing a continuation requires an explicit intervention contract; it cannot be justified as invisible maintenance. Such authority does not implicitly grant arbitrary evaluation, additional ordinary continuations, NLR crossing, dead-home revival or relaxed initializer rules. Language-visible VM services, debuggers and language monitors remain explicitly supplied Aliens using ordinary boundary sends. No general intervention API is implemented by this agreement. All agreements preserve fixed lookup, identity, return-home lifetime and initializer phase rules. NLR crossing still requires an explicitly supporting boundary agreement.

Implementations may use parallel work, concurrent collectors and boundary optimizations without a global representation lock. They must preserve logical identity, return-home liveness, roots and agreed observations, and coordinate their concrete data structures correctly. An optimization cannot silently replay foreign effects or change their specified ordering. Boundary bookkeeping, such as recording a pending request or an arriving completion, does not itself advance a native continuation.

A richer execution agreement may explicitly authorize simultaneous native transitions, including a model checker’s request to execute proven independent transitions on a parallel VM. It must specify execution authority, shared-state and observation semantics, and applicable independence or synchronization conditions. Token uniqueness is a property of the sequential agreement, not a universal serialization requirement. The accepted extension principle and the remaining implementation work are separated in Concurrency and Parallelism.

Concurrency Boundary

The boundary supports synchronous same-thread callbacks and explicitly call-associated worker callbacks. Native execution remains serial over one runtime/store under the sequential agreement. Each NF invocation suspends and roots its native caller, transfers the conceptual control token, and records its call ancestry. An admitted FN callback acquires that authority, runs a separate native continuation, and shares the active budget. Nested NF calls repeat this protocol.

Foreign code captures a CallbackContext on its own active operation thread and may explicitly pass it to a worker. Its send requires an Expat from the same runtime; the context grants permission to request admission, not receiver authority or possession of the control token. Contexts may be copied among workers; competing requests negotiate access to the unique token. Expats obtained before the NF invocation remain valid targets. Unassociated entry on another thread during an active execution is rejected, as is callback entry during selection. Neither thread identity alone nor possession of an Expat grants admission to an outstanding foreign call.

Only callbacks associated with the innermost active foreign invocation may acquire native execution permission. Other associated requests wait for their turn without running native code. A descendant operation cannot synchronously use an ancestor context to wait on its own completion; that request is rejected. There is no FIFO or fairness guarantee. A future FIFO policy must respect call eligibility: a waiting ancestor request cannot block a needed descendant callback merely because it arrived first. Foreign completion closes admission, rejects queued or late requests and waits for already admitted descendants to finish before importing the result and resuming its native caller. A foreign result can arrive while a callback owns the token; arrival is recorded, and delivery waits for ownership transfer. Retained call contexts cannot attach to a later invocation. This preserves the existing NLR barriers and callback-local failure contract.

This protocol provides no preemption or termination guarantee: foreign work or an admitted descendant may never finish, and foreign dependencies may deadlock. Independent-entry scheduling, detached asynchronous native tasks and parallel native execution remain outside this contract. Execution limits belong to the implementation policy.

Lifecycle and Garbage Collection

Ownership, resource expiry, callback lifetime and cross-boundary cycles belong to each adapter’s contract. No universal reclamation protocol is defined. Public raw addresses are not a substitute for that contract.

Foreign Kinds and Capability Contracts

An adapter may classify a value as callable, pointer, struct or endpoint; these are foreign contracts, not native classes. Analysis needs explicit assumptions about effects, callbacks, blocking, determinism and state changes. Unknown behavior stays opaque. General contract metadata, provenance registries and foreign reflection remain unimplemented; see the boundary assessment.

VM Services and the Trusted Seed

The host boundary has a public foreign facet and a privileged VM-service facet over one private owner. The public facet exposes only the ordinary transport, explicit mirror grant and call-associated callback admission. Trusted seed provisioning supplies narrow VM service capabilities; public clients have no operation for obtaining the provisioning facet or raw runtime representations. Object’s identity service is provisioned only to its definition scope. The optional public IdentityMirror grants its own limited observations.

Both facets share identity maps, conversion, execution admission, budgets and GC roots. Current services use the same serial admission protocol. Privilege changes authority, not lookup, return or failure semantics; privilege alone grants no additional ordinary native execution. A future independently operating service requires an explicit execution or intervention agreement. The same capability view preserves identity across either route. Distinct restricted views have distinct identities even when they concern one resource. Deliberately exporting a privileged capability delegates that capability; a partition label does not silently attenuate it. No new privilege registry, selector allowlist or native invocation path is introduced.

Language-visible VM services use this same boundary; there is no privileged native-function invocation path. The trusted backend may privately allocate values, maintain stores and implement lookup/continuations. Those internal operations are not language services.

A service returning a native object must return its Expat, so import recovers the object. Returning its raw backend representation as a foreign value is invalid. Any future representation-sensitive service requires explicit authority and private unwrapping without adding raw-world access to public Expats. See the VM boundary decision.

Identity and kinds

Identity comparison is reflexive, symmetric and transitive on its supported domain. It observes native identity or adapter-preserved Alien identity, never semantic equality or remote resource equivalence. Compatible round trips preserve identity and hashes; same identities hash equally, but collisions are permitted. Hashes are neither addresses nor stable across sessions. A wrapper and its payload differ; differently restricted handles must not be merged merely because they refer to the same resource. Ownership failures require an explicit bridge.

The supported kind labels are exactly "Object" and "Alien", case sensitive. Object includes native instances, class objects, metaclasses, canonical null and Booleans, and lambdas. Alien includes opaque foreign references and VM services exposed through the adapter. It does not imply callability or trust. Classification is relative to the observing runtime; importing its owned Expat recovers a native object.

Current integer/string codec values belong to neither kind and have no native class or mixin membership. Identity operations on them, including mixed same queries, fail with CONVERSION; interning does not specify scalar identity. Future native or preserved foreign scalars require their own specified contracts. Thus isNative is not implemented as the negation of isAlien. Object’s default equals with a codec scalar still returns false because its receiver is native. An unknown kind label fails with LANGUAGE_FAILURE, a non-string kind label with CONVERSION, and a missing selector/arity follows ordinary lookup failure.

Class and contribution references

The second argument of both membership queries is a native class reference, obtained through ordinary messages or explicit capability provision. For an ordinary class, it is the same definition object usable in superclass and mixin applications. instanceOf uses that class’s identity; applies selects that class’s owned reified mixin, just as <: C does. It does not send an ownedMixin accessor or require a separately exposed mixin token. The query does not resolve a name or consult a class registry. Names and hashes, including old anonymous labels, are not targets.

instanceOf starts at the receiver’s actual class and follows superclasses through root Object, inclusive. It returns at the first matching class identity. It does not treat a mixin application’s source class as a superclass.

applies walks the same linear contribution order used for native dispatch: the class’s owned contribution, its direct applications left to right, then its superclass’s owned contribution and direct applications, continuing through Object inclusive. It returns true at the first match and false after the chain is exhausted. Matching compares the reified contribution’s identity, not its syntax, name or semantic equality. An application contributes only the selected source’s owned mixin; this query does not traverse that source’s superclass or applications. Owned, inherited and repeated contributions are included without collapsing occurrence identities or executing construction routes.

Anonymous and named definitions follow identical identity rules. Distinct class evaluations and distinct per-enclosing-receiver member realizations remain distinct even when they share a declaration or name. Aliases to the same class select the same identity and owned mixin. No identity hash participates in membership, so hash collisions cannot change an answer.

For a class object, queries inspect its metaclass hierarchy and class-side contributions; they never switch to the represented class’s instance hierarchy. The target rule remains the same: C denotes C itself or C’s owned instance-side mixin, not its metaclass’s contribution. In particular, instanceOf(C, C) and applies(C, C) are normally false. If a metaclass reference is explicitly supplied, it can select that metaclass or its owned class-side contribution. This does not add a public class/metaclass getter.

Both arguments undergo ordinary boundary ownership validation. A non-class target, including a string, canonical null, ordinary instance or foreign object, fails with CONVERSION; an unowned class fails with OWNERSHIP. Invalid targets fail even when the subject is an Alien or codec value. With a valid target, Aliens and codec values return false because they have no native membership.

These are structural identity tests, not proofs that a selector is supported or that a contribution’s behavior remains effective after overriding. They do not establish trust in a subclass or authorize its behavior. The design note records the routing and capability tradeoffs.

Explicit Store: The Key Commitment

A VMObject contains a mutable ValueRef[]; a slot holds a reference rather than a separately allocated binding cell. Initialization, setters, caches and home retirement mutate backend objects. Configurations share RuntimeWorld: retaining an earlier configuration does not preserve an earlier store state. Only reachable native entries survive a collection. Definition, construction and synchronous callbacks share one transition budget. It returns an Expat; the host explicitly sends any entry message. Host sends contribute an empty caller scope.

BootstrapRuntime.evaluate is the distinct expression harness, using the assembled kernel as parent and receiver. Its supplied capability context may become part of returned closures/classes. The normative isolation contract is in Program Structure; the richer contexts are described in Tooling.

MinimalRuntimeWorld installs ordinary immutable bundle slots named null, true, false and Object, holding the corresponding seed identities. Additional supplied capabilities cannot replace those slots in this assembler. These are this tooling bundle’s assembly rules, not reserved language names; nearer declarations can shadow its slots through ordinary lexical lookup. Normal modules do not receive these bindings implicitly.

Java Boundary

ForeignBoundary.identityMirror() returns a stable, boundary-owned capability. It is supplied explicitly to modules and observes identity and membership through the ordinary mirror protocol, never a special evaluator dispatch branch. The narrow root Object service shares private identity helpers without exposing the mirror. Current identity hashes use the retained native/Alien representation’s Java identity hash; that algorithm is a backend policy, not a portable identifier.

DefaultJavaBoundary owns the Alien/Expat contract. BootstrapRuntime.boundary() returns a narrow PublicFacet; package-private VmServices provisions the seed identity service. Both delegate to the same private owner. It uses a Java identity cache for Aliens and a per-native-identity Expat cache, both retaining strong references, which are roots for native collection and implement the specified identity round trips.

Integer/string interning is a non-owning native cache: collection removes cache entries whose native transport values were reclaimed. An explicit public boundary reference still pins its value. Conversion by value does not promise host identity.

Exact native null/Boolean identities map to Java null/Boolean without Expats. Byte, Short, Integer and in-range BigInteger normalize to Long; Long and String use by-value transport. Other numeric forms and raw VM representation values are rejected. Arbitrary objects become opaque Aliens, not reflected Java method collections. Integers and strings currently have no native class dispatch.

For the specified callback admission protocol, DefaultJavaBoundary.Call records the suspended configuration, parent call, originating thread, admission state and active callback count. NativeHeap transition leases root suspended configurations until their native thread resumes; closed calls clear their configuration and ancestry references.

CallbackContext.send uses a permit to serialize native execution and short representation-sensitive services. invoke releases permission around the selected foreign operation and reacquires it before result conversion. Selection retains native permission and prohibits callbacks. Worker callbacks run on their own host thread, so the blocked caller needs no callback pump. The coordinator’s native owner, active call and idle state collectively realize conceptual token ownership; neither copied contexts nor nested permits are individual tokens.

The innermost call admits callbacks and completion waits for admitted descendants, as required by the contract. The implementation uses wait/notifyAll, with no FIFO or fairness guarantee. Waiting admission can be interrupted with EXECUTION_POLICY; required caller restoration waits without abandoning native state and preserves the thread’s interrupt flag. No foreign-thread affinity or termination guarantee is added. The shared guard also protects this concrete store’s representation-sensitive operations; it is an implementation constraint, not a universal physical-memory token rule.

The callback nesting limit is 64; pending requests do not consume nesting depth. The default no-crossing NLR agreement is implemented by checking home liveness and the callback continuation, then delegating crossing rejection to DefaultJavaBoundary.nonLocalReturnFailure(). Control.Error aborts the callback and retires its homes before the boundary exports the specified diagnostic. The shared Execution retains only the step budget, not a sticky failure marker; foreign recovery does not replenish it. Exhaustion prevents further native transitions without vetoing a terminal foreign result that needs no further step. Host exception classes and message text are not language interfaces.

Stack Safety

The native driver loops over explicit frames, so language method/lambda calls and nested initializers do not recursively call the Java evaluator. Synchronous foreign calls and callbacks do use the host stack. A transition budget cannot preempt a blocking foreign operation; termination remains an adapter concern. The callback limit, retained allocations and possible resource exhaustion prevent any claim of unlimited execution.

Tooling Architecture

The interpreter executes without consulting analysis annotations. Tools may add naming, diagnostics, inferred types, contracts or analysis results around the descriptor layer. This chapter specifies intended tooling interfaces and their current limits; it does not claim an implemented analyzer or debugger.

Evaluation Contexts

A tool can evaluate with explicitly supplied objects or select a debug activation. The context uses activation objects, ordinary lexical lookup and the same Alien/Expat and return rules. It introduces neither a separate Environment namespace nor a global service registry. Language-visible debugger and mirror services must be explicitly supplied boundary capabilities. Internal activation selection does not make activations public language values.

OperationContext
Module instantiationEmpty top activation; explicit constructor inputs
Tool expression evaluationExplicitly supplied objects, such as sample data or a console
Proposed debugger evaluationSelected activation’s bindings plus explicitly supplied services

A tool must identify its context and additional capabilities. It cannot silently enrich normal module entry. Results retain actual lexical captures, including classes that resolve superclass/mixin targets there; export and persistence must preserve or explicitly account for those dependencies.

The Java entry paths implement module and supplied-expression evaluation, not a general selected-activation debugger API.

Execution, Observation and Intervention

The execution agreement distinguishes ordinary evaluation, representation maintenance and explicitly authorized observation/intervention. Tools use that contract rather than gaining execution rights from possession of a configuration. Backend preparation and retention follow the Java coordination rules.

For example, an immutable published observation can be consumed while ordinary execution continues. Reading live slots needs a specified consistency model; changing one is an intervention whose effective ordering must be defined. Replacing or resuming a continuation also needs an ownership-transfer protocol so its previous owner cannot continue. These examples do not imply a general monitor or selected-activation intervention API in the current prototype.

A model checker is another explicitly supplied tool: a supporting parallel VM could honor its request for independent simultaneous transitions under the parallel-agreement requirements. The execution capability, proof evidence and concrete implementation must meet that agreement; a saved configuration alone supplies none of them.

Descriptors as the Naming Bridge

Intrinsic declaration names identify many syntax elements. A descriptor can name an otherwise anonymous expression, for example (compute(x) : intermediate). It attaches information without changing execution. Name resolution for tool references is separate from language message lookup.

External Annotation Files

Each tool may keep a separate external file associating syntax identities with its own facts: a type, interval, units assumption, proof obligation or diagnostic. Formats and interpretations belong to the tool. Adding or changing annotations does not alter raw execution, supply runtime capabilities or establish that an asserted property holds. Different tool views need not use a shared format.

Qualified Naming

Paths such as module.Class.method.local are proposed tooling conventions, not language selectors. Tools must resolve collisions and preserve references when source changes. Descriptor-supplied names can identify subexpressions, but a stable AST/source-mapping scheme is still required; spelling a name alone does not solve identity across edits.

Connection to Abstract Interpretation

The explicit-state visitor machine provides a starting point for analysis. AAM and ADI are research approaches, not modes enabled by an allocator or an “abstract kernel.” The required derivation is described under Persistence and Analysis.

Annotations may supply domains or assumptions to a particular analysis, which must state their meaning and justify its results. Descriptors alone perform no checking. Analysis, mirror tooling and persistence remain future work.

Future Directions

This chapter separates accepted extension directions from unresolved proposals; neither implies an implemented feature or promised release. Extensions preserve the accepted capability inputs, lookup, construction and boundary contracts unless a later decision explicitly changes them. Tool annotations alone cannot change raw execution. Any default handler, mirror or scheduling service must be supplied explicitly, not discovered through an ambient kernel.

Operators and Control Structures

Proposed surface extension. Binary operators, conventional conditionals, loops, pattern matching and library DSLs could lower to the core’s sends, lambdas and objects. A monadic extensible parser inspired by Lean 4 is one candidate. Precedence, hygiene, phase separation and preservation of evaluation order need specification. The current syntax already expresses control through ordinary messages and thunks; no extensible parser is implemented.

Named and Optional Arguments

Proposed; dispatch unresolved. Named arguments, defaults and varargs must coexist with exact name/arity selection and generated setters. A candidate name = expression argument form would need a distinct grammar context from assignment. Decisions include parameter-name binding, default evaluation scope and timing, duplicate/unknown arguments, and how omitted or variable arguments map to selectors. The current language has positional arguments only.

String Interpolation

Proposed syntax. Interpolation could lower to explicit conversion and concatenation messages. Delimiters, conversion protocol and evaluation order remain unspecified. It also depends on native string operations, which the prototype does not yet implement; see the scalar design note.

Collection Literals

Proposed syntax and libraries. Lists/maps could be constructed through ordinary supplied classes, with future literal sugar. Syntax must avoid conflicting with object literals. Collection classes, key equality and hashing, mutability and element evaluation order require contracts; example List/Map names do not denote ambient standard objects.

Mixin Contract Verification

Proposed analysis. A verifier could collect a contribution’s super sends and check the required selectors at each actual application occurrence. The selected continuation of the dispatch chain, arity and invocation rules matter; a set of names alone is insufficient. Descriptors could state stronger contracts. Results belong to external tooling and do not replace runtime failure on an unsatisfied contract. See object-model dispatch and tooling.

Deep Family and Mixin Composition

Accepted direction; deferred semantics. Deep composition with state in member classes needs rules for nested declarations, constructor signatures, sibling references, state and ordering. The current whole-declaration member override and ordered contributions remain the reference. Preserve declaration identities, definition scopes and occurrence identities so later composition can distinguish repeated applications.

Possible operations include aliasing, renaming, hiding, exclusion, precedence and explicit state sharing/mapping. They are distinct: an alias need not rewrite recursive sends; hiding need not remove internal access; selecting behavior does not settle storage collisions. Effectful initializer routes require an execution plan—registrations and callbacks cannot be assumed to commute or roll back. One-object construction and the foreign boundary must survive any extension. See the accepted scope decisions and composition design space.

Trait-Style Conflict Resolution

Alternative under consideration. Detection of overlapping method selectors could require an explicit own override or contribution-specific delegation, instead of silently accepting declared precedence. That would change current ordered override semantics and is not accepted. Direct contribution delegation syntax and its receiver/origin rules are also unresolved. Reified definitions help detection, but future composition may require additional metadata.

doesNotUnderstand as a Message

Open design. Receiver interception through a doesNotUnderstand message could support proxies and delegation. Questions include recursive failure, typo masking, default behavior and analysis of dynamic selectors. Signaling a missing-message condition is another proposal. Neither is implemented: current missing dispatch is a fatal diagnostic and never invokes a DNU method.

Exception System

Proposed condition/restart system. Current fatal diagnostics are not catchable, resumable or retryable. The design goals are local recovery, escalation through callers, optional resumption at the signal site with a supplied value, and an explicitly configured last-resort policy.

The Common Lisp-inspired proposal separates:

RoleResponsibility
ConditionDescribe a problem at the signaling site.
HandlerSelect recovery policy in an enclosing dynamic context.
RestartOffer a named recovery operation near the component that can perform it.

One candidate scans active handler/restart frames while preserving the signaling continuation, then either resumes or explicitly unwinds. Direct frame mechanisms and a design built from delimited continuations/algebraic effects remain alternatives. Handler matching and ordering, restart extent and selection, resumption multiplicity, cleanup, home liveness and foreign-call barriers need precise rules. Two or three new frame classes would not by themselves specify this semantics or prove its analysis cost.

The proposed missing-message condition would replace fatal DNU only after an accepted change. Unhandled conditions could reach a deployment-supplied handler: a test runner may record failure, a simulator may choose a degraded value, and an analyzer may represent alternatives. These are distinct execution policies, not capabilities implicitly available to every module. Existing boundary failure kinds must survive propagation; changing resumability requires an explicit contract for external effects.

A later library could offer try/catch, ensure and assertion-like operations over the chosen mechanism. Cleanup on normal return, failure and non-local return must be defined before claiming that ensure is ordinary sugar. The investigation order is basic signaling/handlers, restarts and explicit abort, library forms, then analysis. No release numbers or implementation-size claims are committed.

AAM Compatibility

No condition-system abstraction has been derived. Finite source or frame forms do not imply finite execution state. An analysis must represent handler/restart instances, dynamic names, continuation alternatives, state updates and control outcomes, with sound matching and transfer rules. Joins combine alternatives; widening is a separate convergence technique when a domain needs it. See analysis obligations.

Tail-Call Optimization

Proposed investigation; not implemented. The objective is bounded control space for eligible native tail-call chains, including mutual calls and delegation. Explicit continuations already avoid one Java evaluator frame per native call; that is distinct from bounded store use or proper tail recursion.

A final send is only a candidate. Its callee may invoke a captured lambda whose ^ still targets the caller’s live home. For ^ recurse(), the operand executes before return delivery; collapsing frames afterward does not reduce peak recursive space. An optimization must preserve home identity and retirement, initializer phases and remaining contributions, constructor results, pending member-cache completion, callback barriers, selected receiver/origin, evaluation order and exactly-once effects. Foreign calls need separate eligibility rules.

The proposed sequence is to measure the recursion catalog, identify core tail contexts and completion obligations, prototype a conservative native optimization, and compare results, traces, identity, failures, continuation depth and allocation. Captured bindings cannot be reused if doing so changes closure observations. Reclamation and retained data/caches need a separate space account; a growing list of deferred homes does not establish bounded control space.

Inlining needs the actual selected behavior or justified guards, not special selector names such as ifTrue. Debug history also has a cost: bounded summaries, recording and replay provide different guarantees. Proper tail recursion remains a stronger uncommitted space property. The research basis is Clinger, Proper tail recursion and space efficiency.

Mirror-Based Reflection API

Broader reflection remains proposed. Mirrors could offer controlled inspection or invocation on a target. Reflective operations belong on mirrors, not ambient methods of Object; the application need not itself implement reflection. Obtaining a mirror requires authority, and language-visible backend services still use the Alien/Expat boundary.

The API must decide which class, slot, method and origin information is exposed, which mutations are allowed, and how access restrictions, optimizations and lifetime are respected. Existing backend fields are implementation evidence, not a public representation contract or proof that no new metadata is needed. There is currently no public class getter or activation reification.

The implemented IdentityMirror protocol is the baseline. Further kinds, standalone mixin references, native scalar identity and broader reflection remain open. The design note records the current scope and limitations.

Access Control

Proposed policy; no language access control is enforced today. The candidate object-capability design treats an object’s export surface as its external behavioral contract:

  1. Private declarations by default, with explicit exports; getter and setter exposure can differ.
  2. Inherited exports remain visible, while parent internals are sealed from subclasses. Whether a separate “heritable” visibility is useful remains open.
  3. A mixin’s exported behavior becomes internal to its applier unless re-exported; the mixin’s own helpers remain available to that contribution but hidden from unrelated contributions.
  4. Lexical nesting grants access to enclosing internals. The exact treatment of explicit sends to an outer ClassName receiver still needs specification.
  5. Class-side new, apply and named factories follow the same export policy; external construction requires an exported path.

These are candidate changes to current lookup, not behavior enabled by existing annotations. Export syntax, especially for synthesized factories, is undecided. A tool-only descriptor could check conventions first; runtime enforcement would require an explicit semantic increment. Expats must then expose the same surface as external native callers. Origin metadata may assist enforcement, but sealing, virtual overrides, state access and composition require proofs and possibly new metadata. Export sets alone do not establish safe pruning in an analyzer.

The accepted outer operation still selects an ordinary declaration-relative receiver. This proposal creates neither a universal parent getter nor public activation reflection. Related Works places this proposal alongside Newspeak and other capability designs; no novelty or simplicity claim is assumed.

Method tear-offs

Proposed; neither syntax nor a method-reification API is implemented. Ordinary obj.m invokes m/0; it never implicitly returns a method. The current candidate obj.m#N would evaluate the receiver once, select an actual method m/N, and return a callable retaining that method, receiver and dispatch origin. Applying it would execute the selected method with its original self and exact apply/N arity. It would not select callable-slot fallback or member-class factory candidates.

Under that proposal, obj.m#2(a,b) obtains the method reference and applies it; a mismatched application arity fails. This requires no separate immediate-apply semantic operation. An earlier $ suffix candidate omitted explicit arity; it is not accepted syntax either. Final grammar, bound versus unbound references, identity/equality of repeated references, interaction with overrides and super, and mirror integration remain open. The accepted distinction between access, invocation and callable values stays in Message sends.

Concurrency and Parallelism

Accepted execution-agreement extension principle; concrete parallel agreements and the composition layer remain future work. No scheduler is implemented. The current execution agreement already permits maintenance refinements and declared interventions while serializing ordinary native control. This section concerns richer agreements authorizing simultaneous native transitions. The Java world’s mutable store and effectful foreign operations supply neither snapshots nor a pure state transformer.

Independent Transitions and Parallel Execution

A model checker with an appropriate capability may ask a supporting parallel VM to execute two independent enabled transitions concurrently. The agreement must specify execution authority, shared-state semantics, observations and the independence evidence it accepts. It need not mandate a proof format: evidence may be supplied with the request or established by a trusted analysis, but it must apply to the actual configuration and assumptions used.

For transitions \(t_1,t_2\) enabled in \(C\), the independence obligation is that each preserves the other’s applicability and both orders yield equivalent configurations and observable effects under the agreement:

\[ C\xrightarrow{t_1}C_1\xrightarrow{t_2}C_{12},\qquad C\xrightarrow{t_2}C_2\xrightarrow{t_1}C_{21},\qquad C_{12}\approx C_{21}. \]

Equivalence includes the specified boundary effects and their ordering, not just equal final slot values. Arbitrary foreign operations cannot be presumed independent; their declared contracts or an explicit effect model must supply the necessary justification. Speculation, cancellation and replay need their own effect agreements.

Semantic independence and concrete concurrency safety are separate obligations. A parallel implementation must correctly coordinate its allocator, store, roots, continuations, caches and collector; mathematical commutation does not make today’s Java data structures thread-safe. An implementation parallelizing work that refines an allowed sequential trace may retain the sequential abstract agreement. Authorizing additional ordinary native control requires the richer agreement and its authority discipline. Neither case changes fixed lookup, identity, return-home lifetime, initializer phases or the boundary’s NLR policy.

This extension principle adopts no parallel VM implementation, scheduler, snapshot representation, model-checking algorithm or public transition-proof API. Those remain separate increments with their own specifications and tests.

Boundary-supported Non-local Returns

Implementing an agreement beyond the default no-crossing boundary requires a transfer mechanism and specified treatment of intervening foreign work. This is separate from parallel execution or scheduling. The NF/FN design note compares immediate escape and deferred delivery without selecting either as a mandatory mechanism.

The Semantic Language Interface (SLI)

The proposed SLI would expose machine stepping, input/output interaction and possibly inspection or snapshots to an external composition runtime. Actors, CSP, dataflow and parallel simulation are candidate compositions, with explicit scheduling, synchronization, time, routing and failure policies. Those policies must preserve native lookup and the message-level Alien/Expat contract; swapping schedulers does not prove application behavior unchanged.

A future boundary suspension could expose an operation request, then resume with a reply. It must define callback/reentrancy, identity, ownership, cancellation and failure behavior before replacing today’s synchronous calls. Snapshot/restore must account for the native store, live homes, continuations and boundary caches, and explicitly exclude, model or compensate external effects. Replay and speculation require recorded inputs and suitable foreign contracts; they are not free consequences of sequential stepping.

The incremental composition proposal starts with bounded native state copying/comparison, explicit admitted state, a small SLI adapter and observations before shared-state composition. Gamine’s SLI, communicating vats/actors, DEVS and virtual-actor runtimes are inspirations, not implemented integrations. Progress and sound analysis across composed machines remain separate proof obligations.

Persistence and Analysis

Deferred. Portable platform persistence must preserve identities, captures, composition origins and explicitly reconnectable foreign bindings. It is not Java object serialization and must not discover new authority while loading. See object-graph persistence.

An abstract execution requires domains, store/control abstractions, transfer rules and foreign-effect assumptions related to the reference semantics. A configurable allocator, supplied abstract object or descriptor does not provide that derivation. Native scalar protocols and foreign conversion must also have explicit contracts; current open choices are recorded in the value/analysis note.

Miller’s Robust Composition connects object capabilities, cooperation and limiting interference. Runtime admission and conceptual control

The following transition rules describe ordinary execution under the sequential execution agreement. Their runtime-level admissibility condition is one conceptual control token \(\tau_c\) per live runtime, with one owner:

\[ \begin{aligned} \operatorname{owner}(\tau_c)\in{}&{\mathrm{idle}}\ &{}\cup{\mathrm{native}(\alpha)\mid\alpha\text{ admitted}}\ &{}\cup{\mathrm{foreign}(\iota)\mid\iota\text{ active}}. \end{aligned} \]

Here \(\alpha\) ranges over native continuations and \(\iota\) over foreign invocations. The condition ranges over one runtime’s evolving state and all its configurations, not separate tokens per configuration, stored version or thread. Ordinary native rules require ownership by their continuation; modeled foreign actions require ownership by their invocation. Transfers below are abstractly atomic, with associations retained in \(B\) and barriers. \(\tau_c\) is ghost state, not a required field or language value; initializer target \(\tau\) is unrelated.

Backend one-step yield may leave a nonterminal successor without retiring its homes or producing a final observation. Later advancement requires readmission. The source evaluator’s driver instead retains authority between native steps until a boundary transfer or completion.

This layer models serialized control effects, not arbitrary foreign computation, host queues, wakeups or fairness. Such work can continue while a callback owns the token. Refinement must reconstruct ownership from the implementation; these conditions are not a completed proof of the Java coordinator.

The execution agreement also permits maintenance refinements and declared interventions. Maintenance may stutter; an intervention changing abstract state needs its own specified transition. The rules below define neither an intervention relation nor a parallel agreement. Proofs must state which extensions, if any, they include.

Exact and invocation lookup

Exact search over an ordered contribution list is:

\[ \begin{aligned} E(v,[],s)&=\bot,\cr E(v,o::L,s)&= \begin{cases}T_{v,o}(s)&T_{v,o}(s)\ne\bot,\cr E(v,L,s)&T_{v,o}(s)=\bot.\end{cases} \end{aligned} \]

\[ P(v,k)= \begin{cases} t&E(v,(\mathrm{apply},k))=t\text{ and }t\text{ is not a generated getter},\cr !\epsilon&E(v,(\mathrm{apply},k))=!\epsilon,\cr \bot&\text{otherwise}. \end{cases} \]

Its target expressions run in \(\rho\); routed arguments run in the fresh declaring initializer home after allocation. The resulting class and receiver are fresh on every evaluation. This introduces no additional private operation or object-specific continuation, and does not call apply or any contributor factory.

For a live current initializer home \(h\) with \(H(h)=\mathrm{slots}\), set \(v=\sigma(\rho).v\), \(o=\sigma(\rho).o\), and \(p_s=L_{\mathrm{class}(v)}(o,j)\) before evaluating the value expression:

\[ \begin{aligned} \langle\mathrm{write}(j,e),\rho,\kappa\rangle_X &\longrightarrow\langle e,\rho,\mathrm{Write}(v,p_s,\rho)::\kappa\rangle_X,\cr \langle\mathrm{val}(w),\rho’,\mathrm{Write}(v,p_s,\rho)::\kappa\rangle_X &\longrightarrow\langle\mathrm{val}(w),\rho,\kappa\rangle_{X[\sigma(v).S[p_s]:=w]},\cr \langle\mathrm{slotsDone},\rho,\kappa\rangle_X &\longrightarrow\langle\mathrm{val}(v),\rho,\kappa\rangle_{X[H(h):=\mathrm{body}]}. \end{aligned} \]

Invalid private targets, arities or phases raise errors. No selector or Expat operation can name these controls.

Completion, return and failure

The rules below model the default boundary agreement, which prohibits non-local returns across foreign execution. Whether to support crossing belongs to the boundary agreement, not a universal native-language prohibition. A supporting agreement requires additional transfer rules; none are defined or implemented here. Lexical return targets, home liveness and initializer phase restrictions remain native rules.

\[ \frac{(\chi,H(h),v’)\in {(\mathrm{method},\mathrm{method},w),(\mathrm{initializer},\mathrm{body},v)}} {\langle\mathrm{val}(w),\rho’,\mathrm{Done}(h,v,\chi,\rho)::\kappa\rangle_X \longrightarrow\langle\mathrm{val}(v’),\rho,\kappa\rangle_{X[H(h):=\mathrm{dead}]}}. \]

An initializer finishing in slots raises PrematureCompletion. A source return first evaluates its operand, capturing \(h=\sigma(\rho).h\):

\[ \begin{aligned} \langle\mathrm{ret}(e),\rho,\kappa\rangle_X &\longrightarrow\langle e,\rho,\mathrm{Return}(h)::\kappa\rangle_X,\cr \langle\mathrm{val}(v),\rho,\mathrm{Return}(h)::\kappa\rangle_X &\longrightarrow\langle\mathrm{return}(h,v),\rho,\kappa\rangle_X. \end{aligned} \]

Let \(\kappa=P\cdot[\mathrm{Done}(h,w,\chi,\rho_c)]\cdot\kappa_c\), with no Barrier in \(P\). Successful delivery requires \(H(h)=\mathrm{method}\) or \(H(h)=\mathrm{body}\), according to \(\chi\). Let \(X’\) retire all homes in that prefix through the target and mark its pending Cache frames failed with AbandonedRealization:

\[ \frac{\kappa=P\cdot[\mathrm{Done}(h,w,\chi,\rho_c)]\cdot\kappa_c \qquad v’=\begin{cases}v&\chi=\mathrm{method},\cr w&\chi=\mathrm{initializer}\end{cases}} {\langle\mathrm{return}(h,v),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{val}(v’),\rho_c,\kappa_c\rangle_{X’}}. \]

Only completion of the target contribution is skipped; its caller’s subsequent contributions continue. A lambda’s captured home is never dynamically rebound.

\[ \langle\mathrm{error}(\epsilon),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{abort}(\epsilon),\rho,\kappa\rangle_X. \]

For an ordinary frame \(f\) (not Barrier), obtain \(X_f\) by retiring its home if it is Done, or caching failed(ε) if it is Cache; otherwise \(X_f=X\):

\[ \langle\mathrm{abort}(\epsilon),\rho,f::\kappa\rangle_X \longrightarrow\langle\mathrm{abort}(\epsilon),\rho,\kappa\rangle_{X_f}. \]

There is no rollback, lookup retry, or revival of a retired home. Aborting a callback retires only frames above its barrier; the suspended caller remains live. Cache failure caused by a successful return does not abort that return.

Alien/Expat transitions

The adapter state B includes call association and admission lifetime. The Java realization may obtain a callback from the operation thread or from a worker holding an explicit call context; admission serializes their native transitions. Each admitted callback belongs to the current foreign invocation, retains its suspended caller and budget, and creates the barrier below. Closing a foreign invocation disallows further callback actions for it and joins admitted descendants before delivering done or fail. Host requests rejected before admission do not create a native callback continuation. These rules describe the serialized native interaction; they do not formalize arbitrary parallel foreign actions, host waiting queues or a general scheduler.

These transitions use the default no-crossing agreement: callback entry installs Barrier, and the foreign action relation has no non-local-return transfer action. A future supporting boundary must define that transfer and its observable interaction with foreign execution; merely removing Barrier is insufficient.

The adapter provides stateful, identity-preserving conversions \(B,\sigma\vdash\bar v\Uparrow(\bar f,B’)\) and \(B,\sigma\vdash\bar f\Downarrow(\bar v,\sigma’,B’)\), or failure with the state reached before failure. Lists convert left-to-right. Exact canonical null/Booleans convert by identity; scalars follow S. Compatible identity round trips satisfy \(\Downarrow\Uparrow v=v\) and \(\Uparrow\Downarrow\phi=\phi\). These are boundary obligations, not privileged native service operations.

\[ \frac{B,\sigma\vdash\bar v\Uparrow(\bar f,B’)} {\langle\mathrm{call}(\mathrm{foreignOp}(\phi,op),\bar v),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{foreign}(op(\phi,\bar f)),\rho,\kappa\rangle_{X[B:=B’]}}. \]

The foreign interaction-state relation \(B\vdash\omega\leadsto(a,B’)\) has actions \(a::=\mathrm{done}(f)\mid\mathrm{fail}(\epsilon)\mid\mathrm{next}(\omega’) \mid\mathrm{send}(v,n,\bar f,\omega’)\). It may block or diverge; it need not be deterministic. The state \(\omega\) records foreign behavior and resumption; it is not the unique control token. Several suspended barriers can retain distinct foreign interaction states. Actions done and fail below mean completion delivery after the admission condition above is satisfied, not the physical arrival of an answer from a foreign worker. Its completion rules are:

\[ \begin{gathered} \frac{B\vdash\omega\leadsto(\mathrm{next}(\omega’),B’)} {\langle\mathrm{foreign}(\omega),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{foreign}(\omega’),\rho,\kappa\rangle_{X[B:=B’]}},\cr \frac{B\vdash\omega\leadsto(\mathrm{done}(f),B_1) \quad B_1,\sigma\vdash f\Downarrow(v,\sigma’,B_2)} {\langle\mathrm{foreign}(\omega),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{val}(v),\rho,\kappa\rangle_{X[\sigma:=\sigma’,B:=B_2]}},\cr \frac{B\vdash\omega\leadsto(\mathrm{fail}(\epsilon),B’)} {\langle\mathrm{foreign}(\omega),\rho,\kappa\rangle_X \longrightarrow\langle\mathrm{error}(\epsilon),\rho,\kappa\rangle_{X[B:=B’]}}. \end{gathered} \]

For callback action send(v,n,fs,ω′), allocate an empty activation \(a\) with no parent, receiver or home:

\[ \begin{aligned} &\langle\mathrm{foreign}(\omega),\rho,\kappa\rangle_X\cr &\quad\longrightarrow \langle\mathrm{callback}(v,n,\bar f),a,\mathrm{Barrier}(\omega’,\rho)::\kappa\rangle_{X’},\cr &\frac{B,\sigma\vdash\bar f\Downarrow(\bar v,\sigma’,B’)} {\langle\mathrm{callback}(v,n,\bar f),a,\kappa\rangle_X \longrightarrow\langle\mathrm{send}(\mathrm{recv}(v),n,\bar v,\mathrm{exact}),a,\kappa\rangle_{X[\sigma:=\sigma’,B:=B’]}}. \end{aligned} \]

Here \(X’\) includes the adapter step and fresh activation. Installing the barrier before import gives conversion failure the same failure path as the callback body. A previously handled failure does not prevent a new callback.

\[ \frac{B,\sigma\vdash v\Uparrow(f,B’)} {\langle\mathrm{val}(v),\rho’,\mathrm{Barrier}(\omega,\rho)::\kappa\rangle_X \longrightarrow\langle\mathrm{foreign}(\omega[\mathrm{result}(f)]),\rho,\kappa\rangle_{X[B:=B’]}} \]

\[ \langle\mathrm{abort}(\epsilon),\rho’,\mathrm{Barrier}(\omega,\rho)::\kappa\rangle_X \longrightarrow\langle\mathrm{foreign}(\omega[\mathrm{failure}(\epsilon)]),\rho,\kappa\rangle_X. \]

Export failure enters error with the barrier still present. The failed callback reports its diagnostic to the foreign continuation. Foreign code can handle it, make another callback and complete normally, or propagate a failure. The outer native caller observes that foreign completion after conversion; no shared fatal marker overrides it. Native mutations and callback-home retirement survive reentry, while suspended caller homes remain live until their own completion or failure. This does not resume the aborted callback or permit NLR crossing.

Conversion failures

Import failure has form \(!(\epsilon,\sigma’,B’)\); export failure has form \(!(\epsilon,B’)\), with unchanged native store. At each site the reached state is retained:

\[ \begin{gathered} \frac{B,\sigma\vdash l\Downarrow !(\epsilon,\sigma’,B’)} {\langle l\rangle_X\longrightarrow \langle\mathrm{error}(\epsilon)\rangle_{X[\sigma:=\sigma’,B:=B’]}},\cr \frac{B,\sigma\vdash\bar v\Uparrow !(\epsilon,B’)} {\langle\mathrm{call}(\mathrm{foreignOp}(\phi,op),\bar v)\rangle_X\longrightarrow \langle\mathrm{error}(\epsilon)\rangle_{X[B:=B’]}},\cr \frac{B,\sigma\vdash\bar f\Downarrow !(\epsilon,\sigma’,B’)} {\langle\mathrm{callback}(v,n,\bar f)\rangle_X\longrightarrow \langle\mathrm{error}(\epsilon)\rangle_{X[\sigma:=\sigma’,B:=B’]}},\cr \frac{B\vdash\omega\leadsto(\mathrm{done}(f),B_1) \quad B_1,\sigma\vdash f\Downarrow !(\epsilon,\sigma’,B_2)} {\langle\mathrm{foreign}(\omega)\rangle_X\longrightarrow \langle\mathrm{error}(\epsilon)\rangle_{X[\sigma:=\sigma’,B:=B_2]}}. \end{gathered} \]

\[ \frac{B,\sigma\vdash v\Uparrow !(\epsilon,B’)} {\begin{aligned} &\langle\mathrm{val}(v),\rho’,\mathrm{Barrier}(\omega,\rho)::\kappa\rangle_X\cr &\quad\longrightarrow \langle\mathrm{error}(\epsilon),\rho’,\mathrm{Barrier}(\omega,\rho)::\kappa\rangle_{X[B:=B’]} \end{aligned}}. \]

Entry, observations and remaining parameters

Normal module definition starts at an empty top activation, with structural superclass Object and no mixins; forbidden top-level contributor clauses fail before evaluation. Instantiation supplies existing argument values to exact new/k, without capturing the service’s scope. Tools may explicitly supply a different starting activation. See module entry. Independent entry requires successful runtime admission from idle under the control agreement above. Construction of an entry configuration does not itself grant execution authority. For a valid module descriptor \(d\), \(d\)’s arity must equal \(|\bar v|\). Allocate fresh \(a\) with \(\sigma’=\sigma[a\mapsto\mathrm{Act}(\varnothing,\bot,\bot,\bot,\bot)]\):

\[ \begin{aligned} \mathrm{module}(d,\bar v;X) &\leadsto\langle\mathrm{class}(d),a,\mathrm{Module}(\bar v)::\mathrm{halt}\rangle_{X[\sigma:=\sigma’]},\cr \langle\mathrm{val}(C),a,\mathrm{Module}(\bar v)::\mathrm{halt}\rangle_X &\longrightarrow\langle\mathrm{send}(\mathrm{recv}(C),\mathrm{new},\bar v,\mathrm{exact}),a,\mathrm{halt}\rangle_X,\cr \mathrm{tool}(e,\rho;X) &\leadsto\langle e,\rho,\mathrm{halt}\rangle_X. \end{aligned} \]

These are admitted independent entry points, not source operations. The entry arrow acquires the existing idle token for the new continuation. The same admission premise applies to independent exact Expat sends; callbacks instead use the foreign invocation’s admission path. A rejected module descriptor has no definition transition; it reports its validation error. Delivery of a Final observation returns control to idle; retaining the final configuration does not retain execution authority.
