VarioHyve Language Specification

Foreign Semantic Values and the Alien/Expat Boundary

VarioHyve programs interact with values and entities governed by other semantic domains: Python, Java, C, simulation engines, databases, hardware interfaces, other VarioHyve runtimes, and the implementation VM itself. This section defines the boundary model. Foreign systems retain their own semantics and execution mechanisms; federation does not require a shared object model.

Design Principles

The boundary follows these constraints:

  1. Foreign semantic sovereignty. Alienation makes a foreign value reachable; it does not supply a VarioHyve class, mixins, lexical receiver structure, or methods. The foreign adapter determines the operations it supports.
  2. Native semantic sovereignty. VarioHyve lexical lookup, self, qualified outer ClassName, super, and native dispatch have fixed language semantics. Crossing to an Alien leaves that semantic domain; it does not customize lookup.
  3. Symmetric crossing. Arguments, results, failures, identity and callbacks obey the Alien/Expat contract in both directions, including VM services.
  4. Explicit adaptation. Ordinary VarioHyve wrappers supply VarioHyve behavior around foreign values. Alienation preserves foreign semantics; wrapping constructs a VarioHyve abstraction.

Aliens — Foreign Semantic Values Inside VarioHyve

An Alien is a VarioHyve-visible reference to a value or entity governed by a foreign semantic domain. Examples include a Python object, C pointer, function, struct value, opaque resource handle, simulator model or remote endpoint. An Alien need not support any direct operation. Its presence in an object slot does not make that containing object its lexical outer.

When VarioHyve code sends a message to an Alien:

aServer.start(port)        // aServer is an Alien wrapping a Python object

The boundary performs the following protocol when its adapter supports that operation:

  1. Expatriate the arguments — each VarioHyve argument is converted (or wrapped) into a foreign representation suitable for the target runtime. VarioHyve objects become Expats; primitive values are marshalled.
  2. Invoke foreign behavior — the adapter interprets the (name, arity) request according to its foreign contract. OO forwarding is one policy; capability operations on otherwise opaque handles are another.
  3. Alienate the result — the foreign return value is converted (or wrapped) back into a VarioHyve value. Foreign objects become Aliens; primitive values are unmarshalled.

│   VarioHyve     │         │  Foreign Runtime  │

│                 │         │                   │

Alien Dispatch

After evaluating an explicit receiver, the evaluator distinguishes native values from Aliens. Native values use fixed VarioHyve lookup. An Alien uses its boundary adapter; native class and mixin lookup does not continue through the Alien. Selector/arity transport does not imply that the foreign entity intrinsically has methods or a VarioHyve class. The adapter may return a genuine selector miss.

An explicit Alien invocation selects exactly its requested name/arity. A foreign getter is not a generated native accessor and is not executed to discover a callable; write alien.f.apply(args) to invoke its returned value explicitly. A stored Alien can supply callable behavior if its adapter advertises exact apply/N, including through ForeignCallable. Candidate selection retains the operation and does not resolve it a second time before execution.

The adapter must distinguish absence before operation entry from failure after selection. Resolution must not execute operations or call back into the language. A resolution or execution failure never resumes lookup or replays effects. Receiver and arguments are evaluated once. See Message Sends.

Explicit foreign selectors named self, outer or super are eligible for ordinary boundary dispatch: alien.outer requests the foreign operation named outer. It does not navigate a VarioHyve scope. The receiver forms self, outer ClassName and super.message retain their separate native meanings. Native declarations do not acquire those reserved names through this exception.

Alien Identity

For identity-bearing values, a boundary defines foreign identity and preserves sharing across repeated crossings. The current in-process Java adapter canonicalizes by Java object identity. This is an adapter policy, not a universal identity law for all domains, and does not synthesize an eq method on Aliens.

For C, numeric address equality, allocation identity, pointer provenance and value equality are distinct concerns. Reused addresses must not automatically identify the same semantic entity. A future C adapter must define its lifetime and identity policy explicitly; no C FFI is implemented by this specification.

Expats — VarioHyve Objects Outside VarioHyve

An Expat exposes a native VarioHyve value’s behavior to a foreign domain. It may present that behavior in the foreign runtime’s idiom, but its public contract does not expose a store, address, activation or VM representation. Invocation reenters fixed VarioHyve semantics. Backend adapters may privately retain the information required to do so.

The bootstrap’s VHExpat.send API performs exact selector dispatch, including zero-argument access. It does not apply source invocation’s generated-binding selection: read a callable binding, then send apply/N to that result explicitly.

When foreign code sends a message to an Expat:

# Python side — server is an Expat wrapping a VarioHyve object
server.start(8080)

The Expat performs the mirror-image protocol:

  1. Alienate the arguments — each foreign argument is converted (or wrapped) into a VarioHyve value. Foreign objects become Aliens; primitive values are unmarshalled.
  2. Forward the message — the foreign call is translated into a VarioHyve (name, arity) dispatch and sent to the wrapped VarioHyve object.
  3. Expatriate the result — the VarioHyve return value is converted (or wrapped) back into a foreign representation. VarioHyve objects become Expats; primitive values are marshalled.

│  Foreign Runtime  │         │    VarioHyve     │

│  msg(args)  ──────►  Expat  ──────►  vh_obj.msg(alienate(args))

Expat Surface

An Expat exposes the VarioHyve object’s full behavioral interface — every method the VarioHyve object can respond to is available through the Expat. In v1 (no access control), this means all methods. When access control is introduced (see Future Directions — Access Control), Expats will expose only the export surface — the same contract that any external VarioHyve caller sees.

Expat Identity

Each VarioHyve object has at most one Expat proxy per foreign runtime. If the same VarioHyve object is expatriated through multiple paths, the runtime returns the same Expat. This preserves identity across the boundary.

The Symmetry

The Alien/Expat model is symmetric:

What it representsForeign semantic value/entityNative VarioHyve value
Lives inVarioHyve storeForeign runtime
On message receiveExpatriate args → forward → alienate resultAlienate args → forward → expatriate result
Proxy forForeign → VarioHyveVarioHyve → Foreign

The two operations preserve compatible reference round trips:

  • Alienate: foreign value → VarioHyve value (wrap foreign objects as Aliens, unmarshall primitives)
  • Expatriate: VarioHyve value → foreign value (wrap VarioHyve objects as Expats, marshall primitives)

For a native reference v and an identity-bearing foreign value f within a compatible runtime pair:

alienate(expatriate(v)) = v
expatriate(alienate(f)) = f

An Expat owned by the importing runtime recovers the original native value; an Alien exported to its originating adapter recovers the foreign value. Cross-runtime references require an explicit bridge, not a guessed identity. By-value conversions instead follow their declared value semantics and may normalize host types; these equations do not promise host representation identity for marshalled primitives.

Explicit Wrappers

A native wrapper can combine several foreign capabilities and supply its own identity, methods, invariants and lifecycle policy. Constructor parameters remain initializer-only, so persistent dependencies are bound into slots:

class Device(deviceHandle, reader, writer, closer) {
    handle = deviceHandle;
    readFn = reader;
    writeFn = writer;
    closeFn = closer;

    read(buffer) { readFn(handle, buffer) }
    write(buffer) { writeFn(handle, buffer) }
    close { closeFn(handle) }
}

The function capabilities can support apply/n, while the handle itself remains opaque and supports no messages. This illustrates an adapter contract, not a built-in C calling convention. Multiple wrappers may share the same Alien while having distinct native identities, lexical scopes and behavior.

VM Services and the Trusted Seed

Language-visible VM services are foreign capabilities and use the same membrane. There is no separate privileged native-function invocation ontology. A finite trusted seed may privately allocate values, maintain stores, and implement lookup and continuations; those internal operations are not language services.

A VM service constructing a native object must return its Expat so import recovers the native value. Returning a Java VMObject representation as an ordinary foreign result is invalid. Representation-sensitive capabilities, if ever exposed, require explicit authority and backend-private Expat unwrapping; public Expats provide no raw-world or address access. See The VarioHyve–VM Boundary.

Constructor Arguments and Optional Bundles

The instantiation service can supply Aliens directly as any of a top-level module’s constructor arguments. It can also assemble an ordinary bundle conventionally called a kernel. The parameter name, number of arguments, and use of a bundle are application choices, not requirements of the foreign protocol:

class(consoleService, fileSystemService) {
    // Each argument may be an Alien or an ordinary VarioHyve object.
    console = consoleService;
    fs = fileSystemService;
}

An optional bundle may itself be an Alien or a VarioHyve object holding Aliens. Objects already belonging to VarioHyve retain their identity through the normal Expat round trip. The service passes existing objects without exposing its other capabilities as a lexical scope. Normal module evaluation has only an empty top activation at its base, with no enclosing application scope; the class inherits only from root Object and composes no mixins. Its constructor inputs are its only external capability entry route.

Tools may explicitly supply Aliens or native objects in development/debugging evaluation contexts. The same boundary contract applies there; those bindings must not silently become capabilities of normal modules’ empty top activations.

Primitive Marshalling

Certain values cross the boundary without proxying — they are marshalled (converted by value) rather than wrapped:

  • Numbers — VarioHyve numbers ↔ host numeric types
  • Strings — VarioHyve strings ↔ host strings
  • Booleans — true/false ↔ host booleans
  • Null — canonical null ↔ host null/None/nil (nil is only a possible platform alias)

Conversions must have explicit value semantics and reject unsupported values. The current Java adapter supports strings, Booleans, null and signed 64-bit integers; it normalizes Java integral representations to Long and rejects unsupported numeric forms. A foreign pointer must not be passed as an integer and expected to retain pointer identity or provenance. Use an explicit handle whose interpretation belongs to its adapter.

Canonical null and booleans are ordinary native objects inside VarioHyve, with language-defined methods and thunk-based control flow. Their Java representation at the boundary is null, Boolean.TRUE or Boolean.FALSE, never an Expat. Incoming Java values map back to the corresponding canonical object in that runtime. This applies equally to results, arguments and callbacks.

Conversion recognizes the canonical identities; it does not call toString, isNull, not or a truth-testing protocol to classify an arbitrary object. Another native object with similar behavior retains its own identity and uses the ordinary Expat route. Core null and empty expressions select the native canonical null directly, without a trip through Java conversion.

Design Considerations

Arity Mismatch

Foreign runtimes may not have a native concept of (name, arity) dispatch. The Alien/Expat layer must map between VarioHyve’s arity-based dispatch and the foreign runtime’s calling convention:

  • Python/Ruby — keyword arguments, *args, default parameters. The mapping is name-based; arity mismatch may surface as a TypeError on the foreign side.
  • Java — selector and arity may participate in an explicit adaptation policy; Java overload resolution can also depend on types. Automatic reflection is not required and is not supplied by the bootstrap adapter.
  • C — a pointer or struct need not receive messages. Explicit capabilities can instead provide call, read, write, field or dereference, subject to a defined ABI, layout, ownership and lifetime contract.

Concurrency Boundary

A future Semantic Language Interface (SLI) may govern scheduling between a sequential VarioHyve VM and concurrent foreign domains. The current boundary implements synchronous same-thread callbacks, not an SLI scheduler. See Future Directions — Concurrency and Parallelism.

Error Propagation

Selector absence and an operation’s raised failure are different outcomes. Foreign failures become defined language failures; native failures crossing an Expat become defined foreign diagnostics. Concrete host exception classes must not define language control flow or leak as ordinary language values. The bootstrap preserves FOREIGN_FAILURE, CONVERSION, OWNERSHIP and EXECUTION_POLICY through machine execution and callback failure propagation. Native missing-selector and control failures remain LANGUAGE_FAILURE. These are defined diagnostic categories, not retained Java exception types or causes. The runtime does not implement resumable conditions or asynchronous callbacks.

Lifecycle and Garbage Collection

Ownership and lifetime belong to the boundary contract for the foreign domain. The current Java adapter retains strong proxy references for the runtime’s lifetime. Future adapters must account for resources without a GC, callback lifetime, and cross-boundary cycles. No universal reclamation protocol is yet defined; exposing raw addresses is not a solution.

Foreign Kinds and Capability Contracts

An adapter may classify values as callable, pointer, struct, remote endpoint or semantic model. Such classifications are foreign contracts, not VarioHyve classes. Future analysis can consume explicit contracts for effects, callbacks, blocking, determinism or state transitions; unknown behavior remains opaque. The bootstrap has no general contract metadata system, provenance registry or foreign reflection API. Those additions must preserve this semantic boundary.
