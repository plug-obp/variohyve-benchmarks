VarioHyve Language Specification

Foreign Semantic Values and the Alien/Expat Boundary

Foreign systems retain their semantics and execution mechanisms. An Alien makes a foreign value reachable inside VarioHyve; it supplies no native class, mixins or lexical outer. An Expat exposes native behavior to a foreign participant. Arguments, results, identity, failures and callbacks obey the same boundary contract in both directions, including language-visible VM services. Native lookup and receiver-origin semantics remain fixed.

The chapter follows values through selection, conversion and control transfer, then defines the VM-service and mirror capabilities. Operational rules are in the formal appendix.

Aliens — Foreign Semantic Values Inside VarioHyve

An Alien may denote an object, function, pointer, struct, resource handle, simulator model or remote endpoint. It need not support direct operations. Storing it in a slot does not make that slot’s owner its lexical outer.

Alien Dispatch

After receiver and argument evaluation, an Alien send selects the adapter’s exact (name, arity) operation. Native class/mixin lookup does not continue through the Alien. Selection must distinguish absence from failure, perform no operation or callback, and retain the selected operation for execution. A resolution or execution failure never restarts lookup or replays effects.

A foreign getter is not a generated native accessor: alien.f(args) does not read f/0 to discover a callable. Write alien.f.apply(args) for that behavior. A stored Alien can qualify for native callable-binding invocation when its adapter advertises exact apply/N; the eligibility check’s selected operation is reused. See Message sends.

Explicit Alien selectors self, outer and super use the foreign protocol. They do not navigate native scope. Native self, qualified outer ClassName and super.message keep their receiver-origin meanings; native declarations do not acquire those reserved selector names through this exception.

Arity Mismatch

An adapter defines how name/arity requests map to foreign behavior. Foreign methods, explicit capability operations and opaque handles need not share one object model. Overloads, defaults, ABI layout and lifetime are adapter concerns; automatic host reflection is not implied.

Alien Identity

Each adapter defines identity and lifetime for its foreign domain and preserves sharing on repeated compatible crossings. Numeric address equality alone is insufficient for pointer identity, provenance or reused allocations. Alienation does not synthesize an eq method. Concrete Java identity caching is an implementation policy, not a universal foreign identity law or an implemented C FFI.

Expats — VarioHyve Objects Outside VarioHyve

An Expat reenters native semantics through a behavioral interface. Its public contract exposes no store, address, activation, private initializer or VM representation. Adapters may privately retain what execution requires. The exact-send interfaces, VHExpat.send within an attached invocation and ExpatReceipt.send under an explicit retention receipt, include zero-argument access; they do not apply source invocation’s callable-binding fallback. To use a stored callable, read the binding and send apply/N to the result explicitly.

Expat Surface

Without language access control, an Expat exposes the same source-visible behavior available to an external native caller, including generated accessors. Backend-private construction routines are not selectors. Proposed export control must preserve equality of the native external interface and the foreign export interface.

Expat Identity

A native object has at most one Expat proxy per compatible foreign runtime. Exporting it repeatedly through different paths returns the same proxy. Retention receipts are separate capabilities for this identity. Independent receipts may concern the same proxy; their own host identities are not the native object’s identity. A proxy alone does not keep its native referent alive or authorize use after its invocation attachment expires.

Cross-runtime references require an explicit bridge. Conversion by value instead follows a declared codec and may normalize host representations; it does not promise preservation of their object identity.

Operation Results

An Alien send returns the operation’s ordinary result through the declared conversion protocol, just as a native send returns its method result. There is no automatic Alien-only ok(value) | AlienError(error) wrapper and no required sum result. Such an outcome protocol is one optional contract an operation may explicitly promise, equally for native and foreign implementations. The boundary does not infer failure from an ordinary returned object’s shape, class name or truth value. Defined exceptional completions remain diagnostics under Error Propagation.

Primitive Marshalling

Numbers, strings, booleans and null may cross by value instead of through proxies. Each adapter must state its supported domains and reject unsupported conversions. A numeric encoding must not silently turn a pointer into an integer while claiming to preserve its provenance.

Canonical null and Boolean roles may hold native objects or Aliens. Assigning one of these roles adds neither methods nor a native class. The internal core null constant and empty expressions select canonical null directly; source names such as null, true, and false use ordinary message lookup.

Each world selects an explicit conversion profile. The Current Native Seed profile uses ordinary native objects and maps their exact identities to Java null, Boolean.TRUE, and Boolean.FALSE, without Expats. Incoming host scalars recover those canonical identities. Conversion never sends toString, isNull, not, or a truth-testing message to classify another object. Similar behavior or a source name does not make an object canonical.

The Host Seed instead preserves its foreign canonical payloads. A world may separately preserve numbers and strings as foreign values while using native canonical null and Booleans. Preserved values obey the originating adapter’s identity laws; by-value codecs obey their declared value relation. Neither policy silently overrides the other. The supported Java subset is recorded in the implementation.

The startup installation contract requires a participating boundary to repair its managed references and retire provisional ownership before publication, consistently with the final codec. It cannot rewrite opaque foreign heaps or leave obsolete mappings that recover retired native addresses. This adds no live-replacement exception to published identity laws and supplies no general foreign garbage collector.

Explicit Wrappers

A native wrapper supplies its own identity, scope and behavior around foreign values. Multiple wrappers may share one Alien without sharing native identity. For example, a callable capability can operate on an opaque handle:

class Device(deviceHandle, reader) {
    handle = deviceHandle;
    readFn = reader;
    read(buffer) { readFn(handle, buffer) }
}

This is explicit adaptation, not a built-in calling convention. Persistent dependencies use slots under the ordinary constructor-scope rules.

Constructor Arguments and Optional Bundles

Aliens, native objects and bundles can be ordinary module constructor inputs. The same conversion contract applies in richer tooling contexts; it does not add capabilities to an isolated module root.

Control and Failure Agreements

Error Propagation

Selector absence is distinct from a selected operation’s failure. Failures cross as defined diagnostics, never as retained host exception objects, classes or causes. The Java categories FOREIGN_FAILURE, CONVERSION, OWNERSHIP and EXECUTION_POLICY survive machine execution and callback propagation; native lookup/control errors use LANGUAGE_FAILURE.

Callbacks use ordinary native semantics and preserve state changes. A failed callback aborts its own native continuation, retires its invocation homes and reports a defined diagnostic to its foreign caller. It does not automatically fail the suspended native caller. Foreign code may handle the diagnostic, make further callbacks and return normally, or propagate a failure. The outer NF send observes the foreign operation’s completion, subject to normal result conversion and execution limits. A propagated diagnostic preserves its kind; a later foreign failure is reported as that failure, not replaced by an earlier handled one.

The Java diagnostic also carries detached best-effort crossing evidence: direction (native to foreign, foreign to native, or host entry), phase, selector and arity, optional source site, and invocation progress. It distinguishes admission, selection, argument conversion, execution/callback and result conversion. Not dispatched describes this invocation only, not earlier argument effects. Completed records a normal invocation return even when result conversion then fails. A thrown foreign failure conservatively records completion unknown; these fields do not promise rollback, cancellation or safe retry.

The original failure kind, reason, source and semantic trace survive propagation. Each actually crossed boundary adds its own evidence, innermost first. Reusing the same crossing during propagation does not duplicate it; recursive calls with the same selector remain distinct. Crossing evidence uses the configured trace limit (five by default, or all), independently of semantic and private physical frames, and reports truncation. Handling a callback failure adds no evidence to later independent outcomes.

Selector absence remains a lookup result until lookup has finally failed; a foreign callable eligibility probe must not become fatal merely to produce a diagnostic. Explicit adapter rejection can carry FOREIGN_REJECTION; arbitrary exception text is never interpreted as rejection or as permission to retry.

Effects already performed are not rolled back. Handling a callback failure does not resume the aborted callback, revive its homes, replay the operation or grant NLR crossing. The suspended caller’s homes remain live until its own completion or failure. Callbacks continue to share the active execution budget; handling an exhaustion diagnostic does not replenish it. There are no native resumable conditions in the current language. See the accepted recovery agreement.

Java host exit limits

The adapter preserves a supplied BoundaryException and its defined kind. It translates other RuntimeExceptions thrown by ForeignObject.resolve into FOREIGN_FAILURE with a resolution reason. Effect-free lifetime metadata selection uses the same failure category and selection evidence, before argument conversion or invocation. Host scalar protocol resolution remains outside that translation catch. Before invocation, argument export annotates defined boundary failures without broadening its catch to other host failures. The existing invocation catch translates Exception from suspension, the selected operation, resumption and result import into FOREIGN_FAILURE; defined conversion/ownership/policy exceptions retain their original kind. Phase/progress evidence locates the translated failure without retaining its host exception object or cause.

JVM Error and native backend invariant failures outside these existing catches are not translated into ordinary language failures. No additional host-loss, cleanup or recovery contract is introduced here; abnormal host exit handling beyond today’s adapter remains deferred.

Non-local Returns Across the Boundary

The boundary is the agreement between native and foreign participants. That agreement owns whether a non-local return may cross a foreign invocation and how the crossing is handled. The native language cannot prescribe how arbitrary foreign execution unwinds or otherwise transfers control.

The default agreement forbids crossing. A callback may return to an accessible home created inside that callback; an attempt to reach a live home across an active foreign-call barrier fails with LANGUAGE_FAILURE. The failure is reported to the foreign caller under the recovery agreement above. This is the only crossing agreement implemented by the current Java boundary.

A boundary may explicitly support crossing under a future agreement. It is responsible for implementing that agreement, including its observable control flow and treatment of intervening foreign work; the foreign-side mechanism is not fixed by VarioHyve. Every intervening boundary must support the requested transfer. Such support does not change the lexical target of ^, revive a retired home, or bypass initializer phase restrictions. Crossing support and its transfer protocol are deferred; the default barrier must not be disabled without implementing a supporting agreement. See the accepted decision and examples.

Control Tokens and Execution Agreements

Ordinary native transitions require execution authority under an explicit execution agreement. The current sequential agreement has one conceptual control token per live runtime. It governs advancement of ordinary native continuations and their NF/FN control transfers. A suspended continuation has no independent authority to advance. The token is neither a language value nor an additional capability that programs must pass; implementations need not reify it. A refinement argument must account for the authority using the implementation’s actual synchronization and state.

The token may be idle at the boundary, assigned to a native continuation, or assigned to a foreign invocation. Independent FN entry acquires the existing idle token. NF transfers it to the selected foreign invocation; admitted callback entry transfers it to a new native continuation. Callback success or failure returns it to that invocation; foreign completion transfers it to the suspended native caller only after admitted descendants finish. Independent native completion returns it to the idle boundary. Nested calls retain suspended continuations and interaction state, not additional control tokens. Backend tooling may also yield after a requested step and later reacquire authority to advance its retained successor. Yielding is not native completion and does not retire homes; storing a configuration grants neither execution authority nor a snapshot of the mutable runtime.

This is an execution discipline, not exclusive physical access to all runtime memory. It permits three distinct forms of activity:

ActivityAuthority and correctness obligation
Ordinary evaluation and callbacksExecution authority under the active agreement; preserve continuations, admission and boundary transfers.
Representation maintenance and optimizations, including concurrent GCImplementation refinement of the agreed semantics and observations; no second ordinary native continuation is implied by concurrent implementation work.
Explicit observation or interventionA granted capability with a declared effect and coordination contract; it may intentionally change abstract program state without owning the ordinary control token.

An observation or intervention contract must specify its subjects and scope, permitted effects, consistency and coordination with execution, authority lifetime, and completion/failure behavior. Reading live state requires a defined consistency model. Changing a slot, pausing execution or replacing a continuation requires an explicit intervention contract; it cannot be justified as invisible maintenance. Such authority does not implicitly grant arbitrary evaluation, additional ordinary continuations, NLR crossing, dead-home revival or relaxed initializer rules. Language-visible VM services, debuggers and language monitors remain explicitly supplied Aliens using ordinary boundary sends. No general intervention API is implemented by this agreement. All agreements preserve fixed lookup, identity, return-home lifetime and initializer phase rules. NLR crossing still requires an explicitly supporting boundary agreement.

Implementations may use parallel work, concurrent collectors and boundary optimizations without a global representation lock. They must preserve logical identity, return-home liveness, roots and agreed observations, and coordinate their concrete data structures correctly. An optimization cannot silently replay foreign effects or change their specified ordering. Boundary bookkeeping, such as recording a pending request or an arriving completion, does not itself advance a native continuation.

A richer execution agreement may explicitly authorize simultaneous native transitions, including a model checker’s request to execute proven independent transitions on a parallel VM. It must specify execution authority, shared-state and observation semantics, and applicable independence or synchronization conditions. Token uniqueness is a property of the sequential agreement, not a universal serialization requirement. The accepted extension principle and the remaining implementation work are separated in Concurrency and Parallelism.

Concurrency Boundary

The boundary supports synchronous same-thread callbacks and explicitly call-associated worker callbacks. Native execution remains serial over one runtime/store under the sequential agreement. Each NF invocation suspends and roots its native caller, transfers the conceptual control token, and records its call ancestry. An admitted FN callback acquires that authority, runs a separate native continuation, and shares the active budget. Nested NF calls repeat this protocol.

Foreign code captures a CallbackContext on its own active operation thread and may explicitly pass it to a worker. Its send requires an Expat from the same runtime with valid attachment or receipt evidence; the context grants permission to request admission, not receiver authority or possession of the control token. Contexts may be copied among workers; competing requests negotiate access to the unique token. Expats obtained before the NF invocation remain valid targets under open retention receipts. Unassociated entry on another thread during an active execution is rejected, as is callback entry during selection. Neither thread identity alone nor possession of an Expat grants admission to an outstanding foreign call.

Only callbacks associated with the innermost active foreign invocation may acquire native execution permission. Other associated requests wait for their turn without running native code. A descendant operation cannot synchronously use an ancestor context to wait on its own completion; that request is rejected. There is no FIFO or fairness guarantee. A future FIFO policy must respect call eligibility: a waiting ancestor request cannot block a needed descendant callback merely because it arrived first. Foreign completion closes admission, rejects queued or late requests and waits for already admitted descendants to finish before importing the result and resuming its native caller. A foreign result can arrive while a callback owns the token; arrival is recorded, and delivery waits for ownership transfer. Retained call contexts cannot attach to a later invocation. This preserves the existing NLR barriers and callback-local failure contract.

This protocol provides no preemption or termination guarantee: foreign work or an admitted descendant may never finish, and foreign dependencies may deadlock. Independent-entry scheduling, detached asynchronous native tasks and parallel native execution remain outside this contract. Execution limits belong to the implementation policy.

Lifecycle and Garbage Collection

The boundary registers shared retention obligations, independently of execution authority, mutation permission and resource validity. Several holders may retain the same referent. A holder releases its own obligation; it neither releases another holder’s claim nor closes a shared resource. Public raw addresses are not a substitute for a lifetime contract.

Invocation attachment

Expats exported as NF arguments are attached to that particular invocation by default. The attachment starts before exposure to foreign code and protects their native graphs until result conversion and all admitted descendants finish. Callback entry and return transfer the conceptual control token but do not end the enclosing invocation’s attachments. Nested NF invocations register their own attachments independently. A live ancestor’s attachment also protects use and transport within its descendant interaction tree; nested foreign helpers need not detach or re-export every alias merely to use it before the ancestor completes. This does not widen detachment permission: registration still cites an authorized argument or result of its owning invocation. Closing callback admission does not itself expire attachment or detachment authority: already admitted work may register authorized receipts while the invocation waits for its descendants and completes result conversion.

The selected operation declares which argument positions permit detachment. This metadata is available before argument conversion and operation execution; it does not cause automatic retention. An explicit detach registers an independent receipt while the authorized attachment is open, before publishing the retained reference. Permission belongs to an argument occurrence, including when several positions contain the same native object. Missing permission means attached-only. Undeclared or late detachment fails without creating a lasting root and without repeating selection or execution. Detachment also requires possession of the Expat being retained; naming an argument position through a callback admission context does not grant access to that argument. The boundary validates the supplied proxy against the occurrence.

An adapter may perform this registration on behalf of a foreign API that stores its arguments. The foreign implementation need not adopt VarioHyve’s collector or a static ownership discipline. The declaration is a promise on which the boundary may act; a proof of foreign code is not required. Optional analysis or review evidence may support the promise, but grants no additional authority and does not replace runtime checks under this agreement.

Results, receipts and checked use

Native results from FN callbacks attach to the enclosing NF invocation. They may outlive the callback but need a separate declared callback-result permission and explicit detachment to outlive that invocation. Permission to detach a parent argument does not authorize detaching every object returned by its accessors. An independent host native result, including module construction, has no enclosing invocation: by-reference export delivers a host retention receipt. Public opaque boundary references likewise carry an explicit releasable hold. By-value codec results need no receipt; compatible Alien round trips follow the foreign domain’s own retention rules.

A receipt supplies checked sending and transport for its canonical Expat. Closing it is idempotent and ends only that receipt’s obligation. Acquiring an independent co-hold creates another receipt; copying one receipt shares the same obligation. Closing one co-hold leaves the others valid. The last release makes an otherwise unreachable native graph eligible for collection, without requiring immediate collection.

Every mediated use and conversion validates the evidence supplied for that use. An expired attachment or closed receipt fails before native access even when another holder keeps the referent alive. Re-export does not revive a closed receipt. A bare canonical proxy is usable only under a currently applicable invocation attachment; outside that context it requires receipt evidence. Copies of a proxy used within the same valid attachment are ordinary aliases: the boundary cannot infer which foreign variable originally acquired that identity. Nor can it observe every hidden store into an opaque foreign heap. It diagnoses observable use without valid evidence, not necessarily the earlier hidden escape.

Lifetime violations use OWNERSHIP, independently of EXECUTION_POLICY for callback admission and LANGUAGE_FAILURE for retired return homes. Retention keeps captured data available; it never revives a return home, extends a CallbackContext, enables NLR crossing or replenishes an execution budget. Checked handles do not make arbitrary foreign raw-pointer operations safe.

Receipt release and admission coordinate so an already admitted use retains its target through completion; subsequent use of a closed receipt fails. Every handoff establishes the receiving root before dropping the sending protection, including an NF result that returns an attached argument unchanged. Partial argument conversion and defined exceptional completion close the invocation’s own attachments. A failed callback does not close its enclosing invocation, and an outer failure does not revoke detached receipts already published by foreign code. Such retention is an effect, not a transaction to roll back. Broader host termination remains subject to the host exit limits.

Alien holds and cycles

An imported Alien establishes an adapter hold before publication. Native GC traces references to it normally and relinquishes that hold when the Alien becomes unreachable. Slots, captures and returns need no native detachment annotation. The adapter counts obligations between participants, not every native alias. Java may realize a hold as a strong payload reference; a foreign reference counted domain may use its own retain/release protocol. Expiring resources and temporary pointers still need an appropriate domain contract: native reachability cannot prolong an allocation that the foreign participant cannot retain.

Identity caches are non-owning indexes. A live observable proxy remains canonical without making its expired native graph a root. Reclamation and reimport must preserve the foreign referent’s identity and identity hash while that identity remains live, including distinctions between restricted capability views. Expired receipts and diagnostic records must not retain their former targets. Releasing a hold is distinct from globally closing a resource. Observable foreign cleanup requires the adapter’s safe cleanup agreement; it must not run arbitrary foreign code inside native tracing. GC makes no prompt resource-cleanup promise.

Cross-boundary cycles are legal by default. Without collector cooperation the boundary conservatively retains cycles that neither participant can prove unreachable. Every retained strong edge still obeys the attachment/receipt contract; allowing cycles does not authorize unregistered escape. An explicit release can break a cycle, but strong relationships must not silently become weak to obtain collection.

An optional future agreement may distinguish foreign external roots from edges whose retaining owners are traceable, preserving opaque edge identities and provenance. Safe collection requires coordinated reachability and mutation observations, validation before reclamation, and agreed weak-reference, finalization and participant-loss behavior. Missing or incomplete cooperation retains conservatively. No universal foreign collector, introspection mechanism or cycle-collection algorithm is prescribed. See the accepted lifetime decision.

Foreign Kinds and Capability Contracts

An adapter may classify a value as callable, pointer, struct or endpoint; these are foreign contracts, not native classes. Analysis needs explicit assumptions about effects, callbacks, blocking, determinism and state changes. Unknown behavior stays opaque. General contract metadata, provenance registries and foreign reflection remain unimplemented; see the boundary assessment.

VM Services and the Trusted Seed

The host boundary has a public foreign facet and a privileged VM-service facet over one private owner. The public facet exposes only the ordinary transport, explicit mirror grant and call-associated callback admission. Trusted seed provisioning supplies narrow VM service capabilities; public clients have no operation for obtaining the provisioning facet or raw runtime representations. Object’s identity service is provisioned only to its definition scope. The optional public IdentityMirror grants its own limited observations.

Both facets share identity maps, conversion, execution admission, budgets and GC roots. Current services use the same serial admission protocol. Privilege changes authority, not lookup, return or failure semantics; privilege alone grants no additional ordinary native execution. A future independently operating service requires an explicit execution or intervention agreement. The same capability view preserves identity across either route. Distinct restricted views have distinct identities even when they concern one resource. Deliberately exporting a privileged capability delegates that capability; a partition label does not silently attenuate it. No new privilege registry, selector allowlist or native invocation path is introduced.

Language-visible VM services use this same boundary; there is no privileged native-function invocation path. The trusted backend may privately allocate values, maintain stores and implement lookup/continuations. Those internal operations are not language services.

A service returning a native object must return its Expat with valid attachment or receipt evidence, so import recovers the object. Returning its raw backend representation as a foreign value is invalid. Any future representation-sensitive service requires explicit authority and private unwrapping without adding raw-world access to public Expats. See the VM boundary decision.

The admitted source services use this route to evaluate captured source with an explicit object context or instantiate an isolated module. They share active admission, budgets, callback depth, roots and result lifetimes. They expose source snapshots and ordinary values, never syntax trees, activations or the runtime world.

IdentityMirror

IdentityMirror is an explicitly supplied capability for observations that must not dispatch through the subject. A host obtains it with runtime.boundary().identityMirror() and can pass it as an ordinary module constructor argument. It is not installed in the kernel or exposed by Object. The Java public interface uses the same ForeignObject selector protocol as other services; it grants no store, address or runtime access.

Identity and kinds

Identity comparison is reflexive, symmetric and transitive on its supported domain. It observes native identity or adapter-preserved Alien identity, never semantic equality or remote resource equivalence. Compatible round trips preserve identity and hashes; same identities hash equally, but collisions are permitted. Hashes are neither addresses nor stable across sessions. A wrapper and its payload differ; differently restricted handles must not be merged merely because they refer to the same resource. Ownership failures require an explicit bridge.

The supported kind labels are exactly "Object" and "Alien", case sensitive. Object includes native instances, class objects, metaclasses, and lambdas. Native canonical null and Booleans belong to Object; canonical values implemented as Aliens belong to Alien. Canonical roles do not override representation kind. Alien also includes opaque foreign references, preserved host scalars, and VM services exposed through the adapter. It does not imply callability or trust. Classification is relative to the observing runtime; importing its owned Expat recovers a native object.

Current integer/string codec values belong to neither kind and have no native class or mixin membership. Identity operations on them, including mixed same queries, fail with CONVERSION; interning does not specify scalar identity. Preserved foreign scalars instead use their adapter’s identity and Alien kind; see Possible Seeds and Worlds. Thus isNative is not implemented as the negation of isAlien. Object’s default equals with a codec scalar still returns false because its receiver is native. An unknown kind label fails with LANGUAGE_FAILURE, a non-string kind label with CONVERSION, and a missing selector/arity follows ordinary lookup failure.

Class and contribution references

The second argument of both membership queries is a native class reference, obtained through ordinary messages or explicit capability provision. For an ordinary class, it is the same definition object usable in superclass and mixin applications. instanceOf uses that class’s identity; applies selects that class’s owned reified mixin, just as <: C does. It does not send an ownedMixin accessor or require a separately exposed mixin token. The query does not resolve a name or consult a class registry. Names and hashes, including old anonymous labels, are not targets.

instanceOf starts at the receiver’s actual class and follows superclasses through root Object, inclusive. It returns at the first matching class identity. It does not treat a mixin application’s source class as a superclass.

applies walks the same linear contribution order used for native dispatch: the class’s owned contribution, its direct applications left to right, then its superclass’s owned contribution and direct applications, continuing through Object inclusive. It returns true at the first match and false after the chain is exhausted. Matching compares the reified contribution’s identity, not its syntax, name or semantic equality. An application contributes only the selected source’s owned mixin; this query does not traverse that source’s superclass or applications. Owned, inherited and repeated contributions are included without collapsing occurrence identities or executing construction routes.

Anonymous and named definitions follow identical identity rules. Distinct class evaluations and distinct per-enclosing-receiver member realizations remain distinct even when they share a declaration or name. Aliases to the same class select the same identity and owned mixin. No identity hash participates in membership, so hash collisions cannot change an answer.

For a class object, queries inspect its metaclass hierarchy and class-side contributions; they never switch to the represented class’s instance hierarchy. The target rule remains the same: C denotes C itself or C’s owned instance-side mixin, not its metaclass’s contribution. In particular, instanceOf(C, C) and applies(C, C) are normally false. If a metaclass reference is explicitly supplied, it can select that metaclass or its owned class-side contribution. This does not add a public class/metaclass getter.

Both arguments undergo ordinary boundary ownership validation. A non-class target, including a string, canonical null, ordinary instance or foreign object, fails with CONVERSION; an unowned class fails with OWNERSHIP. Invalid targets fail even when the subject is an Alien or codec value. With a valid target, Aliens and codec values return false because they have no native membership.

These are structural identity tests, not proofs that a selector is supported or that a contribution’s behavior remains effective after overriding. They do not establish trust in a subclass or authorize its behavior. The design note records the routing and capability tradeoffs.
