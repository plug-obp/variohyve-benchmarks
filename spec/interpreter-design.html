VarioHyve Language Specification

Interpreter Design

The v1 interpreter is an AAM-style CESK machine — a small-step abstract machine with four components:

  • Control — the current AST node being evaluated
  • Environment — a mapping from names to store addresses
  • Store — a mapping from addresses to values
  • Kontinuation — a stack of frames representing what to do next

The interpreter runs by repeatedly applying a transition function step : State → State until a final state is reached.

Current implementation note: The visitor machine represents lexical scope with activation objects, not a separate Environment class. Method and initializer invocations establish private return homes. CallReturnFrame implements method completion; InitializerReturnFrame completes one initializer contribution, discarding its value and preserving the construction receiver. ReturnFrame below is a design-level name from an earlier interpreter sketch, not a current Java class. Configurable allocation alone does not provide the abstract interpretation described as a goal in this chapter.

Module Instantiation Requirements

Named and anonymous class literals receive capabilities through inheritance, mixin composition, lexical nesting and constructor parameters. Normal module definition starts in an empty top activation: no capability bindings, no capability-bearing lexical parent or receiver, and no enclosing application scope. The activation frame still exists. Such a class has only root Object inheritance and no mixins. The instantiation service supplies existing object arguments at the declared constructor arity. A kernel is an optional bundle, not a mandatory single input.

The machine must bind constructor parameters using activation objects and must not expose those bindings as instance-method scope or retain an automatic edge from an instance to its own initialization activation. Ordinary lambdas and class expressions can deliberately capture that activation. Member-class declarations instead bind to the enclosing instance and retain their declaration/application origin. Activations remain backend-private, with no public reification. The machine must not capture the service’s or caller’s scope. Class creation and subsequent instance construction are distinct: constructor arguments cannot supply that top-level class’s own superclass or mixins. Nested class definitions may use class/mixin objects available through their enclosing module. See Program Structure.

Tools may explicitly supply a richer evaluation activation or select a debug activation. These contexts use the same object-based scope and invocation rules, and values created there retain their actual lexical captures. The current kernel-injected expression harness is an example of supplied evaluation context: its lack of local slots does not make its parent/receiver capability graph empty. The separate BootstrapRuntime.instantiateModule path evaluates a class literal over an empty top activation and constructs it through an exact Expat new send. Definition, initialization and synchronous callbacks share one transition budget; host sends contribute an empty caller scope. The instance is returned as an Expat, and its entry method is invoked explicitly by the host. See Evaluation Contexts.

Machine Components

Addresses and Allocation

Every binding goes through the store via an explicit address. Values are never stored directly in the environment.

Env   = Map<Name, Addr>
Store = Map<Addr, Value>
Alloc : Context → Addr

The Alloc function is the single parameterization point:

  • Concrete allocation — returns a fresh integer on every call. This is the v1 interpreter.
  • Abstract allocation — returns a bounded address derived from the call site and a prefix of the environment (k-CFA). This enables finite-state analysis.

The interpreter core is written once; swapping Alloc switches between concrete execution and abstract analysis.

Values

All runtime values live in the store. The full runtime representation — objects, classes, mixins, metaclasses, method activations, and dispatch origin tracking — is defined in the Object Model.

The key points for the CESK machine:

  • Objects hold slots and point to their class and internal definition scope. Public outer ClassName is declaration-relative, not a lexical-parent getter.
  • Classes hold methods and point to their super, mixin list, and metaclass.
  • Mixins are regular objects — no special runtime type.
  • Method activations are objects in the store — their var locals are slots, their parameters are read-only entries. This uniformity is what makes activation-as-object semantics (and closure capture) fall out naturally.
  • Dispatch origin is tracked per activation so super knows where to resume in the class/mixin chain.

Continuations

The continuation is an explicit linked list of frames. Each frame records what work remains after the current sub-evaluation completes:

  • MessageFrame — receiver evaluated, waiting for arguments; then dispatch
  • ArgFrame — evaluating argument list left to right
  • SeqFrame — statement list; evaluate next statement
  • ReturnFrame — conceptual method boundary; the current visitor uses CallReturnFrame and a private activation that tracks home liveness
  • InitializerReturnFrame — ends one initializer contribution and resumes its continuation with the allocated receiver, ignoring the body’s result
  • Private initializer-call frame — evaluates the receiver and arguments of an identity-bound invocation before entering a fresh initializer activation
  • Private slot-write frame — completes an initializer expression, writes its value through the receiver’s complete storage layout, then resumes ordinary expression sequencing

^ targets its lexically captured method or initializer home. Each initializer invocation has a fresh home even when its class captures an earlier activation. When ^ is evaluated, the continuation chain is scanned for that exact home; it never chooses the nearest dynamic method or borrows the caller’s home.

  1. Method or initializer entry establishes a fresh live home and the corresponding completion frame. An initializer begins in the slot phase.
  2. Normal completion retires the home. A method delivers its body result; an initializer ignores its result and resumes the contribution continuation with the receiver.
  3. ^ evaluated checks the captured home’s liveness and matching frame. Missing/retired homes produce a dead-context error. A live initializer target still in its slot phase produces a premature-completion error, including a return before the final slot value is assigned. A post-slot initializer target completes only its contribution and ignores the returned value. A method target returns that value normally.
  4. Failure or unwinding retires intervening homes. An outside lambda retains its own target and can unwind construction to it if live. An active Alien-call barrier forbids unwinding across that boundary.

The return expression is evaluated normally before delivery; failure there is not a successful early exit. Home liveness is separate from reachable captured data. See Initializer completion and the accepted policy. Explicit continuations implement these transitions without using host exception unwinding as the language’s return semantics.

State Transitions

Class realization finalizes its immutable complete instance layout and retains resolved initialization edges. Formals and the anonymous slot/post-slot initializer belong to each reified instance mixin. Direct mixin edges refer to the selected owned mixin, while superclass edges refer to the complete class. Allocations reuse the class’s physical layout and preserve shared-name storage. Each generated accessor resolves its selected contribution occurrence and local slot number through the actual receiver class’s immutable logical-to-physical mapping.

Class realization generates ordinary CoreUserFunction bodies for primary new, each owned contribution initializer and the class’s coordinator. ClassTargetFrame resolves native class targets before publication; MemberClassReturnFrame completes the declaration/application cache.

Primary new is installed on the owned class-side mixin and follows ordinary lookup and method invocation. Its body allocates the bound class’s receiver, invokes the private coordinator, and returns that receiver. The coordinator sequences superclass and applied-owned-mixin invocations with ordinary core expressions, then executes its own initializer body in the same activation/home. An applied mixin never follows its source class’s original dependency routes. Object literals run this same generated construction path.

Backend-private ConstructionCode operations provide bound-class allocation, identity-bound initializer invocation, direct slot writes and an explicit slots-complete marker. A slot write resolves its contribution-local number using the active initializer’s occurrence and actual receiver layout before evaluating the value expression, then retains the destination in its continuation. The marker separates mandatory slot initialization from the optional final body; a return before the final slot write remains invalid. Private call arguments and writes use explicit continuations, while ordinary expression sequencing replaces the former contribution/slot schedule frames. No source or Expat selector selects a private initializer.

Empty argument lists still pass through the machine scheduler, so deep initialization does not recurse on the host stack. Failure or unwind retires initializer homes and caches in-progress member realization as a defined failure. See the construction operation contracts.

Explicit Store: The Key Commitment

The one structural decision that enables the AAM path: the store and allocation are explicit from day one. Objects live in the interpreter’s own Store, not on the Java heap.

This costs almost nothing in v1:

  • A HashMap<Integer, VHObject> with an incrementing counter is a concrete store.
  • Slot reads and writes go through store.get(addr) / store.put(addr, value) instead of direct field access.

But it unlocks the full AAM abstraction path later: replace the concrete store with a store that joins on write, replace Alloc with a k-CFA allocator, and the interpreter becomes a sound abstract machine — without rewriting the core step function.

Connection to Analysis Tools

The CESK design connects directly to the Tooling Architecture:

  1. Concrete CESK → v1 interpreter. Deterministic, one successor state per step.
  2. Abstract CESK → static analysis tool. Non-deterministic, returns a set of successor states per step. Explores all reachable abstract states to compute program properties.
  3. External annotations (via descriptor names) tell the abstract instantiation what abstract values to assume for named elements — e.g., type constraints, intervals, or contract pre/post-conditions.

This follows the approach of Van Horn and Might (2010), Abstracting Abstract Machines: a systematic method for deriving sound abstract interpreters from concrete machines by parameterizing over address allocation.

TCO and Continuations

Because continuations are explicit, tail-call optimization is a natural extension: a tail call in tail position pops the current ReturnFrame before pushing the callee’s frame. TCO is introduced incrementally in layers — from no optimization (v1 bootstrap) through direct tail calls to non-local-return-as-tail-return — all as local changes to the step function’s frame-push logic. See Future Directions for the full layered design.

Stack Safety

The CESK machine runs as a flat while (!isFinal(state)) { state = step(state); } loop. The continuation K is a heap-allocated linked list — the host language’s call stack is not involved in VarioHyve recursion. This means:

  • No stack overflow. A VarioHyve program that recurses 10 million times deep will not crash with a StackOverflowError. Each recursive call allocates a continuation frame on the Java heap, not on the JVM thread stack.
  • Graceful degradation. Without TCO, deep recursion consumes heap memory proportional to the recursion depth (one continuation frame per call). This is bounded by available heap (gigabytes), not by the JVM’s thread stack size (typically 512KB–1MB). The program may eventually run out of memory, but it degrades gracefully with GC pressure rather than crashing abruptly.
  • TCO as a space optimization. In this context, TCO is not needed for correctness or crash prevention — it is a space efficiency optimization. A tail call in tail position can reuse the current continuation frame instead of allocating a new one, reducing heap allocation from O(n) to O(1) for tail-recursive loops. See Clinger (1998) for the formal treatment of proper tail recursion as a space efficiency property.
