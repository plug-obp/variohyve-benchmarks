VarioHyve Language Specification

Interpreter Design

The v1 interpreter is a CESK-inspired small-step machine and a starting point for experiments with Abstracting Abstract Machines (AAM). Its components are:

  • Control — the current evaluation, send, value or error
  • Environment — lexical scope represented by activation and enclosing objects, using the object protocol rather than a separate name-to-address namespace
  • Store — a mapping from addresses to values and continuation frames
  • Kontinuation — a linked chain of frames representing what to do next

VisitorSemanticsVM executes a Configuration(control, environmentRef, runtimeWorld, continuationRef). The environment reference identifies an activation or lexical object scope, and the runtime world supplies the store and boundary. Control distinguishes expression evaluation, an exact send, a selected foreign call, a returned value and a terminal error.

The Java step API returns a set of successors. The concrete driver requires exactly one successor for every nonterminal configuration and stops at an error or a value with HaltFrame. That API shape does not implement nondeterministic or abstract execution. Configurations share a mutable runtime world; keeping an earlier configuration does not create a snapshot of its store.

The implementation anchors are VisitorSemanticsVM, EvaluateStepVisitor and ContinuationStepVisitor. Method and initializer invocations establish private return homes. Scope and continuation representations are backend-private, not public language objects or reflection APIs.

Module Instantiation Requirements

Named and anonymous class literals receive capabilities through inheritance, mixin composition, lexical nesting and constructor parameters. Normal module definition starts in an empty top activation: no capability bindings, no capability-bearing lexical parent or receiver, and no enclosing application scope. The activation frame still exists. Such a class has only root Object inheritance and no mixins. The instantiation service supplies existing object arguments at the declared constructor arity. A kernel is an optional bundle, not a mandatory single input.

The machine must bind constructor parameters using activation objects and must not expose those bindings as instance-method scope or retain an automatic edge from an instance to its own initialization activation. Ordinary lambdas and class expressions can deliberately capture that activation. Member-class declarations instead bind to the enclosing instance and retain their declaration/application origin. Activations remain backend-private, with no public reification. The machine must not capture the service’s or caller’s scope. Class creation and subsequent instance construction are distinct: constructor arguments cannot supply that top-level class’s own superclass or mixins. Nested class definitions may use class/mixin objects available through their enclosing module. See Program Structure.

Tools may explicitly supply a richer evaluation activation or select a debug activation. These contexts use the same object-based scope and invocation rules, and values created there retain their actual lexical captures. The current kernel-injected expression harness is an example of supplied evaluation context: its lack of local slots does not make its parent/receiver capability graph empty. The separate BootstrapRuntime.instantiateModule path evaluates a class literal over an empty top activation and constructs it through an exact Expat new send. Definition, initialization and synchronous callbacks share one transition budget; host sends contribute an empty caller scope. The instance is returned as an Expat, and its entry method is invoked explicitly by the host. See Evaluation Contexts.

Machine Components

Addresses and Allocation

The concrete machine uses an explicit store and allocator. Parameters and locals belong to activation objects; source access follows generated accessor messages. The following notation describes backend storage, not a separate language environment or a public address API:

ValueRef        = value address with a long identifier
ContinuationRef = continuation address with a long identifier
Entry           = Value(VMValue) | Continuation(ContinuationFrame)
ConcreteStore   = Map<Address, Entry>
Allocator.next(environmentRef, continuationRef) -> long

The store interface provides set-valued reads, while ConcreteStore holds exactly one entry per allocated address. The concrete allocator returns fresh increasing identifiers. Concrete singleton reads reject multiple entries; join rejects conflicting entries. Reusing addresses is therefore not an available abstract execution mode.

Allocation is one part of a possible abstraction:

  • Concrete allocation — returns a fresh integer on every call. This is the v1 interpreter.
  • Abstract allocation (proposed) — may return a bounded address based on program location and calling context. Reusing addresses requires an abstract store that safely combines the represented values.

Changing the allocator alone does not produce an analyzer. Abstract values, store updates, control representation, transition rules and foreign effects must all be accounted for, with a soundness argument relating the analysis to concrete execution. A finite-state analysis also needs to bound all relevant state components, not just allocation. These are future obligations.

Values

Value references resolve to VMValue entries. Continuations occupy separately typed store entries; method syntax and construction metadata can be retained inside those values without their own store addresses. See Object Model for the semantic relationships.

  • VMObject holds a mutable array of value references, slot declarations, a class reference, a lexical parent and a hidden member-class cache.
  • VMClass and VMMetaclass extend that representation. A class retains references to reified contributions, its superclass, initialization edges, complete layout and private coordinator.
  • VMMixinClosure is a dedicated closure value retaining the contribution’s syntax, definition scope, formals and generated initializer. It is not a VMObject with a public class or method protocol.
  • Activations extend VMObject internally, with no class reference in the bootstrap. Method/lambda parameters are immutable slots; lowered var locals occupy separate let activations. A LexicalObjectScope associates a receiver with a particular declaration/application origin and its definition scope.
  • VMLambdaClosure retains its function, captured scope, receiver and return home. Its exact apply/N operation is intrinsic to dispatch.
  • Canonical null and booleans are native objects with ordinary methods. Integer and string literals currently use private VMPrimitiveValue entries without native class dispatch. Aliens retain foreign semantics through the boundary; they do not acquire a native class or lexical outer.

Continuations

Continuation frames are stored by ContinuationRef. Linked frames retain the reference of the next frame and the state needed to resume work. The current frame types are:

FrameWork resumed when a value arrives
ReceiverFrameEvaluate a send’s arguments after its explicit receiver
ArgFrameContinue evaluating arguments left-to-right, then dispatch
LetFrameBind a local or complete a sequence step, then advance the lowered let expression
CallReturnFrameRestore the caller’s scope; retire a method home when present
DoReturnFrameDeliver the evaluated return expression to its captured home
ClassTargetFrameRetain a resolved contributor and continue class realization
MemberClassReturnFrameCache a realized member class and restore its caller
ApplyFrameInvoke a selected, newly realized member class with the saved arguments
InitializerCallFrameEvaluate a private initializer call’s receiver and arguments
InitializationWriteFrameWrite a slot value at the already resolved physical index
InitializerReturnFrameRetire one initializer home and deliver the allocated receiver, ignoring the body’s value
HaltFrameMark final value delivery

Sequence evaluation uses lowered CoreLetExpression steps and LetFrame; there is no separate SeqFrame. CallReturnFrame is also used to restore scope after lambda calls and let expressions, without creating a new return home.

^ targets its lexically captured method or initializer home. Each initializer invocation has a fresh home even when its class captures an earlier activation. When ^ is evaluated, the continuation chain is scanned for that exact home; it never chooses the nearest dynamic method or borrows the caller’s home.

  1. Method or initializer entry establishes a fresh live home and the corresponding completion frame. An initializer begins in the slot phase.
  2. Normal completion retires the home. A method delivers its body result; an initializer ignores its result and resumes the contribution continuation with the receiver.
  3. ^ evaluated checks the captured home’s liveness and matching frame. Missing/retired homes produce a dead-context error. A live initializer target still in its slot phase produces a premature-completion error, including a return before the final slot value is assigned. A post-slot initializer target completes only its contribution and ignores the returned value. A method target returns that value normally.
  4. Failure or unwinding retires intervening homes. An outside lambda retains its own target and can unwind construction to it if live. An active Alien-call barrier forbids unwinding across that boundary.

The return expression is evaluated normally before delivery; failure there is not a successful early exit. Home liveness is separate from reachable captured data. See Initializer completion and the accepted policy. Explicit continuations implement these transitions without using host exception unwinding as the language’s return semantics.

State Transitions

Class realization finalizes its immutable complete instance layout and retains resolved initialization edges. Formals and the anonymous slot/post-slot initializer belong to each reified instance mixin. Direct mixin edges refer to the selected owned mixin, while superclass edges refer to the complete class. Allocations reuse the class’s physical layout and preserve shared-name storage. Each generated accessor resolves its selected contribution occurrence and local slot number through the actual receiver class’s immutable logical-to-physical mapping.

Class realization generates ordinary CoreUserFunction bodies for primary new, each owned contribution initializer and the class’s coordinator. ClassTargetFrame resolves native class targets before publication; MemberClassReturnFrame completes the declaration/application cache.

Primary new is installed on the owned class-side mixin and follows ordinary lookup and method invocation. Its body allocates the bound class’s receiver, invokes the private coordinator, and returns that receiver. The coordinator sequences superclass and applied-owned-mixin invocations with ordinary core expressions, then executes its own initializer body in the same activation/home. An applied mixin never follows its source class’s original dependency routes. Object literals allocate their receiver and enter the same private coordinator directly; they do not dispatch a public new selector.

Backend-private ConstructionCode operations provide bound-class allocation, identity-bound initializer invocation, direct slot writes and an explicit slots-complete marker. A slot write resolves its contribution-local number using the active initializer’s occurrence and actual receiver layout before evaluating the value expression, then retains the destination in its continuation. The marker separates mandatory slot initialization from the optional final body; a return before the final slot write remains invalid. Private call arguments and writes use explicit continuations, while ordinary expression sequencing replaces the former contribution/slot schedule frames. No source or Expat selector selects a private initializer.

Empty argument lists still pass through the machine scheduler, so deep initialization does not recurse on the host stack. Failure or unwind retires initializer homes and caches in-progress member realization as a defined failure. See the construction operation contracts.

Explicit Store: The Key Commitment

Language values and continuation frames are addressed through the explicit store. The concrete backend implements that store with Java heap objects: ConcreteStore contains a Map<Address, Entry>, and a VMObject contains a mutable array of ValueRefs. A slot is an array location holding a value reference, not a separately allocated binding cell. A getter reads that reference; a setter replaces it after ordinary accessor selection.

Initialization, local binding, member-cache updates and home retirement also mutate backend objects. The explicit store makes references and allocation visible to the interpreter, but does not make transitions pure or configurations persistent. There is no implemented language garbage collector; retained store entries and proxy caches can keep otherwise unreachable values alive.

This explicit representation supports investigation of an AAM derivation. An abstract store with joins and a bounded allocator would be parts of that derivation, alongside abstractions of values and control and models of foreign operations. The objective is to preserve a justified relationship to the reference transitions, not to assume that an unchanged concrete step function already supplies a sound analysis.

Connection to Analysis Tools

The CESK design connects directly to the Tooling Architecture:

  1. Concrete execution → the current sequential interpreter. Native transitions follow fixed rules; observable determinism also depends on the supplied foreign capabilities.
  2. Abstract execution (proposed) → an analysis with sound abstract transitions and a state-exploration or fixed-point strategy appropriate to its domains.
  3. External annotations (proposed) → named assumptions, abstract domains or properties interpreted by a particular analysis tool. Descriptors alone do not implement those checks.

Van Horn and Might (2010), Abstracting Abstract Machines, provides the research inspiration: refactor a concrete machine into a form amenable to systematic abstraction. A corresponding derivation and validation for VarioHyve remain future work.

TCO and Continuations

Tail-call optimization is not implemented. Explicit continuations make it possible to study continuation reuse, but replacing a call frame must preserve captured return homes, their liveness, initializer completion and foreign-call barriers. Popping the current method frame unconditionally would not meet those requirements. See Future Directions for the proposed increments.

Stack Safety

The concrete driver loops over configurations. Native method/lambda calls and initializer calls schedule their bodies through continuation frames, so language call depth is not represented by recursive Java evaluator calls. This supports deep native recursion without consuming one Java stack frame per language call.

Synchronous foreign calls and Expat callbacks do use the host call stack. The current visitor imposes a callback nesting limit of 64 and shares the active transition budget across callbacks. Non-local returns cannot cross an active foreign-call boundary. A transition budget does not preempt a blocking foreign operation; its behavior remains an adapter obligation.

Explicit continuations do not guarantee unlimited execution or graceful memory exhaustion. The concrete store retains allocated values and frames, and there is no language GC or TCO. A program may hit its transition budget or exhaust memory. Reducing continuation depth alone would not establish bounded total space without accounting for these other allocations and retention policies.
