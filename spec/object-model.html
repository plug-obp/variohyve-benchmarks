VarioHyve Language Specification

Runtime Object Representation

This implementation chapter describes VisitorSemanticsVM’s records and links. The language contracts are in Objects and Classes, Slots, Name Resolution, and Message Sends. These Java structures are backend-private; none is a required representation for foreign clients.

Core Structures

The following sketches abbreviate the current value types:

VMObject       = { ValueRef[] slots, slotLayout, classRef?, lexicalParentRef?, memberCache }
VMMixinClosure = { definitionScope, declarationName, mixinSyntax, parameters, initializer }
VMClass        = VMObject + { mixins, superclassRef, initializationEdges, instanceLayout, initializer }
VMMetaclass    = VMClass

VMObject has no per-instance method dictionary. Reified contributions retain method syntax and declarations; ObjectProtocol selects their operations. VMClass.mixins[0] is its owned mixin; later entries are direct applications. Class objects currently have empty value-slot arrays: instance declarations belong to their contributions, and instance values belong to allocated receivers.

VMMixinClosure and method closures remain dedicated VMValue types. VMLambdaClosure is a VMObject with the shared native Lambda class and private function/captured-scope/receiver/origin/return-home fields. Its ordinary Object methods use the closure as receiver; intrinsic apply/N uses its lexical captures. No captured slots, internal closures or activations become public. Activations reuse VMObject storage but have no class reference. A missing Java reference is distinct from the language’s canonical null object. Alien and scalar nodes are described under Java boundary representation.

Applying a reified contribution reuses its identity without importing the source class’s construction or inheritance chain. Mirror membership selects the supplied class’s owned contribution and compares that identity; it requires no naming metadata or reverse link to the owning class.

Store Entries

Evaluating a class expression creates a class/metaclass pair. A member accessor creates that pair on first successful realization. Construction creates its receiver; each object-literal evaluation realizes a fresh anonymous class/metaclass pair with its selected contributors and sends primary new/0 to create the receiver. These are object-graph counts, not total backend allocations: contributions, activations and continuations also occupy representation space.

VMObject.MemberClassKey contains applying class, contribution index and member declaration. The cache lives on the enclosing receiver, completing the semantic key. Each entry records a realized value, a retained failure, or an in-progress flag. ClassTargetFrame sequences target computations; MemberClassReturnFrame publishes a result. Failure and unwind clear the in-progress state and cache the failure, preventing retries and permanently busy entries.

Contribution Occurrences and Layouts

The backend identifies an occurrence by (applyingClass, mixinIndex) and a logical slot by adding its contribution-local position. Inherited occurrences retain their own applying-class identities. Direct applications hold the selected VMMixinClosure, without importing the source class’s construction record.

InstanceLayout collects owned/direct/inherited contributions and interns physical positions by slot name. Its immutable mapping is cached on the realized class. Instances allocate fresh arrays from its physical declarations. Logical identities survive name sharing; physical index order is an implementation choice.

selected slot: (applyingClass, mixinIndex, localSlot)
physicalIndex = actualReceiverClass.instanceLayout.physicalIndex(selected slot)

Accessor mutability and eligibility come from the selected contribution, not from the declaration chosen to represent the physical cell. Initialization uses the same mapping. Ordinary source sends still pass through lookup; only an already selected accessor or private initializer write uses a direct array operation. See the accepted layout decision.

Class Assembly

ClassConstruction resolves contributor targets, creates each distinct metaclass, installs owned factories and finalizes layouts and coordinators. VisitorSemanticsVM retains backend entry points that delegate trusted seeding and anonymous assembly to it. seedClassGraph installs the six root identities implementing the flat graph, plus Lambda and its metaclass. Lambda extends Object and has no public factories. The metaclass has no additional constructor arity, argument routes or initializer fields. The factory contracts specify their public selectors.

Representing Top without Reification

The specification’s Top is the empty constructor of the class algebra. VisitorSemanticsVM deliberately does not allocate a VMClass, metaclass, mixin or handle for it. The implementation refines the specification with this field-specific representation:

decodeSuperclass(Object, absent Java reference) = Top
decodeSuperclass(C, reference to S)             = S

Only Object’s superclass may use the absent case in a well-formed class graph. An absent lexical parent, receiver or class link has its own meaning; it does not denote Top. Neither Java absence nor Top is the canonical language null. The spec’s super(Object) = Top and the VM’s Object.superclassRef() == null therefore describe the same terminal structure at different representation levels.

The correspondence is local and concrete:

Semantic empty caseCurrent implementation
lin(Top) = []; exact/invocation search over it missesObjectProtocol stops when the superclass reference is absent, after searching Object’s contribution. No extra operation is selected or executed.
Top has an empty layout and no contributionClassConstruction.finish adds no superclass layout when that reference is absent; Object retains its ordinary owned mixin.
No initialization dependency on TopObject has no superclass initialization edge. No terminal initializer, activation, return home or argument evaluation is introduced.

No current source or boundary operation observes a Top object. Reification would extend the value contract and is justified only by an accepted feature requiring such a first-class reference. Its exposure, identity, class-of and construction rules would then need specification. The Top decision records that criterion and the rationale for the present representation.

ClassConstructionChecks asserts the absent root superclass and flat metaclass graph. NativeSeedSourceTest checks the corresponding source recipe. These are implementation evidence; the general Java simulation proof remains an obligation.

Private Construction Code

ConstructionCode generates CoreUserFunction bodies for ordinary primary new, default apply, owned initializers and class coordinators. Coordinators sequence dependency calls using CoreLet, then evaluate their owned body directly in the existing initializer home. The language schedule and argument binding are specified in Construction Order.

Private operationRequired backend work
AllocateAllocate one receiver using a bound class’s cached layout.
InvokeInitializerEvaluate receiver and arguments through frames; enter a bound complete coordinator or owned contribution with its occurrence and fresh home.
WriteSlotResolve the active initializer’s occurrence-local destination through the actual receiver layout before evaluating the value; retain the destination in a write frame.
SlotsCompleteEnable the post-slot phase after the final write has completed.

These operations have no selectors. new itself uses ordinary method lookup; no privileged construction lookup target is required. The construction decision records why the four operations are necessary.

Method Activations

MethodActivation records immutable parameter slots, the selected VMMethodClosure, receiver, caller continuation and a fresh return-home reference. Its lexical parent is a LexicalObjectScope, pairing the receiver with its selected contribution and linking to that contribution’s definition scope:

method activation
  → lexical receiver scope(receiver, applyingClass, contributionIndex, definition)
    → definition.definitionScope

InitializerActivation likewise has constructor parameter slots and a fresh home, plus slot/body phase state. Instances never acquire an automatic link to their own constructor activation. A lowered CoreLetExpression creates a separate activation, reserves all locals first, and inherits receiver and home metadata.

Lambda Activations

VMLambdaClosure retains its function, captured scope, receiver, applying class and return target. Invocation allocates parameter slots over the captured scope and restores the caller afterward, without a fresh home. Let/method/initializer activations can remain captured after their homes retire. Native tracing retains their reachable data without reviving return authority. The first collector conservatively also traces activation continuation links, which can retain old caller graphs; see collection trade-offs.

Dispatch Origin Tracking

For lexical lookup and super, VMMethodClosure retains (applyingClass, contributionIndex) separately from definition scope. MethodActivation.methodOrigin and LexicalObjectScope preserve that selection. Let/lambda activations follow lexical links; initializers use their own occurrence. Origins are neither inferred from a mixin’s source class nor copied to every activation.
