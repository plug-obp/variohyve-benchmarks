RELEASE REFERENCE · V0.3.2

This public reference is rendered from the v0.3.2 source commit f1c5c8cc77dc1dca4a1058d7a0e1369798535df8. Code, test and design-note links point to that exact revision in the private source repository and require repository access. Specification, tutorial and packaging-guide links are public.

Bring your own Alien package

A provider does not need to be shipped by VarioHyve or registered in host code. The current folder convention loads Java providers implementing the public ForeignObject boundary API. The provider adapts its foreign library; the native recipe chooses and constructs it. Other binary formats still need an appropriate bridge; the packager does not infer one from arbitrary classes or executables.

Start with the project from the installation walkthrough. New projects declare "alienRoot": "." in Main.vh.launch.json and contain their own aliens/console and aliens/starter-values folders. alienRoot is relative to the sidecar, just like root. It selects one package root for both startup adapter loading and recipe loadAlien calls. There is no fallback to the tools installation. Omit it for the older installed-provider behavior. Copy any other required built-in packages into your project's aliens directory explicitly.

Build a provider

The distribution includes two example Java sources in examples/custom-alien/src: MultiplierLibrary.java is an independent library; MultiplierRealizer.java is a small adapter. Neither is precompiled into the runtime or registered with it. Replace the library/adapter with your own when needed.

The realizer is a public concrete ForeignObject with a public no-argument constructor. Loading returns this callable realizer. Its apply/1 accepts a factor and returns a fresh capability exposing multiply/1. This example keeps only host scalars, so it needs no detached native receipts. Providers retaining native objects or callbacks must obey the boundary retention contract.

Set VH to the extracted tools directory and PROJECT to your project. If you installed only the VSIX, its packaging directory is the same tools distribution; you can use that directory as VH from VS Code's integrated terminal. The Java sources and boundary API are included there. These commands need only JDK tools and ordinary shell/file utilities, not the repository, Maven or Gradle:

mkdir -p "$PROJECT/build/library" "$PROJECT/build/provider" "$PROJECT/aliens/multiplier/lib"
javac --release 23 -d "$PROJECT/build/library" "$VH/examples/custom-alien/src/example/MultiplierLibrary.java"
jar --create --file "$PROJECT/aliens/multiplier/lib/multiplier.jar" -C "$PROJECT/build/library" .
javac --release 23 -cp "$VH/lib/*:$PROJECT/aliens/multiplier/lib/multiplier.jar" -d "$PROJECT/build/provider" "$VH/examples/custom-alien/src/example/MultiplierRealizer.java"
jar --create --file "$PROJECT/aliens/multiplier/provider.jar" -C "$PROJECT/build/provider" .

On Windows, create the directories with PowerShell and separate the two classpath entries with ; instead of :. Java 23+ supplies javac and jar. Compile against the API in lib/*; do not copy runtime or boundary API classes into the provider JAR. The package loader shares the boundary API and isolates provider implementation classes and dependencies.

Compute SHA-256 for both JARs (sha256sum on Linux, shasum -a 256 on macOS, or PowerShell Get-FileHash -Algorithm SHA256, converted to lowercase). Write aliens/multiplier/alien.json, replacing the two digest placeholders:

{
  "format": "variohyve-java-alien-1",
  "boundary": "variohyve-java-boundary-1",
  "java": 23,
  "entry": "example.MultiplierRealizer",
  "jars": [
    {"path": "provider.jar", "sha256": "<provider JAR SHA-256>"},
    {"path": "lib/multiplier.jar", "sha256": "<library JAR SHA-256>"}
  ],
  "deployment": {"provisioning": "none", "resources": []}
}

Declare every runtime dependency JAR. Declare required notices and other loose artifacts in deployment.resources using the same path/digest shape. Resources needed through Java's classloader belong inside declared JARs. Update digests when rebuilding; missing or changed bytes are errors. provisioning: "none" means the loader injects no ambient services; capabilities can still be supplied explicitly as realizer arguments. A provider requiring unsupported deployment provisioning is rejected, never silently converted into a deployable package. Classloader isolation does not sandbox Java code's host-process authority.

Compose, test and deploy

In World.vh, replace the native multiplier import with:

makeMultiplier = loadAlien("aliens/multiplier");
multiplier = makeMultiplier(3);

The application and tests stay unchanged: both the native package and this Alien expose multiply(value) and receive their factor at construction.

The existing test still expects 42. Run Test File and Run File in VS Code, or use vh-world as in the walkthrough. Each launch opens a fresh provider session; editing Java source alone does not rebuild a JAR or update its pin.

Remove source("packages/multiplier/Multiplier.vh") from Package.vh and add this declaration before output.finish():

output.alien("aliens/multiplier", sources.alien("aliens/multiplier"));

sources.alien captures the project's provider folder without initializing it; output.alien publishes its manifest, JARs and declared resources at the path used by the recipe. The existing native policy also captures the project's startup adapter and console. Neither development nor packaging searches for undeclared dependencies or changes the tools installation.

Use Package Application and Run Deployment, or the CLI commands in the walkthrough. The result contains the custom provider and its separate dependency JAR. Move it to another Java 23+ machine; the original project, compiled classes, tools installation and foreign source files are not needed at runtime. Both the CLI archive journey (--custom-alien) and real VSIX journey exercise this case, including a changed dependency pin and removal of the producing tools/project.
