Contract and conformance map

These stable IDs connect current contracts to their owners and executable evidence. They are navigation anchors, not a claim of complete language conformance. “Implemented” describes the listed scope; release validation is recorded separately. Proposed persistence, abstract execution and deep families remain outside this executable contract.

The specification defines language semantics and labelled runtime/tooling contracts. Accepted decisions record rationale. Tests check implementations and examples; they do not redefine either.

Specification, Java and Lean

Use this map to follow a claim across the three maintained descriptions. The specification defines source behavior; Java regressions and differential runs are executable evidence; Lean theorems have the domains and premises recorded in the proof ledger. No row asserts a formal refinement of Java. The detailed Lean traceability map owns construct-level theorem links rather than duplicating them here.

Run the validation matrix for current evidence: check-lean.sh checks proofs, ./gradlew test checks Java and executable specification examples, and the structural/native/entrypoint scripts compare implementations with independent expected observations. Passing one gate does not substitute for another. Performance reports remain revision-specific and do not establish semantic equivalence.

Small SDK boundary

The supported starter surface is the selected scalar protocols, explicit Console and parsers, small lists/maps, native SUnit and module composition. See the starter reference for exact messages. This release does not promote a filesystem API, registry, solver, network stack or general collection framework into the language. New host operations require a concrete boundary need; application composition and orchestration should start in native VarioHyve.
