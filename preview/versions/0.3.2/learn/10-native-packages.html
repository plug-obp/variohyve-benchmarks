LEARN VARIOHYVE · V0.3.2

Publish and consume a tiny native package

A native package can be a folder containing an entry module and a short contract. It needs no registry or package-manager syntax. Start with this complete Multiplier.vh:

// Entry module of an independently authored native package.
class Multiplier(factor) {
    factor = factor;
    multiply(value) { value.times(factor) }
}

Its contract names the entry, constructor input and multiply/1 protocol. The integer times/1 behavior comes from the chosen startup value adapter. No console, filesystem or kernel is supplied.

Publish the folder, then consume it

Copy or archive the multiplier folder. The tools archive also ships this independent producer as examples/native-package. A consumer copies that folder to packages/multiplier inside its own source root. Use the project from the previous chapter; it already contains this wiring.

In its recipe, importModule(files.resolve("packages/multiplier/Multiplier.vh"), 3) constructs the dependency. The recipe passes that object into Main.vh. The application sends multiply(14) and gets 42. It knows the protocol, not the file path or how the dependency was built.

In Package.vh, source("packages/multiplier/Multiplier.vh") declares the entry in the production inventory. Packaging captures its bytes and pins its digest. Run the tests, package the project and move the deployment elsewhere as before. The producer folder can be deleted: the consumer owns its copy and the deployment owns its captured bytes. Our extracted-archive check performs exactly that copy, then deletes both source project and producing tools before the final run.

For a package with several modules, document their inputs and declare each needed file in the consuming native policy. Directory names are distribution conventions; they do not add global names or implicit imports to VarioHyve.

Substitute an Alien without changing the application

The archive's CUSTOM-ALIENS.md explains how to compile the independently packaged Java multiplier and its separate dependency JAR. It implements the same multiply/1 protocol. Replace only the recipe's multiplier construction with loadAlien("aliens/multiplier"), followed by calling that realizer with factor 3. Replace the native source declaration in the policy with output.alien("aliens/multiplier", sources.alien("aliens/multiplier")).

Keep Main.vh and Tests.vh unchanged. Run, test and deploy again through the CLI or VS Code. The loader validates the package manifest, boundary version and JAR digests. Neither a built-in provider registration nor a repository checkout is needed. The host code is necessary here only to adapt the foreign library to the Alien boundary; composition and packaging policy remain native.
